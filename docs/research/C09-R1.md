## 1. Outcome

C09-R1 confirms the Arc premise but does not authorize production implementation.

The recommended research architecture is:

1. use `@solidity-parser/parser` only as an exact-version, test-only feasibility
   parser for C09-R3-A;
2. retain compiler-produced Solidity Standard JSON AST fixtures as a ground-truth
   comparator for selected corpus cases;
3. do not add `solc`, Tree-sitter, a Solidity grammar, or a custom tokenizer to
   the production package before C09-D;
4. keep source/value feasibility and Arc deployment association as separate
   experiments;
5. block public emission unless C09-R3-B proves an exact contract-to-Arc
   deployment association;
6. preserve both current public rule IDs until C09-D selects a migration.

The likely lowest-risk Build architecture, if later authorized, is one private
analyzer with temporary compatibility shells. This is only an R1 preference, not
an implementation decision.

## 2. First-party premise

Current Arc documentation states that:

- Arc targets the Prague EVM hard fork;
- `PREVRANDAO` always returns `0` on Arc;
- the value does not provide randomness on Arc;
- bridge contracts should not use `block.prevrandao` for relay shuffling or
  random selection;
- affected bridge logic should use an external oracle or deterministic
  round-robin design instead.

Pinned Arc sources:

- `https://docs.arc.io/integrate/infrastructure`
- `https://docs.arc.io/integrate/infrastructure/bridges`

Current Solidity documentation states that:

- `block.prevrandao` is available for Paris and later EVM targets;
- `block.difficulty` is a deprecated alias for `block.prevrandao` on later EVM
  targets;
- inline assembly `prevrandao()` is introduced for Paris and later targets;
- inline assembly `difficulty()` is disallowed for Paris and later targets;
- final opcode semantics still depend on the deployment chain.

Pinned Solidity sources:

- `https://docs.soliditylang.org/en/latest/cheatsheet.html`
- `https://docs.soliditylang.org/en/latest/using-the-compiler.html`
- `https://docs.soliditylang.org/en/latest/yul.html`

No pinned source establishes blanket source-text equivalence between `mixHash`
and PREVRANDAO.

## 4. Parser option audit

### Option A — `@solidity-parser/parser`

Observed research state:

- JavaScript package based on an ANTLR4 Solidity grammar;
- MIT license;
- latest observed release: `0.20.2`, published 2025-07-21;
- supports AST traversal and optional source locations;
- used by established Solidity tooling.

Advantages:

- direct Node.js integration;
- no compiler process required;
- contract, function, expression, and statement ownership can be tested through
  an AST rather than text proximity;
- location data can support deterministic evidence offsets.

Risks and required tests:

- it is not the official compiler AST;
- grammar coverage may lag current Solidity syntax;
- inline assembly and newer syntax must be tested explicitly;
- malformed-source recovery must fail closed rather than return partial evidence;
- AST node contracts and location behavior must be pinned by corpus tests;
- transitive dependency, package-size, and supply-chain cost must be measured
  before any production proposal.

R1 disposition: **selected for R3-A as a temporary exact-version test-only
feasibility parser**.

This selection does not authorize a production dependency.

### Option B — Solidity Standard JSON AST

The Solidity compiler documents Standard JSON as the recommended interface for
complex and automated compiler use. AST output can be requested for each source
unit.

Advantages:

- official compiler syntax and source ownership;
- compiler-version semantics are explicit;
- strong ground truth for contract, function, source, and expression structure;
- errors are returned in structured JSON.

Risks and workflow cost:

- compiler invocation is heavier than a parser-only library;
- `solc` always reports compiler errors through JSON and may still exit
  successfully, so error handling must be explicit;
- compiler-version coupling is unavoidable;
- `solc-js` is resource-intensive and materially enlarges the dependency and
  supply-chain surface;
- requiring users to compile source would change ArcReady's current static-scan
  workflow;
- imported source resolution introduces a wider project capability.

R1 disposition: **selected only as a retained-fixture ground-truth comparator**.

R3 may generate AST fixtures outside production runtime, record the exact
compiler version, and commit only the bounded fixture inputs required for
comparison. Production compiler invocation is not authorized.

### Option C — Tree-sitter with `tree-sitter-solidity`

Tree-sitter core is active and MIT licensed. The available Solidity grammar is
also MIT licensed and actively developed, but its own documentation states that
the generated AST structure is not stable.

Advantages:

- robust concrete syntax tree;
- useful source ranges;
- good malformed-source tolerance for editor tooling.

Risks:

- the Solidity grammar AST contract is explicitly unstable;
- malformed-source tolerance is undesirable if unsupported partial trees are
  accidentally treated as critical evidence;
- native or Wasm runtime integration adds build and packaging complexity;
- Solidity grammar coverage and Yul ownership still require separate validation.

R1 disposition: **rejected as the primary C09 feasibility parser**.

It may be revisited only if the selected ANTLR parser cannot represent a required
bounded source family and a separate dependency review is approved.

### Option D — custom narrow tokenizer or parser

Advantages:

- no third-party production dependency;
- grammar can be limited to the approved C09 surface.

Risks:

- comments, strings, nested expressions, casts, shadowing, contract/function
  ownership, inline assembly, malformed syntax, and source ranges quickly become
  a partial Solidity parser;
- maintenance burden moves into ArcReady;
- false-positive risk is high for a default critical rule;
- the implementation can silently expand into a general parser platform.

R1 disposition: **rejected as the first feasibility path**.

A custom tokenizer may be reconsidered only after the corpus proves that the
required grammar is substantially smaller than the selected parser surface.

## 5. Selected R3-A architecture

C09-R3-A should:

- pin one exact `@solidity-parser/parser` version in test-only scope;
- keep the package production manifest unchanged;
- parse complete `.sol` fixtures only;
- reject parser errors, missing locations, unknown nodes, ambiguous ownership,
  and malformed syntax;
- evaluate direct `block.prevrandao` first;
- evaluate inline assembly `prevrandao()` as a separate family;
- defer `block.difficulty` until exact post-Paris compiler/EVM-target evidence is
  present;
- exclude arbitrary bare `PREVRANDAO` identifiers and all `mixHash` matching;
- support direct expressions or one single-assignment same-function local binding
  only;
- prove the supported sink within the same function and contract candidate;
- compare selected positive, safe, and adversarial fixtures against retained
  compiler Standard JSON AST output;
- emit private research classifications only.

R3-A may receive explicit synthetic Arc ownership from its test harness to isolate
source and value-dependency feasibility. That synthetic input is not production
repository evidence and cannot authorize a public finding.

## 6. Minimum deployment-association contract

Production public emission requires all of the following:

1. an exact Solidity contract definition identity;
2. exact Arc network evidence through chain ID `5042002` or the official Arc
   Testnet RPC;
3. an exact deployment artifact or manifest entry naming that contract;
4. a deterministic path or identifier relationship between the artifact and the
   analyzed source definition;
5. one unambiguous Arc deployment association;
6. no conflicting network, contract, path, or duplicate deployment evidence.

The following are insufficient:

- a repository README mentioning Arc;
- an Arc comment or string in Solidity;
- an unrelated wallet or bridge config;
- a broad project-level Arc keyword;
- an imported or computed network value;
- a multichain config without contract-level association;
- a generated artifact that does not identify the source contract;
- synthetic R3-A ownership.

## 7. R3-B candidate boundary

R3-B should compare at most one adapter from each of these framework families:

- a Foundry broadcast or deployment artifact that records chain ID and exact
  contract identity;
- a Hardhat deployment artifact or manifest that records network identity and
  exact contract identity.

R3-B must not implement a generic deployment-discovery framework.

Before selecting one adapter, R2 must materialize complete-project fixtures for:

- exact contract and exact Arc chain association;
- same contract deployed only to Ethereum;
- one contract deployed to both Arc and another chain;
- two contracts with similar names;
- duplicate and conflicting deployment artifacts;
- artifact contract name with no matching Solidity definition;
- matching definition with no artifact;
- imported or computed chain IDs;
- generated artifact outside configured scan scope;
- path traversal and sibling-project isolation.

If no bounded adapter proves meaningful coverage without unrestricted cross-file
analysis, C09-R3-B must report deployment ownership as infeasible and C09-D must
choose Advice-only or Retire.

## 8. Public-ID and preset impact

R1 does not change either public ID.

If C09-D later authorizes Build, the lowest migration risk is currently:

- one private analyzer and one shared evidence model;
- temporary wallet and bridge compatibility shells;
- one execution cache or deterministic evidence key to prevent duplicate parser
  work and duplicate findings;
- each shell limited to sinks truthfully owned by its current preset contract;
- no new `solidity` preset or finding category;
- explicit later review to consolidate or retire the shells.

This preference remains provisional because R3 may show that only one sink family
is feasible or that Arc deployment association cannot be proven.

## 9. R2 handoff requirements

C09-R2 must create machine-validated complete-source and complete-project fixtures
with unique IDs.

Each case must record separate expected fields for:

```text
parseStatus
sourceClass
contractOwnership
functionOwnership
bindingClass
sinkClass
arcDeploymentOwnership
publicEmissionEligibility
```

Required parser pressure cases include:

- supported Solidity versions and exact pragma ranges;
- direct `block.prevrandao`;
- direct cast and modulo/index use;
- one single-assignment local binding;
- comments and strings between tokens;
- multiple contracts and functions;
- local shadowing and duplicate declarations;
- reassignment and branch joins;
- inline assembly `prevrandao()`;
- inline assembly `difficulty()`;
- unknown syntax and malformed source;
- unsupported Yul blocks;
- `block.difficulty` with and without exact EVM-target evidence;
- bare identifiers and `mixHash` names;
- LF and CRLF;
- deterministic earliest candidate selection.

R2 must also pin selected compiler AST fixture versions and verify that fixture
source hashes match their retained AST outputs.

## 10. Decision gates

C09-R3-A may begin only when:

- the R2 corpus is complete and machine validated;
- the test-only parser version is exact;
- parser error and location behavior are pinned;
- compiler AST comparator fixtures are reproducible;
- no production dependency is added.

C09-R3-B may begin only when:

- the deployment-association corpus is complete;
- at most one bounded adapter is selected for the first experiment;
- exact contract identity and Arc network evidence are specified;
- conflicts and ambiguity fail closed.

C09-D may select Build only when:

- R3-A proves bounded source ownership and value dependency;
- R3-B proves bounded contract-to-Arc deployment association;
- meaningful first-party or realistic pressure shapes are supported;
- duplicate public execution can be prevented;
- a production dependency and package-cost review is approved;
- public-ID, preset, severity, inventory, and deprecation behavior are explicit.

Otherwise C09-D must choose Advice-only or Retire.

C09-R1 does not authorize:

## 13. Conclusion

The Arc premise is strong enough to continue research, but the current critical
keyword rules are not defensible as value-dependency analyzers.

C09 should proceed to R2 with a complete corpus. R3-A should use an exact-version,
test-only ANTLR parser and retained official compiler AST fixtures. R3-B must
separately prove a bounded contract-to-Arc deployment association.

No public finding, production dependency, rule migration, or parser integration is
authorized by this artifact.
