## 1. Decision

C08-R2 defines one bounded feasibility family:

```text
CCTP V2 + direct global fetch + exact Iris host + same-file polling loop
```

The corpus does not authorize an analyzer or a public finding. It separates two
questions that the current rule conflates:

1. can ArcReady classify the owned polling control flow conservatively; and
2. is there enough provenance to justify a critical public finding?

A direct `transactionHash` parameter proves only which value is placed into the
request. It does not prove that the value came from a successful burn. Because
Circle documents incorrect transaction hash or source domain as possible causes
of `404`, an unsafe-looking terminal branch cannot become a critical finding
from request ownership alone.

C08-R3 must therefore test two independent gates:

- **control-flow feasibility** for the direct-fetch family; and
- **public-finding eligibility** based on same-file burn-result provenance.

If the second gate requires generic interprocedural or cross-file analysis, the
final C08 disposition must be Advice-only or Retire rather than an overclaimed
critical Build.

No Build, Advice-only, or Retire disposition is selected by R2.

## 2. First-family boundary

The first family includes only:

- plain `.js` and `.ts` files;
- CCTP V2 messages requests;
- exact Circle Iris production or sandbox host;
- direct global `fetch`;
- exact `/v2/messages/{sourceDomainId}` path;
- direct `transactionHash` query parameter;
- one direct same-file polling loop;
- direct response binding;
- direct status and response-body checks;
- direct retry delay;
- one bounded exit form.

The first family excludes:

- CCTP V1;
- Axios;
- shadowed or wrapped `fetch`;
- imported endpoint, domain, or delay configuration;
- helper polling functions called from another function;
- arbitrary URL construction;
- nested loops, callbacks, recursion, and mutation graphs;
- generic control-flow, SSA, taint, or data-flow;
- cross-file burn-result provenance.

Exclusion means unsupported, not incorrect.

## 3. Source-shape evidence

### 3.1 Circle documentation quickstarts

Current Circle Arc quickstarts use direct global `fetch` in `while (true)` with a
V2 messages URL. They delay and repeat while an attestation is not ready, then
return a completed message.

These examples are useful syntax seeds, but they do not establish the final
critical contract because they may:

- use an unbounded loop;
- retry multiple non-ready states through shared handling;
- lack a dedicated `429` policy;
- omit cancellation and timeout;
- rely on surrounding code for source-domain and burn-hash correctness.

### 3.2 Circle maintained sample application

The Circle-maintained `circlefin/circle-cctp-crosschain-transfer` sample uses a
more realistic React hook shape:

- an outer transfer flow receives a burn transaction hash from a burn helper;
- the outer flow passes that hash to `retrieveAttestation`;
- `retrieveAttestation(transactionHash, sourceChainId)` is another nested helper;
- `IRIS_API_URL` and `CHAIN_CONFIGS` are imported;
- the request domain is computed from
  `CHAIN_CONFIGS[sourceChainId].destinationDomain`;
- a local URL binding is passed to direct global `fetch`;
- `response.status === 404` delays and continues;
- another non-OK status throws;
- a complete body returns;
- other body states delay and repeat;
- the loop is unbounded;
- `429` is not handled separately.

This source demonstrates that real first-party usage needs helper-call and
imported-configuration provenance. It is a required pressure case, not a reason
to silently add those capabilities to the first family.

### 3.3 Public integration pressure

Public integrations additionally use:

- bounded-attempt direct-fetch loops;
- one-shot requests that stop on pending state;
- Axios loops that retry `error.response.status === 404`;
- shared endpoint builders;
- response parsing before status checks;
- dynamic host selection.

These shapes remain separate corpus families.

## 4. Two-stage classification contract

Each corpus case declares both fields below.

### 4.1 `controlFlowClass`

Allowed values:

```text
safe-candidate
unsafe-candidate
unsupported
```

`safe-candidate` means the exact owned polling source distinguishes modeled
pending, completion, rate-limit, unexpected-status, and bounded-exit behavior.
It is not a runtime safety claim.

`unsafe-candidate` means the exact owned polling source contains one supported
control-flow defect. It is not automatically a public finding.

`unsupported` means ownership or syntax is outside the bounded family. R3 must
produce no candidate for this class.

### 4.2 `publicFindingEligibility`

Allowed values:

```text
eligible-proven-burn
blocked-unproven-burn
not-applicable
```

`eligible-proven-burn` requires a separately approved same-file proof that the
queried transaction hash is the result of a successful supported burn operation
and that the source chain/domain pairing is exact.

`blocked-unproven-burn` means the request hash is owned syntactically but its
successful-burn provenance is not proven. An `unsafe-candidate` with this value
must not be emitted as a critical public finding.

`not-applicable` is used for safe and unsupported cases.

The first direct-parameter corpus intentionally contains no
`eligible-proven-burn` case. R3 must decide whether such a case can be added
without violating ArcReady's architecture.

## 6. Canonical safe-candidate source

```ts
const SOURCE_CHAIN_ID = 5042002;
const SOURCE_DOMAIN_ID = 26;
const MAX_ATTEMPTS = 60;

async function pollArcAttestation(transactionHash: string) {
  const url =
    `https://iris-api-sandbox.circle.com/v2/messages/${SOURCE_DOMAIN_ID}` +
    `?transactionHash=${transactionHash}`;

  for (let attempt = 0; attempt < MAX_ATTEMPTS; attempt += 1) {
    const response = await fetch(url);

    if (response.status === 404) {
      await new Promise((resolve) => setTimeout(resolve, 5_000));
      continue;
    }

    if (response.status === 429) {
      await new Promise((resolve) => setTimeout(resolve, 10_000));
      continue;
    }

    if (!response.ok) {
      throw new Error(`Unexpected Iris status: ${response.status}`);
    }

    const body = await response.json();

    if (body.messages.length === 0) {
      await new Promise((resolve) => setTimeout(resolve, 5_000));
      continue;
    }

    const message = body.messages[0];

    if (message.status === "pending") {
      await new Promise((resolve) => setTimeout(resolve, 5_000));
      continue;
    }

    if (message.status === "complete" && message.attestation) {
      return message;
    }

    throw new Error(`Unexpected attestation state: ${message.status}`);
  }

  throw new Error("Attestation polling timed out");
}

void SOURCE_CHAIN_ID;
void pollArcAttestation;
```

## 8. Complete pressure sources

### R2-P01 — Circle maintained sample shape

```ts
import { CHAIN_CONFIGS, IRIS_API_URL } from "./chains";

const POLL_INTERVAL_MS = 5_000;

export async function retrieveAttestation(
  transactionHash: string,
  sourceChainId: number
) {
  const url =
    `${IRIS_API_URL}/v2/messages/` +
    `${CHAIN_CONFIGS[sourceChainId].destinationDomain}` +
    `?transactionHash=${transactionHash}`;

  while (true) {
    const response = await fetch(url);

    if (response.status === 404) {
      await new Promise((resolve) => setTimeout(resolve, POLL_INTERVAL_MS));
      continue;
    }

    if (!response.ok) {
      throw new Error(`Attestation request failed: ${response.status}`);
    }

    const body = await response.json();
    if (body?.messages?.[0]?.status === "complete") {
      return body.messages[0];
    }

    await new Promise((resolve) => setTimeout(resolve, POLL_INTERVAL_MS));
  }
}
```

Expected:

```text
controlFlowClass=unsupported
publicFindingEligibility=not-applicable
```

Missing first-family proof:

- imported host;
- computed source domain;
- complete-only body model;
- no dedicated `429` branch;
- no bounded exit.

## 10. Burn-provenance feasibility obligations

R3 must test whether a separate exact source can establish
`successfulBurnProvenance=proven-supported-sink` without generic analysis.

At minimum, research must consider:

1. direct same-function burn call returning the queried hash;
2. direct receipt or success evidence required before polling;
3. exact CCTP TokenMessenger or supported SDK identity;
4. exact source chain/domain pairing;
5. no imported sink, config, wrapper, or cross-file value;
6. no helper-call chain beyond an explicitly reviewed bound;
7. no assumption that a variable named `burnTx` proves a successful burn.

The Circle maintained sample does not satisfy this first-family gate because its
burn helper, client construction, addresses, and domain mapping depend on
imported or computed configuration.

If no meaningful real-world source satisfies the bounded burn gate, C08 must not
ship a critical Build merely because control-flow parsing is technically
possible.

## 12. R3 decision gates

A technical control-flow prototype passes only if it:

- handles every safe and unsafe candidate correctly;
- produces no candidate for every unsupported case;
- proves request, response, loop, status, body, delay, and terminal-action
  ownership without generic CFG, SSA, taint, or cross-file resolution.

A critical Build remains blocked unless R3 also demonstrates a meaningful
`eligible-proven-burn` family.

Therefore:

- control-flow pass + burn-provenance pass may support a Build proposal;
- control-flow pass + burn-provenance failure supports Advice-only or Retire;
- control-flow failure supports Advice-only or Retire;
- negligible coverage of real first-party shapes is a product failure even when
  the parser technically passes synthetic cases.
