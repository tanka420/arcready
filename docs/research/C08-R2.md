## 1. Decision

C08-R2 defines one bounded feasibility family:

```text
CCTP V2 + direct global fetch + exact Iris host + same-file polling loop
```

The corpus does not authorize an analyzer or a public finding. It separates two
questions that the current rule conflates:

1. can ArcReady classify the owned polling control flow conservatively; and
2. is there enough source-level burn-hash provenance to justify a critical
   public finding?

A direct `transactionHash` parameter proves only which value is inserted into
the request. It does not prove that the value came from an exact burn call, that
a receipt was checked, or that the burn succeeded at runtime.

Because Circle documents incorrect transaction hash or source domain as possible
causes of `404`, an unsafe-looking terminal branch cannot become a critical
finding from request ownership alone.

C08-R3 must therefore test two independent gates:

- **control-flow feasibility** for the direct-fetch family; and
- **public-finding eligibility** based on a separately reviewed exact same-file
  burn-hash source and receipt guard.

Even the strongest source-level burn evidence remains a static source claim. It
must not be described as proof of runtime burn success.

If the eligibility gate requires generic interprocedural or cross-file analysis,
C08-D must choose Advice-only or Retire rather than an overclaimed critical
Build.

No Build, Advice-only, or Retire disposition is selected by R2.

## 2. First-family boundary

The first control-flow family includes only:

- plain `.js` and `.ts` files;
- CCTP V2 messages requests;
- exact Circle Iris production or sandbox host;
- direct global `fetch`;
- exact `/v2/messages/{sourceDomainId}` path;
- direct `transactionHash` query parameter;
- one direct same-file polling loop;
- direct response binding;
- direct status and response-body checks;
- direct retry delay;
- one bounded exit form.

The first family excludes:

- CCTP V1;
- Axios;
- shadowed or wrapped `fetch`;
- imported endpoint, source/domain pair, or delay configuration;
- helper polling functions called from another function;
- arbitrary URL construction;
- nested loops, callbacks, recursion, and mutation graphs;
- generic control-flow, SSA, taint, or data-flow;
- cross-file burn-hash provenance.

Exclusion means unsupported, not incorrect.

## 3. First-party source-shape evidence

### 3.1 Circle documentation quickstarts

Current Circle Arc quickstarts use direct global `fetch` in `while (true)` with a
V2 messages URL. They delay and repeat while an attestation is not ready, then
return a completed message.

These examples are syntax seeds, not a complete critical contract, because they
may:

- use an unbounded loop;
- retry multiple non-ready states through shared handling;
- lack a dedicated `429` policy;
- omit cancellation and timeout;
- rely on surrounding code for source-domain and burn-hash correctness.

### 3.2 Circle maintained sample application

The Circle-maintained `circlefin/circle-cctp-crosschain-transfer` sample uses a
more realistic React hook shape:

- an outer transfer flow receives a burn transaction hash from a burn helper;
- the outer flow passes that hash to `retrieveAttestation`;
- `retrieveAttestation(transactionHash, sourceChainId)` is another nested helper;
- `IRIS_API_URL` and `CHAIN_CONFIGS` are imported;
- the request domain is computed from
  `CHAIN_CONFIGS[sourceChainId].destinationDomain`;
- a local URL binding is passed to direct global `fetch`;
- `response.status === 404` delays and continues;
- another non-OK status throws;
- a complete body returns;
- other body states delay and repeat;
- the loop is unbounded;
- `429` is not handled separately.

This first-party source demonstrates that meaningful production-like coverage
requires helper-call and imported-configuration provenance. It is a pressure
case, not a reason to silently add those capabilities to the first family.

### 3.3 Alternate public shapes

Other public CCTP integrations use:

- bounded-attempt direct-fetch loops;
- one-shot requests that stop on pending state;
- Axios loops that retry `error.response.status === 404`;
- shared endpoint builders;
- response parsing before status checks;
- dynamic host selection.

These remain separate corpus families.

## 4. Two-stage classification contract

Every materialized case declares both fields below.

### 4.1 `controlFlowClass`

Allowed values:

```text
safe-candidate
unsafe-candidate
unsupported
```

`safe-candidate` means the owned source distinguishes modeled pending,
completion, rate-limit, unexpected-status, and bounded-exit behavior. It is not
a runtime safety claim.

`unsafe-candidate` means the owned source contains one supported control-flow
risk. It is not automatically a public finding.

`unsupported` means ownership or syntax is outside the bounded family. R3 must
produce no candidate for this class.

### 4.2 `publicFindingEligibility`

Allowed values:

```text
eligible-source-validated-burn
blocked-unvalidated-burn
not-applicable
```

`eligible-source-validated-burn` requires a separately approved exact same-file
source relation from a supported CCTP burn sink, through a source-level receipt
or success guard, into the queried hash and matching source chain/domain pair.

The term describes source evidence only. It does not prove runtime burn success,
Circle observation, API availability, or mint success.

`blocked-unvalidated-burn` means the request hash is owned syntactically but the
burn source/guard is not proven. An unsafe candidate with this value must not be
emitted as a critical public finding.

`not-applicable` is used for safe and unsupported cases.

The current 51-case corpus intentionally contains no
`eligible-source-validated-burn` case. R3 must decide whether a meaningful exact
family can be added without violating ArcReady's architecture.


co-located constants.

## 8. Representative corpus pressure

The complete corpus includes these boundaries:

- production and sandbox Iris hosts;
- direct URL and one immutable URL binding;
- direct hash parameter and one immutable hash alias;
- exact Arc/26 and Ethereum/0 source objects;
- bounded `for`, bounded `while`, deadline, and abort-aware variants;
- terminal throw, return, and break on owned `404`;
- immediate retry without delay;
- `404`/`429` conflation;
- terminal empty or pending body states;
- completed attestation ignored;
- unexpected non-OK silently retried;
- bounded exit removed;
- wrong, imported, or computed hosts/domains/hashes;
- V1, Axios, wrapper, helper, nested-loop, alias-chain, mutation, documentation,
  malformed, and TSX cases;
- the Circle maintained imported-config/helper shape.

## 9. Burn-hash eligibility experiment

R3 must separately test whether a meaningful source can establish:

```text
burnHashProvenance=exact-source-sink-and-receipt-guard
```

At minimum, the experiment must require:

1. an exact supported CCTP burn sink;
2. direct same-file ownership of the returned transaction hash;
3. a reviewed source-level receipt or success guard before polling;
4. exact source chain/domain pairing;
5. direct transfer of the guarded hash into the V2 messages request;
6. no imported sink, client, address, domain map, wrapper, or cross-file value;
7. no assumption that a variable named `burnTx` proves anything.

The Circle maintained sample does not satisfy this first experiment because its
burn helper, client construction, addresses, and domain mapping rely on imported
or computed configuration.

If no meaningful real-world source satisfies the bounded eligibility gate, C08
must not ship a critical Build merely because control-flow parsing is technically
possible.

## 10. R3 decision gates

A control-flow prototype passes only if it:

- matches all nine safe candidates;
- matches all eleven unsafe candidates with the exact class;
- produces no candidate for all thirty-one unsupported cases;
- proves request, response, loop, status, body, delay, and terminal-action
  ownership without generic CFG, SSA, taint, or cross-file resolution.

A critical Build remains blocked unless R3 also demonstrates a meaningful exact
source-validated burn-hash family.

Therefore:

- control-flow pass plus eligibility pass may support a Build proposal;
- control-flow pass plus eligibility failure supports Advice-only or Retire;
- control-flow failure supports Advice-only or Retire;
- negligible coverage of first-party shapes is a product failure even when the
  parser technically passes synthetic cases.
