## 1. Purpose

C09-R2 materializes the complete-source and complete-project evidence matrix
required before any Solidity parser or deployment adapter is prototyped.

The corpus is a research contract, not a detector implementation. It does not
change either PREVRANDAO rule, add a parser dependency, or authorize public
findings.

## 3. Expected classification fields

Each case records all of the R1-required evidence dimensions:

```text
parseStatus
sourceClass
contractOwnership
functionOwnership
bindingClass
sinkClass
arcDeploymentOwnership
publicEmissionEligibility
```

These fields are intentionally independent. A parseable PREVRANDAO source can be
blocked by unsupported value flow, a missing sink, or absent Arc deployment
ownership.

## 4. Source corpus

The source corpus covers:

- direct `block.prevrandao` modulo and array-index selection;
- direct casts and one single-assignment same-function binding;
- authorization and ordering sinks;
- exact inline assembly `prevrandao()` extraction;
- compiler-target-gated `block.difficulty`;
- LF and CRLF;
- diagnostic return, event emission, zero assertions, unused values, and hashing
  without a supported sink;
- deterministic replacement logic;
- comments, strings, bare identifiers, and `mixHash` names;
- reassignment, two-hop aliases, branch joins, loops, cross-function flow, and
  cross-contract flow;
- unsupported Yul, assembly `difficulty()`, malformed Solidity, and future
  grammar;
- same-line false-positive pressure, different-function and different-contract
  ownership, shadowing, mutation, indirect collection length, and deterministic
  earliest-candidate pressure.

Source cases use `synthetic-r3a` ownership only. That value permits parser and
value-flow feasibility testing; it never qualifies a public finding.

## 5. Project corpus

The project corpus pins two reviewed artifact contracts:

- Foundry `forge script` broadcast `run-latest.json`, with chain identity in the
  broadcast path and JSON and CREATE contract identity in the transaction record;
- hardhat-deploy v1, with network identity in
  `deployments/<network>/.chainId` and contract identity in the deployment
  filename. The contract JSON uses the v1 `address` and `abi` contract; inline
  `contractName`, `receipt.chainId`, and `rpcUrl` fields are negative pressure,
  not accepted evidence.

Hardhat-deploy v2 uses a different Rocketh-based artifact contract and remains
outside this corpus.

It covers:

- exact Arc chain ID and contract-name association;
- exact official Arc RPC and contract-name association;
- Ethereum-only deployment;
- one contract deployed to Arc and another chain;
- duplicate and conflicting artifacts;
- artifact without matching Solidity definition;
- definition without artifact;
- similar contract names;
- imported or computed chain IDs;
- generated artifacts outside configured scope;
- sibling-project isolation;
- traversal-like paths;
- network-directory names without exact network evidence;
- conflicting chain ID and RPC evidence.

R2 compares both framework families. Independent review selects Foundry
broadcast artifacts for the first C09-R3-B adapter experiment because the bounded
path and JSON expose chain identity and CREATE contract names directly. The
hardhat-deploy v1 cases remain comparison and negative pressure only. R3-B remains
limited to exactly one framework-specific adapter total.

## 6. Public-emission boundary

The corpus uses these eligibility states:

- `r3a-candidate-only`: source/value experiment only;
- `r3b-association-candidate`: project association suitable for later adapter
  evaluation;
- `blocked-no-arc-association`: source may be interesting but Arc ownership is
  absent, ambiguous, conflicting, or unsupported;
- `blocked-unsupported`: parser, ownership, binding, or sink exceeds the bounded
  grammar;
- `not-applicable`: safe or non-reportable source.

No case is labeled production-public-eligible. That decision remains blocked
until both R3-A and R3-B succeed and C09-D approves a migration.

## 7. Compiler AST comparator set

R2 selects a small comparator set spanning positive, safe, assembly, and
adversarial ownership cases:

```text
C09-S01
C09-S03
C09-S06
C09-N04
C09-A03
```

The corpus pins compiler version `0.8.30` and computes a SHA-256 for each source.
The retained Standard JSON AST manifest records both source and normalized AST
hashes. The research-only generator invokes exact `solc 0.8.30` Standard JSON and
supports `--check` mode, which fails unless regenerated compiler output is
semantically identical to the retained manifest.

Compiler AST generation is a research build step only. It does not add `solc` or
`solc-js` to the production package manifest.

## 8. Validator guarantees

The module rejects:

- duplicate case IDs;
- unknown enum values;
- empty or missing files;
- unresolved placeholders;
- source cases with more than one file;
- project cases without a Solidity source or deployment/project companion file;
- unknown deployment artifact contracts;
- hardhat-deploy v1 contract files that contain nonstandard inline network or
  contract-identity fields;
- malformed CRLF pressure with CR-CR-LF or lone LF;
- missing comparator sources;
- invalid source SHA-256 values;
- fewer than 35 source cases;
- a project-case count other than 16.

The validator also reports counts by public eligibility and Arc deployment
ownership so review can detect accidental distribution drift.

## 9. Explicit exclusions

C09-R2 does not:

- execute `@solidity-parser/parser`;
- add a production or development dependency;
- implement Solidity AST traversal;
- implement a Foundry or Hardhat adapter;
- choose the R3-B framework;
- infer ownership from README, comments, broad Arc keywords, or unrelated files;
- treat `mixHash` or bare `PREVRANDAO` identifiers as opcode sources;
- change current public rules, IDs, presets, severity, catalog, scoring, reports,
  CLI, schemas, fixtures, or FindingV2.

## 10. R3 handoff

C09-R3-A may begin only after independent review confirms that:

- the source cases adequately separate source, ownership, binding, and sink
  evidence;
- safe and adversarial cases prevent obvious keyword and ownership shortcuts;
- comparator AST artifacts and hashes are reproducible;
- the exact parser version remains test-only.

C09-R3-B may begin only after independent review confirms the Foundry broadcast
family as the single first adapter experiment. Hardhat support requires a later
separate adapter review.

## 12. Exit criteria

C09-R2 is complete only when:

- all source and project cases are materialized;
- the validator passes;
- retained compiler AST outputs are linked to exact source hashes and compiler
  version;
- independent review reports zero blocker, major, and minor findings;
- full repository verification passes;
- no production behavior changes.
