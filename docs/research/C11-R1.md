## 1. Research question

After C10 selected Research / Defer, ArcReady's roadmap requires real repository
and user evidence before another analyzer milestone. This audit asks:

1. what the current default scan reports on current Arc integrations;
2. whether those findings are truthful and actionable;
3. whether repeated unsupported patterns or premise defects justify a bounded
   correction.

The audit does not treat a finding count as proof. Every reported file is read
against the rule's claimed ownership and current first-party Arc guidance.

## 4. Finding classification

### 4.1 `NO_ETH_GAS_LABEL`

Six of the seven ArcLens file findings are concrete false positives:

- correct contrast copy such as “Gas paid in USDC — not ETH”;
- correct explanatory copy that Arc uses USDC and has no ETH exposure;
- an AI/tool description that explicitly tells users gas is paid in USDC;
- a base-fee display in Gwei alongside a dollar amount.

The seventh file is mixed. It contains an “ETH Transfer” example that may be
actionable, but the file also contains first-party-compatible Gwei gas
calculation and display. The file-level finding does not identify which line or
which claim justified the critical result.

Current official Arc custody guidance expresses minimum base fee and EIP-1559
fee fields in Gwei. Therefore `gwei` is not evidence that a fee is denominated
in ETH. Current line matching also does not recognize plain “not ETH” as
corrective guidance.

Result: the rule drove one real repository to score zero from six definite false
positives and one mixed file. This satisfies the adoption trigger to implement
the backlog's existing Advice-only decision through a separately reviewed R3
default/severity/public-contract migration. It does not justify another regex
patch inside C11.

### 4.2 `ARC_CHAIN_METADATA` hexadecimal identity

The adoption audit exposed an independent exact-value defect:

- official Arc pages consistently identify Arc Testnet as decimal chain ID
  `5042002`;
- one official wallet page renders that as `0x4CF4B2`, but that hexadecimal
  value is decimal `5043378` and conflicts with its own decimal value;
- a read-only `eth_chainId` call to `https://rpc.testnet.arc.network` returned
  `0x4cef52`;
- `0x4cef52` is decimal `5042002`;
- ArcReady's C07 transaction analyzer and tests already use `0x4cef52`;
- the real ArcLens EIP-3085 request also uses `0x4cef52`.

The wallet chain-object scanner currently special-cases the wrong
`0x4cf4b2` value and converts it to `5042002n`. The public remediation text and
catalog also recommend that wrong hexadecimal string.

The scanner is shared by `wallet/ARC_CHAIN_METADATA` and
`wallet/WALLET_NATIVE_USDC_DISPLAY`. That creates a second current defect: a
generic object named only `chain` can use `0x4cf4b2` as its sole Arc-ownership
evidence and receive a native-currency finding. Once the value is parsed
truthfully as `5043378n`, that generic object must become ineligible rather than
being silently treated as Arc. An independently Arc-owned object, such as
`arcTestnet` or one with `name: "Arc Testnet"`, remains eligible and can report
both the wrong ID and any supported native-currency contradiction.

Three complete CLI probes demonstrate the current behavior:

| Probe                | Chain ID   | Current result                       |
| -------------------- | ---------- | ------------------------------------ |
| correct live hex     | `0x4CEF52` | pass                                 |
| wrong documented hex | `0x4CF4B2` | pass — false negative                |
| control wrong hex    | `0x1`      | `wallet/ARC_CHAIN_METADATA` critical |

The wrong value is accepted only because of the explicit production alias.
JavaScript `BigInt` parsing already handles the correct hexadecimal value.

## 5. Product decision

Proceed with one bounded C11 correction:

1. remove the incorrect `0x4cf4b2 → 5042002n` alias;
2. use `0x4CEF52` in legacy and FindingV2 remediation;
3. replace safe tests with the correct hexadecimal value;
4. add regressions proving string and numeric `0x4CF4B2` are incorrect;
5. make the shared native-display ownership effect explicit and fail closed;
6. align the rule catalog.

This passes the product decision test:

- EIP-3085 hexadecimal chain IDs are a real Arc wallet integration surface;
- the exact literal can be proven locally without new analysis infrastructure;
- the corrective action is exact and mechanically verifiable.

Risk is R2 because a default critical rule will begin reporting one exact
previously accepted wrong value and the same shared scanner will stop treating
that non-Arc value as independent Arc ownership. The architecture remains
unchanged: bounded object ownership, literal identity, severity, inventory, and
reporting paths are retained.

## 6. Deliberate scope boundary

C11 does not:

- change `NO_ETH_GAS_LABEL` code, severity, default status, message, or tests;
- claim the gas-label rule is safe;
- introduce a new rule ID or analyzer;
- add any chain-object ownership source, syntax, path, or endpoint logic;
- change inventories, presets, schemas, reporters, score weights, or exit
  policy;
- call Arc RPC during production scans;
- silently correct or reinterpret other first-party documentation.

The gas-label evidence triggers a separate R3 architecture and implementation
milestone for the existing Advice-only decision. That milestone must define
default exclusion or explicit opt-in, severity, and the public-contract
migration. C11 performs neither that migration nor another regex patch.

## 7. Validation contract

The correction must demonstrate:

- decimal `5042002`, string `"5042002"`, numeric `0x4cef52`, and string
  `"0x4CEF52"` remain safe;
- numeric and string `0x4cf4b2` produce one deterministic incorrect-ID finding;
- generic numeric and string `0x4cf4b2` do not independently establish Arc
  ownership for `WALLET_NATIVE_USDC_DISPLAY`;
- independently Arc-owned wrong-hex metadata still exposes a supported
  native-currency contradiction;
- combined wallet execution locks the intended finding count, order, score,
  status, and exit behavior;
- other wrong IDs and ambiguous shapes retain current behavior;
- legacy and FindingV2 remediation contain `0x4CEF52` and never `0x4CF4B2`;
- the focused wallet and FindingV2 suites pass;
- the exact cumulative candidate passes independent adversarial review and
  `corepack pnpm verify:full` before merge.

## 8. Residual limitations

The eight-repository corpus is bounded and can miss other false-positive and
false-negative classes. The exact hex defect does not depend on corpus
completeness because integer conversion, live RPC evidence, existing C07
semantics, and controlled CLI probes agree.

No claim is made that the remaining seven clean scans prove those projects free
of Arc integration problems. They show only that the current default rules did
not emit findings on the discovered files.
