# C10-R1 — Versioned App Kit Compatibility Baseline and Spike

Status: Complete — Research / Defer

Risk: R3 premise and architecture assessment

Base branch: `main`

Base SHA: `6a01ea832555bb8c62bc71013f0013ca4ceb1534`

Research branch: `docs/c10-versioned-app-kit-plan`

Verified: 2026-08-20

## 1. Research question and outcome

C10 investigated whether ArcReady should replace the deprecated generic App Kit
capability detector with a version-aware compatibility rule.

Outcome: Defer implementation.

The research found a real official version boundary and demonstrated a narrow
syntax path, but did not find a real pre-boundary integration failure that
justifies a new default critical finding. The initial build candidate also used
the wrong release floor and did not prove effective installed-version or
receiver ownership.

## 2. Official evidence

### Arc documentation

Verified on 2026-08-20:

- `https://docs.arc.io/app-kit/references/supported-blockchains`
  - identifiers are case-sensitive;
  - Arc Testnet uses `Arc_Testnet`;
  - current Arc Testnet support includes Send, Bridge, Swap, and Unified
    Balance;
  - Bridge and Unified Balance support USDC only;
  - Arc Testnet Swap lists USDC, EURC, and cirBTC;
  - adapter support is a separate compatibility dimension.
- `https://docs.arc.io/app-kit/references/sdk-reference`
  - `AppKit.getSupportedChains(operationType)` is the documented runtime
    discovery API;
  - operation types and parameter shapes are versioned.
- `https://docs.arc.io/app-kit`
  - official examples use nested operation-specific adapter and chain context.

These current pages describe the supported surface. They do not by themselves
establish when each capability first shipped.

- 1.4.0: Unified Balance support.

The inspected 1.3.0 declarations include `SwapChain.Arc_Testnet`. Therefore the

The inspected 1.0.0 tarball does not contain the implementation and declaration
entrypoints named by its package metadata. It cannot be treated as equivalent
to every later pre-1.3.0 release. A truthful historical matrix would require
release-by-release package inspection and classification.

## 3. Real-repository and compiler evidence

Public repository inspection found JavaScript App Kit Arc Swap integrations,
including a project declaring 1.3.0 and another declaring 1.8.1. These examples
confirm that JavaScript/no-checkJs call shapes exist, but both are at or above
the corrected support floor.

Search did not produce a real project that both:

1. effectively used a pre-1.3.0 App Kit release; and
2. attempted Arc Testnet Swap in a language/toolchain path that permitted it.

Compiling the proposed direct `Arc_Testnet` Swap literal against the published
1.2.1 TypeScript declarations produces TS2322 because that chain is not in the
pre-support Swap type. The compiler already prevents the exact typed pattern
the candidate intended to make a default critical finding.

Absence from a bounded repository search is not proof that the bug never
occurs. It is enough to show that the research did not satisfy the product
contract required before building a trusted default rule.

## 4. Existing ArcReady baseline

At base `6a01ea8`:

- `app-kit/APPKIT_CHAIN_IDENTIFIER_VALID` is a default critical regex rule;
- it can match unsupported-looking Arc strings without proving an App Kit
  argument or configuration slot;
- `app-kit/APPKIT_CAPABILITY_SUPPORTED` relies on generic guard words or a
  nearby `try` block;
- the capability rule is deprecated, default-excluded, low-confidence, and
  retained only for public API compatibility;
- the package already depends on TypeScript, but dependency availability alone
  does not justify new analyzer infrastructure.

C10 does not change either existing rule. Their documented precision limits
remain open product debt rather than evidence for a version rule.

## 5. Disposable syntax spike

A disposable TypeScript AST probe exercised ten declared examples covering
direct Bridge, Swap, and Send chain slots; valid literals and enum members;
local lookalikes; unrelated strings; spreads; and bound objects.

Result: `10 / 10` matched the probe's declared outcomes.

The probe showed that this exact lexical path is feasible:

```text
named @circle-fin/app-kit import
→ direct const new AppKit() binding
→ direct operation call
→ direct parameter object
→ operation-owned chain slot
→ exact literal
```

It did not test version classification, installed-package ownership, or the full
production lexical contract. Specifically it did not establish:

- package-manager resolutions, overrides, workspaces, or lockfile authority;
- receiver mutation, escape, deletion, aliasing, or property replacement;
- source-order and block/function shadowing;
- field-specific shorthand, duplicate, computed, method, or accessor policy;
- malformed TypeScript AST shape handling;
- public-rule naming, severity, default status, scoring, or exit behavior.

The spike is evidence of syntactic feasibility only.

## 6. Independent architecture review

The initial candidate proposed a new default critical rule for exact manifest
versions below 1.4.0 plus a direct owned Arc Testnet Swap call.

Independent review result: `CHANGES_REQUIRED — 1 blocker / 5 major / 0 minor`.

The blocker was the false 1.4.0 floor. The five major classes were:

1. no demonstrated real pre-floor user problem and a TypeScript compiler that
   already rejects the proposed exact pattern;
2. root manifest declaration was treated as the effective installed version;
3. the supported object-shape contract contradicted its shorthand example;
4. immutable receiver binding did not prevent method mutation or escape;
5. the proposed public ID overclaimed a single Arc Swap/version boundary.

The review established an architecture reset condition before any runtime code
or fixture expansion.

## 7. Options after correction

### A — Patch the floor and keep the build

Rejected. Changing 1.4.0 to 1.3.0 repairs the blocker but not the missing
product evidence or effective-version ownership problem.

### B — Add lockfile/workspace resolution

Rejected. This creates a broad dependency-analysis platform before a proven
rule consumer exists and still does not establish a real user problem.

### C — Limit the rule to JavaScript

Rejected for now. JavaScript integration shapes exist, but no real pre-floor
Arc Testnet Swap case was found. A hypothetical audience is insufficient for a
new default critical rule.

### D — Research / Defer

Selected. Preserve current public/runtime boundaries, record precise reopening
evidence, and spend implementation effort on demonstrated Arc integration
problems.

## 8. Reopen evidence

A future milestone may reassess versioned App Kit compatibility when a real
repository, user report, repeated unsupported pattern, or first-party premise
change demonstrates the problem. It must then pin the exact affected release
class and prove effective version plus operation ownership.

Separate evidence may justify hardening
`app-kit/APPKIT_CHAIN_IDENTIFIER_VALID`, but invalid-spelling evidence does not
prove a version-operation problem and must not be used to revive this plan.

## 9. Final research boundary

C10-R1 authorizes no production implementation, public ID, rule inventory,
severity, score, exit, schema, reporter, config, preset, package, or dependency
change. The deprecated capability rule remains default-excluded and unchanged.

The research conclusion is intentionally narrow: the version-aware App Kit
rule candidate is deferred until product evidence satisfies the repository's
three-part decision test.
