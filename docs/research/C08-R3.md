## 1. Decision

C08-R3 reaches two different conclusions.

### Control-flow feasibility: pass

A private TypeScript AST prototype can classify the deliberately narrow C08-R2
family without generic CFG, SSA, taint, package resolution, or cross-file data
flow.

The corrected prototype passes:

- all 51 source cases;
- all 9 safe candidates;
- all 11 unsafe candidates;
- all 31 unsupported cases;
- one explicit R3 corpus erratum invariant;
- ten adversarial ownership and policy tests;
- one invariant that every unsafe candidate remains blocked from public emission.

### Critical public-finding feasibility: fail

The control-flow pass is insufficient for a critical Build.

All 11 unsafe candidates remain:

```text
publicFindingEligibility=blocked-unvalidated-burn
```

No corpus case proves a meaningful exact source relation from a supported CCTP
burn call, through a source-level receipt or success guard, into the queried
transaction hash and matching source chain/domain pair.

Current first-party integration shapes also exceed the bounded control-flow
surface. Expanding the prototype to cover them would require imported client and
configuration provenance, helper-call ownership, richer URL construction,
additional HTTP shapes, and inter-function hash flow.

C08-R3 therefore recommends that C08-D select:

```text
Advice-only
```

It does not recommend Build.

## 2. Prototype boundary

The disposable prototype accepts only plain `.js` and `.ts` sources that prove:

- one exact `SOURCE` object with either Arc/26 or Ethereum/0 pairing;
- one exact `pollArcAttestation` function;
- one direct polling loop;
- one direct global `fetch` call;
- one direct response binding;
- an exact Circle Iris V2 messages URL;
- direct or one-const transaction-hash request ownership;
- separate `404`, `429`, and unexpected non-OK branches;
- direct V2 empty, pending, and complete body branches;
- direct numeric retry delays;
- an attempt or deadline bound, with an optional direct abort check;
- a direct terminal timeout after the loop.

It fails closed for:

- V1 endpoints;
- Axios and wrapper clients;
- shadowed `fetch`;
- imported host, source/domain pair, or transaction hash;
- environment-selected or computed URLs;
- helper polling boundaries;
- nested loops;
- multiple requests or crossed response ownership;
- alias and mutation graphs;
- response JSON consumed before status ownership;
- imported or computed delay helpers;
- callback terminal actions;
- malformed source and TSX.

This is a research grammar, not a proposed public API.

## 4. CI-discovered corrections

The first full corpus run was valuable because it rejected three mistaken
assumptions.

### 4.1 Supported action with wrong policy is unsafe

The initial prototype classified these as unsupported:

- retrying after a completed attestation;
- retrying an unexpected non-OK response.

Both actions are syntactically owned and supported by the bounded grammar. They
are wrong policy choices, so their correct class is `unsafe-candidate`.

The corrected branch classifier now follows this rule:

```text
unknown action -> unsupported
known required action -> safe-candidate
known but different action -> unsafe-candidate
```

### 4.2 Removing an optional semicolon is not malformed source

C08-R2 case `R2-X25` removed the semicolon after a final `void` expression and
expected a parse failure. JavaScript and TypeScript accept that source through
automatic semicolon insertion.

R3 does not teach the analyzer to reject valid semicolonless code. Instead,
`docs/research/fixtures/c08-r3-corpus.mjs` records one transparent overlay:

```text
R2-X25: optional-semicolon-is-valid
```

The overlay appends an unmatched parenthesis to exercise an actual parse error.
The merged C08-R2 corpus remains unchanged for auditability.

### 4.3 Public eligibility failure was consequential, not independent

The initial aggregate eligibility assertion failed only because two owned unsafe
cases were incorrectly labeled unsupported. After correction, all 11 unsafe
cases are classified correctly and remain blocked from public emission.

### 4.4 Independent review hardened structural ownership

Independent review required the prototype to prove, rather than infer by
substring or first-match behavior:

- the exact Circle Iris host and V2 messages URL grammar;
- an exact positive attempt or deadline bound;
- top-level polling-function ownership;
- source-wide global `fetch` ownership;
- direct `body.messages[0]` ownership for `message`;
- exactly one branch for every modeled status and body state;
- a positive retry delay; and
- an exact complete return of `message` or `message.attestation`.

Ten adversarial tests now cover wrong complete returns, duplicate status/body
branches, deceptive host substrings, compound unbounded conditions, crossed
message ownership, global `fetch` shadowing, nested polling helpers, zero-delay
retry, and combined-plus-separate status handling.

## 5. Burn-hash provenance experiment

C08-R3 separately audited whether current first-party source shapes can support:

```text
burnHashProvenance=exact-source-sink-and-receipt-guard
```

### 5.1 Current Ethereum-to-Arc direct-mint quickstart

Current Circle documentation uses a same-file flow with:

1. `burnUSDC()` calling a viem client transaction whose encoded function is
   `depositForBurn`;
2. the returned `burnTx` passed from `main()` into
   `retrieveAttestation(burnTx)`;
3. the hash used in the V2 messages query.

This proves a useful same-file hash relation. It does not meet the R2 eligibility
contract because the current direct-mint `burnUSDC()` example returns `burnTx`
without a source-level `waitForTransactionReceipt({ hash: burnTx })` success
check before polling.

The same quickstart's polling helper also uses:

- imports from `viem`, `viem/accounts`, and `viem/chains`;
- top-level client and address configuration;
- a helper function called from `main`;
- `fetch(url, { method: "GET" })` rather than the first-family one-argument call;
- an unbounded `while (true)` with `try`/`catch`;
- generic non-OK retry behavior;
- no dedicated `429` branch;
- complete-only body handling rather than the first-family body model.

The source is therefore a meaningful first-party shape but is outside the
bounded candidate family.

Source:
`https://developers.circle.com/cctp/quickstarts/transfer-usdc-ethereum-to-arc`

### 5.2 Current Arc/Stellar quickstart

Current Circle Arc/Stellar documentation includes a burn transaction followed by
`waitForTransactionReceipt({ hash: burnTx })`, then returns the hash for
attestation retrieval.

That is stronger source-level evidence, but the complete integration still uses
imported viem clients, imported or configured addresses, helper functions, chain
constants, and a broader polling shape. Supporting it would require a separate
one-hop viem burn and helper-provenance family, not a small extension to the R2
control-flow grammar.

Source:
`https://developers.circle.com/cctp/quickstarts/transfer-usdc-stellar-arc`

### 5.3 Circle maintained sample application

The maintained sample application orchestrates approve, burn, attest, and mint
in one React hook, but its production-like shape uses imported configuration,
computed chain/domain lookup, helper functions, and framework state.

R2 pressure fixtures deliberately classify this family as unsupported.

Source:
`https://github.com/circlefin/circle-cctp-crosschain-transfer`

## 6. Product coverage verdict

The prototype succeeds on the synthetic bounded grammar but fails the product
coverage gate.

Measured outcomes:

```text
C08-R2 control-flow cases classified: 51 / 51
Unsafe cases eligible for critical emission: 0 / 11
First-party maintained pressure shapes supported: 0 / 2
```

A Build based only on the passing synthetic corpus would create a technically
precise analyzer that remains silent on the realistic Circle shapes used to
justify the rule. That is not a useful critical default.

Expanding coverage would require at least:

- viem import provenance;
- exact client construction or binding ownership;
- one-hop burn helper resolution;
- one-hop polling helper resolution;
- encoded `depositForBurn` or `depositForBurnWithHook` sink analysis;
- receipt-result ownership and success semantics;
- source-chain/domain relation across constants or maps;
- `fetch` options and `try`/`catch` ownership;
- additional V2 body and forwarding-service models.

That work is a separate analyzer program, not a bounded replacement for the
current regex.

## 7. Why Advice-only is preferable to Retire

The current critical heuristic is not defensible, but the underlying guidance
still has educational value:

- a CCTP attestation `404` can represent an expected not-yet-observed state;
- it can also indicate a wrong transaction hash or source domain;
- retry should be delayed and bounded;
- `429`, other non-OK responses, empty messages, pending, and complete states
  should not be conflated.

Advice-only provides the lowest-risk migration path:

1. remove `bridge/ATTESTATION_404_NOT_FATAL` from the default critical path;
2. retain the rule ID temporarily as default-excluded, deprecated guidance;
3. change the catalog wording so it does not claim every `404` is retryable;
4. avoid breaking explicit user configurations immediately;
5. permit later retirement after a deprecation period if usage is negligible.

Retire is less suitable as the first disposition because it removes useful
migration guidance and creates avoidable configuration breakage without adding
safety.

## 12. Conclusion

C08-R3 proves that a narrow same-file control-flow classifier is technically
possible. It also proves that technical feasibility alone does not produce a
credible critical rule.

The required burn-hash eligibility and meaningful first-party coverage are not
available inside the bounded surface. Enlarging the surface would exceed the
intended scope and recreate the generic provenance problem C08 was designed to
avoid.

The objective recommendation is Advice-only: remove the current heuristic from
the default critical path, retain temporary deprecated guidance for migration,
and do not build a new critical analyzer from the R3 prototype.
