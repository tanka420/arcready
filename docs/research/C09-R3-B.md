## 1. Purpose

C09-R3-B evaluates one bounded contract-to-Arc deployment-association adapter.
It does not implement a production rule or authorize public findings.

R3-A already demonstrated that a private parser can classify the approved
Solidity source and bounded same-function value dependency. R3-B asks the
separate question: can ArcReady prove that the exact analyzed contract was
deployed to Arc through one reviewed repository artifact family?

## 2. Pinned adapter

The experiment uses exactly one adapter family:

```text
Foundry forge script broadcast run-latest.json
```

Pinned research version:

```text
Foundry v1.7.1
```

The retained R2 artifact contract is:

```text
broadcast/<Script>.s.sol/<chainId>/run-latest.json
```

The adapter accepts only:

- a normalized repository-relative path with no empty, dot, parent, absolute, or
  backslash segments;
- a broadcast artifact under the same bounded project root as the Solidity
  `src/` directory;
- an integer chain ID in both the path and the JSON `chain` field;
- exact equality between path and JSON chain IDs;
- a `transactions` array;
- `CREATE` records with an exact Solidity contract name and a valid 20-byte
  contract address;
- an exact Arc Testnet chain ID of `5042002`.

## 3. Explicit exclusions

The adapter does not interpret:

- hardhat-deploy artifacts;
- network directory names without an exact chain ID;
- RPC URLs as deployment proof;
- generated artifacts under `vendor/`;
- traversal-like or normalized-different paths;
- artifacts from a sibling project root;
- computed or imported chain IDs;
- fuzzy contract names as positive identity;
- non-`CREATE` transactions;
- artifacts without a valid deployed address;
- runtime RPC state or explorer data.

Hardhat cases remain negative pressure and must return `unsupported-adapter`.

## 4. Classification contract

The private prototype returns one status:

- `arc-foundry`: one exact Arc deployment address for an exact source contract;
- `non-arc`: exact deployment records exist only on non-Arc chains;
- `ambiguous`: exact records span Arc and non-Arc, or a fuzzy name can map to
  multiple source contracts;
- `conflict`: path/JSON chain identity conflicts or duplicate Arc artifacts
  disagree on deployed address;
- `unknown`: bounded evidence is absent or incomplete;
- `unsupported-adapter`: the project case belongs to another artifact family.

None of these statuses is a public FindingV2 eligibility decision.

## 6. Fail-closed properties

The prototype deliberately declines association when:

- the source and broadcast artifact do not share the same project root;
- the exact contract definition is absent;
- the artifact is absent;
- contract identity is only similar rather than exact;
- the deployed address is absent or malformed;
- the artifact path is outside the approved root;
- JSON is malformed or has an unsupported shape;
- chain evidence is missing, computed, or contradictory.

This boundary prefers false negatives over lending Arc ownership from unrelated
repository evidence.

## 7. R3-A and R3-B composition

R3-A and R3-B remain separate private experiments.

A later C09-D decision may consider a Build disposition only if it can define a
bounded composition that requires both:

1. an R3-A source/value candidate for one exact Solidity contract; and
2. an R3-B `arc-foundry` association for that same exact contract and project
   root.

The current prototype does not combine the records and does not emit findings.

## 8. Preliminary decision pressure

If the 16-case contract passes, R3-B demonstrates that a narrow Foundry adapter
is technically feasible for the retained artifact family.

It does not establish broad ecosystem coverage. Projects using Hardhat,
custom deployment scripts, generated manifests, explorer-only deployment data,
or runtime-only configuration remain unsupported.

C09-D must weigh this narrow coverage against:

- the production cost of a Solidity parser dependency;
- the production cost and maintenance of the Foundry adapter;
- compatibility behavior for the two existing public rule IDs;
- duplicate prevention across wallet and bridge presets;
- whether the supported deployment surface is sufficient for a default critical
  rule, warning-only rule, Advice-only migration, or Retire outcome.

## 11. Exit criteria

C09-R3-B is complete only when:

- all 16 project cases match the reviewed adapter expectations;
- non-Foundry cases remain unsupported;
- exact project-root and contract identity remain mandatory;
- no public finding is emitted;
- no production dependency or behavior changes;
- full repository verification passes;
- independent review reports `APPROVE` with zero blocker, major, and minor
  findings.

The next phase after R3-B is C09-D. Production implementation remains blocked.
