## 2. Research architecture

The prototype uses:

- exact test-only `@solidity-parser/parser@0.20.2` installation in a temporary CI
  directory;
- strict parsing with `tolerant: false`;
- source locations and ranges;
- AST ownership for source, contract, and function identity;
- a length-preserving lexical mask before any bounded text classification;
- same-function source, local-binding, and supported-sink classification;
- private research records only.

The repository package manifest and lockfile remain unchanged.

The prototype is not imported by production runtime code, public rule exports,
presets, schemas, reporters, CLI code, scoring, catalog code, or FindingV2.

## 3. Why AST ownership was not sufficient alone

The initial prototype used the parser AST to establish source, contract, and
function ownership, then used bounded regular expressions inside the selected
function range.

That design passed the 36-case corpus after ownership hardening but initially
passed only 2 of 10 lexical adversarial cases. Raw function text allowed comments
and string literals to imitate:

- collection selection;
- loops;
- local declarations;
- reassignment;
- multi-hop bindings;
- reportable sinks.

The final prototype therefore masks comments and string contents before all
binding and sink classification. The mask preserves newlines and UTF-16 code-unit
length so parser ranges and masked source offsets remain aligned, including
Unicode surrogate pairs.

This masking step is required for any later production proposal. Using AST
ownership with unmasked function text is not an acceptable implementation base.

## 4. Supported source families

The reviewed prototype recognizes these source classes:

- direct `block.prevrandao`;
- direct cast of `block.prevrandao`;
- one same-function single-assignment local binding;
- exact inline assembly `prevrandao()` extraction;
- `block.difficulty` only when the caller supplies explicit post-Paris EVM-target
  evidence.

The prototype intentionally excludes:

- arbitrary bare `PREVRANDAO` identifiers;
- all blanket `mixHash` matching;
- inline assembly `difficulty()`;
- nested assembly functions;
- malformed Solidity;
- unsupported future syntax;
- unproven `block.difficulty` aliases.

## 5. Supported sink families

The reviewed prototype classifies these bounded behavior sinks:

- direct collection modulo and index selection;
- one approved local binding followed by collection selection;
- direct authorization or eligibility comparisons;
- direct ordering-key use;
- exact safe observation through event emission;
- exact diagnostic return;
- exact compatibility checks that compare PREVRANDAO to zero;
- hash-only or unused reads as non-reportable.

An exact compatibility return such as:

```solidity
return block.prevrandao == 0;
```

is safe observation, not authorization dependency.

A nonzero comparison that uses the value in an eligibility decision remains an
authorization candidate.

## 6. Fail-closed boundaries

The prototype blocks or marks unsupported:

- reassignment or mutation;
- multi-hop aliases;
- branch joins;
- cross-function flow;
- cross-contract flow;
- ambiguous multiple-contract ownership;
- loops;
- indirect collection-length aliases;
- nested or unsupported assembly;
- malformed input;
- future unsupported syntax;
- unsupported source families;
- missing explicit post-Paris evidence for `block.difficulty`.

These boundaries prefer false negatives over unsupported critical evidence.

## 7. Adversarial coverage

The 22 additional adversarial cases cover:

- comments containing fake reportable sinks;
- strings containing fake selection, loop, declaration, mutation, and alias
  syntax;
- escaped quotes;
- Unicode strings and comments;
- comment-split `block.prevrandao` tokens;
- fake reassignment and multi-hop text;
- event-only observation;
- exact zero compatibility return;
- exact zero compatibility `require`;
- real nonzero authorization comparison;
- comment markers embedded in strings;
- quote and Unicode content inside comments.

All 22 cases pass on the final prototype.

## 8. Parser and dependency conclusion

`@solidity-parser/parser@0.20.2` is adequate for the reviewed R3-A grammar when:

- the version is exact;
- parser errors fail closed;
- unknown or unsupported syntax is blocked;
- AST ownership is combined with length-preserving lexical masking;
- supported binding and sink grammar remains narrow;
- compiler Standard JSON AST fixtures remain a comparison oracle for selected
  cases.

This result does not approve the parser as a production dependency.

A later C09-D Build decision must still review:

- production package and supply-chain cost;
- exact dependency placement;
- parser-version upgrade policy;
- maintained syntax-version coverage;
- runtime performance and caching;
- duplicate execution across temporary wallet and bridge compatibility shells.

## 13. Conclusion

Bounded source, contract, function, one-binding local flow, and direct sink proof
is technically feasible for the reviewed Solidity grammar.

The important implementation lesson is that parser ownership alone is
insufficient when bounded text classification is used inside source ranges.
Length-preserving comment and string masking is mandatory.

R3-A is complete. C09 remains blocked on the separate Foundry-only R3-B deployment
association experiment and the later C09-D implementation decision.
