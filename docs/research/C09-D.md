# C09-D — PREVRANDAO Replacement Decision

Status: Decision selected; implementation pending

Risk: R2

Base branch: `main`

Base SHA: `16e3d00a26784655d5049fbffab6618e34e98297`

Decision branch: `docs/c09-d-bounded-build-decision`

Last reviewed: 2026-08-06

## 1. Decision

C09 selects **Build: one private bounded analyzer with two temporary public
compatibility shells**.

Production implementation remains blocked until the accompanying C09A plan is
independently reviewed and merged.

The Build disposition is justified because the research established both
required feasibility layers:

- C09-R3-A proved bounded, fail-closed Solidity source and same-function value
  dependency for the approved grammar;
- C09-R3-B proved bounded exact contract-to-Arc deployment association for one
  reviewed Foundry `forge script` broadcast artifact family.

The current wallet and bridge keyword detectors must not remain in production
unchanged. They are replaced, not hardened.

## 2. Evidence

### Premise

Arc documentation establishes that `PREVRANDAO` returns zero on Arc and cannot
supply randomness. No reviewed source establishes blanket `mixHash` equivalence.

### R3-A result

The private parser experiment matched:

```text
36 / 36 canonical source cases
21 / 21 independent adversarial cases
```

It proved the feasibility of:

- exact `block.prevrandao`;
- one approved direct cast;
- one same-function single-assignment local binding;
- exact inline assembly `prevrandao()` extraction;
- separately gated post-Paris `block.difficulty`;
- bounded selection, authorization, and ordering sinks;
- fail-closed behavior for mutation, aliases, joins, malformed syntax,
  unsupported Yul, cross-function flow, and cross-contract flow.

### R3-B result

The private Foundry adapter matched:

```text
16 / 16 canonical project cases
9 / 9 independent adversarial cases
```

It proved the feasibility of exact association through:

```text
broadcast/<Script>.s.sol/<chainId>/run-latest.json
```

with exact project root, concrete contract identity, path/JSON chain agreement,
`CREATE` transaction, valid address, and Arc Testnet chain ID `5042002`.

The adapter deliberately does not cover Hardhat, custom scripts, generated
manifests, explorer-only evidence, or runtime-only deployment evidence.

## 3. Why Build instead of Advice-only or Retire

A reportable record under the combined contract is not a keyword guess. It proves
all of the following:

1. a supported PREVRANDAO source;
2. one bounded same-function dependency;
3. one supported behavioral sink;
4. one exact concrete Solidity contract;
5. one exact Foundry deployment artifact for that contract;
6. exact Arc Testnet chain identity.

On Arc, the proven source evaluates to zero. A supported selection,
authorization, or ordering decision that relies on that value is therefore an
actual compatibility defect, not merely advice.

Advice-only would understate the defect after exact ownership and value-flow are
proven. Retire would discard a demonstrated bounded capability.

## 4. Why not one new public rule

ArcReady has only three runtime presets and finding categories:

```text
wallet
bridge
app-kit
```

Adding a `solidity` preset or category would widen config schemas, project
detection, reporters, CLI contracts, fixtures, and public compatibility surface.
C09 does not authorize that expansion.

A single new public ID under either `wallet` or `bridge` would misrepresent at
least part of the supported sink surface and create a larger migration than the
current product needs.

The lowest-risk migration is therefore:

- one shared private analyzer and private evidence model;
- temporary compatibility shells for the two existing public IDs;
- no new public preset, category, or ID;
- a later evidence-based consolidation or retirement review.

## 5. Public compatibility shells

The retained public IDs are:

```text
wallet/PREVRANDAO_NOT_SUPPORTED
bridge/NO_PREVRANDAO_RELAY_SELECTION
```

They remain public exports and default-scheduled rules during the first bounded
implementation.

Neither shell may contain its current keyword detector. Both shells must consume
records from one shared analyzer invocation.

### Bridge shell ownership

The bridge shell may own only records whose supported sink and exact identifiers
establish relay, relayer, validator, sequencer, or committee selection behavior.

### Wallet compatibility shell ownership

The wallet shell temporarily owns the remaining supported non-bridge selection,
authorization, and ordering records.

The `wallet` namespace is retained for compatibility, not because every supported
Solidity contract is a wallet implementation. Documentation and catalog copy must
state this limitation.

### Duplicate prevention

Each private analyzer record must receive exactly one shell owner before public
conversion.

When wallet and bridge presets are both selected:

- the source project is parsed once per scan;
- the Foundry association is evaluated once per scan;
- one private record is routed to exactly one shell;
- no duplicate Finding is emitted;
- deterministic file, offset, record, rule, and finding order is preserved.

A private record emits only when its exact owner shell rule is selected. The
other shell never borrows the record. Wallet-only, bridge-only, both-presets,
and owner-shell-not-selected behavior must be pinned explicitly. Both presets
still produce exactly one finding for one eligible record; ambiguous shell
ownership remains silent.

## 6. Production dependency decision

C09 authorizes an exact production dependency review for:

```text
@solidity-parser/parser@0.20.2
```

Authorization is conditional, not automatic. C09A-E1 must verify before merge:

- exact package version and integrity in the lockfile;
- MIT license compatibility;
- package contents and installed size;
- zero runtime transitive dependencies as expected;
- Node 22 compatibility;
- ESM/CommonJS loading behavior under ArcReady's tsup build;
- lazy loading so non-Solidity scans do not pay parser startup cost;
- package smoke behavior from the packed ArcReady artifact.

`solc`, `solc-js`, Tree-sitter, and Foundry binaries are not authorized production
dependencies.

The Foundry adapter reads retained JSON artifacts only; it does not execute
`forge`.

Foundry v1.7.1 is the reviewed research and schema baseline. A retained broadcast
artifact does not prove which Foundry version produced it. Production validates
the exact supported structure and must not claim producer-version provenance.

## 7. Supported production contract

The first production analyzer is bounded to the R3-reviewed families.

### Sources

- exact `block.prevrandao`;
- one approved direct cast;
- one same-function single-assignment local binding;
- exact inline assembly `prevrandao()` assignment;
- `block.difficulty` only with separately proven post-Paris EVM target evidence.

### Sinks

- approved direct collection index or modulo selection;
- approved relay, validator, sequencer, committee, winner, recipient, allocation,
  authorization, eligibility, or ordering behavior;
- exact sink ownership in the same function and contract.

### Deployment ownership

- normalized same-project `src/` and Foundry `broadcast/` roots;
- exact concrete contract definition;
- exact contract name in a `CREATE` record;
- valid 20-byte deployed address;
- exact path/JSON chain agreement;
- Arc Testnet chain ID `5042002`.

### Fail-closed exclusions

- `mixHash` and arbitrary bare PREVRANDAO identifiers;
- comments, strings, documentation, and tests as evidence;
- mutation, reassignment, multi-hop aliases, branch joins, loops, callbacks,
  modifiers, cross-function and cross-contract flow;
- imported or inherited helper flow;
- unsupported Yul;
- malformed or unsupported Solidity;
- Hardhat and custom deployment adapters;
- fuzzy or duplicate contract ownership;
- missing, invalid, conflicting, sibling-project, vendor, or traversal-like
  deployment evidence.

## 8. Severity and catalog policy

For a record that satisfies the complete source, sink, and Arc ownership
contract:

```text
default severity: critical
impact: required-change
default confidence: medium
recommended default enabled: true
recommended CI failure eligible: false
```

The rules remain non-canonical FindingV2 rules in C09A. Canonical promotion
requires a separate review after production evidence and adoption data.

The catalog must no longer describe either rule as a low-confidence keyword
heuristic after implementation. It must accurately describe the bounded parser,
Foundry-only ownership adapter, compatibility-shell routing, and unsupported
surfaces.

## 9. Inventory and compatibility target

C09A targets no inventory-count change:

```text
19 known / 16 default / 7 wallet / 4 canonical
```

Both public IDs remain during one compatibility period. A later review must
choose one of:

- consolidate into a new or surviving ID under a separately approved public
  architecture;
- default-exclude or downgrade one shell;
- retire one or both shells when usage and migration evidence justify it.

C09A must not silently change config schemas, reporters, scoring contracts,
`failOn`, CLI behavior, or FindingV2.

## 10. Implementation phases

Implementation is delegated to `docs/exec-plans/active/C09A.md`.

Required phases:

1. C09A-E1 — dependency, parser, and private source records;
2. C09A-E2 — bounded value-flow and sink proof;
3. C09A-E3 — Foundry association and record composition;
4. C09A-E4 — compatibility shells, policy, fixtures, and reports;
5. C09A-E5 — independent closeout.

Every semantic phase requires independent blocker, major, and minor review counts
and full repository verification.

## 11. Non-goals

C09 does not authorize:

- a general Solidity parser, CFG, SSA, taint, symbolic-execution, or vulnerability
  platform;
- runtime RPC or explorer queries;
- execution of Foundry or Solidity compiler binaries;
- Hardhat, custom script, or additional deployment adapters;
- arbitrary imports, inheritance, libraries, Yul, or cross-file value flow;
- randomness-quality analysis outside the Arc zero-value premise;
- a new runtime preset, public category, generic plugin system, or arbitrary rule
  registry;
- canonical FindingV2 promotion;
- C10 implementation.

## 12. Exit criteria

C09-D is complete only when:

- the Build disposition is independently reviewed;
- the shared analyzer and compatibility-shell architecture is explicit;
- dependency conditions are explicit;
- source, sink, ownership, and fail-closed contracts are explicit;
- severity, confidence, inventory, and canonical status are explicit;
- duplicate prevention and deterministic routing are explicit;
- the implementation plan is approved;
- independent review reports `APPROVE` with zero blocker, major, and minor
  findings.

Production implementation remains blocked until this decision and C09A are
merged.
