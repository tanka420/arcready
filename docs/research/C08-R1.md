## 1. Decision

C08-R1 confirms that the product problem is real but that the current critical
regex is not a defensible implementation contract.

The next step is **C08-R2 source-shape corpus research**, not implementation.
C08-R2 should start with one bounded candidate family only:

- CCTP V2;
- direct global `fetch`;
- exact Circle Iris sandbox or production host;
- exact `GET /v2/messages/{sourceDomainId}` shape;
- direct `transactionHash` query parameter;
- one same-file polling loop;
- direct status and response-body checks;
- explicit retry delay;
- separate `429` handling.

CCTP V1 and Axios remain separate candidate families. They must not be folded
into the first feasibility surface merely to preserve broad coverage.

No Build, Advice-only, or Retire disposition is selected by R1.

## 3. API and state model

### 3.1 V2 messages endpoint

The current V2 request shape is:

```text
GET https://iris-api[-sandbox].circle.com/v2/messages/{sourceDomainId}
  ?transactionHash={hash}
```

At least one of `transactionHash` or `nonce` is required. Arc-oriented Circle
quickstarts use `transactionHash` from the source burn result.

The following states must remain distinct:

| Evidence | Meaning supported by Circle | Static-analysis consequence |
| --- | --- | --- |
| HTTP `404` | Iris has not observed or processed the burn, or the transaction hash/domain is incorrect. | `404` alone does not prove either safe retry or terminal failure. |
| HTTP `200` with empty `messages` | The transaction was found but has not been processed. | Polling may continue, but the branch must belong to the proven V2 response. |
| Message `status: "pending"` | Required confirmations have not completed. | Polling may continue. |
| Message `status: "complete"` with attestation | Attestation is ready. | The flow may leave polling and proceed to mint. |
| HTTP `429` | Rate limit was exceeded. | Must not be modeled as ordinary `404`; it requires a separate retry/backoff policy. |
| HTTP `400` or other unexpected non-OK | Request or service failure outside the expected pending state. | Must not be silently conflated with `404`. |

Circle's troubleshooting guidance says a persistent `404` should trigger checks
that the burn succeeded and that the transaction hash and source domain are
correct. Therefore, indefinite retry is not universally correct.

### 3.2 V1 messages endpoint

The V1 messages request shape is:

```text
GET https://iris-api[-sandbox].circle.com/v1/messages/{sourceDomainId}/{transactionHash}
```

V1 places the transaction hash in the path rather than a query parameter. A V2
analyzer must not accept V1 syntax by proximity or substring similarity.

### 3.3 V1 attestation endpoint

The V1 attestation request shape is:

```text
GET https://iris-api[-sandbox].circle.com/v1/attestations/{messageHash}
```

A successful response distinguishes:

- `status: "pending_confirmations"` with a null attestation;
- `status: "complete"` with a signed attestation.

This endpoint is message-hash based, not transaction-hash based. It requires a
separate analyzer family if C08 later evaluates it.

### 3.4 Hosts and rate limiting

Circle documents these Iris hosts:

- testnet: `https://iris-api-sandbox.circle.com`;
- mainnet: `https://iris-api.circle.com`.

Circle's V1 API documentation states a rate limit of 35 requests per second and
a temporary block returning `429` after the limit is exceeded. R2 must keep
`429` separate from ordinary pending-state logic even when a sample uses one
generic delay for all non-OK responses.

## 4. Official Arc quickstart shape

Current Circle Arc quickstarts provide a useful source-shape seed, not an
approved analyzer contract. The common TypeScript shape is:

1. receive `transactionHash` from a source burn function;
2. build an exact V2 Iris URL with a source-domain constant;
3. enter `while (true)`;
4. call direct global `fetch`;
5. on non-OK response, avoid logging `404`, delay five seconds, and `continue`;
6. parse JSON after an OK response;
7. continue for empty or pending state;
8. return when a complete attestation is available.

Important limitations of the sample shape:

- the loop is unbounded;
- no cancellation or external abort contract is proven;
- `429` is not necessarily given a distinct backoff branch;
- unexpected non-404 failures may be logged and then retried;
- correctness of the transaction hash and source domain is supplied by the
  surrounding quickstart, not established by HTTP status alone.

R2 should use this source as a positive syntax seed while adding adversarial
cases for timeout, cancellation, invalid parameters, and status conflation.

## 5. Current ArcReady rule audit

Current implementation:

```text
packages/arcready/rules/bridge/attestation-404-not-fatal.ts
```

Current public rule:

```text
bridge/ATTESTATION_404_NOT_FATAL
```

Current behavior:

- severity is `critical`;
- the rule scans bridge files as text;
- `isCctpRelated` is used as a broad file-level gate;
- obvious comment/documentation lines and negative guidance are filtered;
- a finding is emitted when `404` occurs near `throw`, `fatal`, `failed`, or
  `error` within fixed character windows;
- the finding is suppressed when `retry`, `pending`, `not ready`, `processing`,
  or `continue` occurs near `404`;
- the finding location is file-level;
- no endpoint, request, response, loop, parameter, or body ownership is proven.

The current rule catalog states that `404` is a retryable pending state. R1 finds
that wording incomplete because Circle also lists incorrect transaction hash or
domain ID as causes of `404`.

The historical quality audit already rated this rule as needing improvement and
identified structured error handling and retry branches as missing precision.
C08 now replaces that incremental-hardening premise with an explicit
Build/Advice-only/Retire decision.

## 6. False-positive classes in the current regex

The existing heuristic can report a critical finding when:

1. an unrelated `404` and an attestation error branch occur in the same
   CCTP-related file;
2. a terminal branch intentionally stops after validating a persistent wrong
   domain or transaction hash;
3. `404` appears in logging, metrics, test data, or a typed error definition
   while `throw` appears in another nearby branch;
4. one response's status is paired with another request's error action;
5. V1 and V2 syntax or body states coexist in one migration file;
6. a catch branch correctly escalates after timeout or cancellation but the
   source still contains `404` nearby;
7. an unexpected non-OK branch is terminal while only the expected `404` branch
   is retryable;
8. character proximity crosses function, block, request, or response ownership.

Comment and guidance filtering reduces some textual noise but cannot establish
control-flow ownership.

## 7. False-negative classes in the current regex

The existing heuristic can remain silent when:

1. a fatal action uses `return`, `break`, rejected state, process exit, callback,
   or custom failure transition instead of the matched fatal words;
2. Axios exposes `error.response.status` and the matched words fall outside the
   fixed character window;
3. status is destructured or assigned to a local binding;
4. a wrapper converts `404` into a custom error before the polling function;
5. a `404` branch terminates by setting state rather than throwing;
6. `retry` or `continue` appears nearby but belongs to another status branch;
7. an infinite tight loop is suppressed merely because it contains a retry word,
   despite having no delay, timeout, or cancellation;
8. `404` and `429` are retried identically without rate-limit backoff;
9. V2 empty `messages` or `pending` is incorrectly treated as complete;
10. a complete attestation is ignored and polling continues indefinitely.

The rule name and current message cover only one of these control-flow errors.

## 8. R2 corpus contract

C08-R2 should build complete-source fixtures before designing an analyzer.

### 8.1 First candidate family

The first candidate family should require all of these properties:

- plain `.js` or `.ts` file;
- exact direct global `fetch` call;
- exact Iris sandbox or production host;
- exact V2 messages path;
- direct `transactionHash` query parameter;
- one direct source-domain literal or one immutable same-file constant;
- one direct URL literal or one immutable same-file URL binding;
- one direct `while` or `for` polling loop;
- one response binding owned by that fetch call;
- direct non-OK status handling;
- direct JSON body parsing owned by that response;
- explicit empty, pending, and complete body branches;
- explicit delay before retry;
- separate `429` behavior;
- unsupported forms fail closed.

### 8.2 Mandatory positive fixtures

R2 should include at least:

- official-style `404` delay and continue;
- empty `messages` delay and continue;
- `pending` delay and continue;
- `complete` return with attestation;
- unexpected non-OK terminal handling;
- separate `429` backoff;
- bounded timeout exit;
- cancellation or abort exit.

### 8.3 Mandatory negative and unsupported fixtures

R2 should include at least:

- terminal `404` without parameter validation;
- infinite immediate retry without delay;
- `404` and `429` conflation;
- wrong or unknown source domain;
- wrong or unknown transaction-hash provenance;
- V1 endpoint in a V2 candidate;
- Axios in the fetch candidate family;
- imported URL, domain, hash, or HTTP wrapper;
- multiple fetch calls with crossed response ownership;
- nested loops, helper polling wrappers, callbacks, recursion, mutation, and
  branch-dependent aliases;
- comments, documentation, tests, strings, and malformed source.

### 8.4 Evidence required per fixture

Each fixture must declare independently:

- endpoint family;
- environment host;
- source-domain ownership;
- transaction-hash ownership;
- HTTP-client identity;
- loop ownership;
- response ownership;
- status branch;
- body state;
- retry delay;
- timeout/cancellation behavior;
- terminal action;
- expected disposition;
- missing proof for unsupported cases.

Finding outcome must not be used to derive the evidence declaration.

## 9. R3 feasibility gate preview

A later Build disposition requires a private analyzer that can prove request,
response, loop, and action ownership without generic HTTP, CFG, SSA, taint, or
cross-file data flow.

R3 must stop and recommend Advice-only or Retire when any required positive case
needs:

- general alias graphs;
- arbitrary URL construction;
- interprocedural control flow;
- cross-file symbol resolution;
- generic Axios/fetch normalization;
- mutation-aware data flow;
- runtime validation of domain or transaction-hash correctness.

The existence of an official quickstart shape is not enough by itself to justify
a critical rule. The supported syntax must also represent meaningful real-world
usage and fail closed outside its exact contract.
