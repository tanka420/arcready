## 1. Decision

C08 selects exactly:

```text
Advice-only
```

`bridge/ATTESTATION_404_NOT_FATAL` must leave the default critical path. The
existing rule ID may remain temporarily as default-excluded, deprecated guidance
for explicit compatibility opt-in.

C08 rejects Build and does not yet select Retire.

This decision does not itself change runtime behavior. Production migration is a
separate C08A implementation milestone.

## 2. Evidence summary

C08-R1 established that an attestation HTTP `404` is conditional:

- it can mean that Circle Iris has not observed or processed the burn;
- it can also mean that the transaction hash or source domain is incorrect.

C08-R2 materialized a 51-case source corpus:

```text
total=51
safe-candidate=9
unsafe-candidate=11
unsupported=31
```

C08-R3 proved that a narrow same-file control-flow classifier is technically
possible, including exact endpoint, polling-loop, response, status, body, delay,
bound, and terminal-action ownership.

The final R3 contract passed:

```text
C08-R3 tests: 63
Repository tests: 2292
Test files: 34
```

However:

```text
Unsafe cases eligible for critical emission: 0 / 11
Maintained first-party pressure shapes supported: 0 / 2
```

The bounded parser cannot establish a meaningful burn-hash source and receipt
success guard for current first-party integration shapes without imported
configuration, helper-call provenance, richer URL construction, or wider
inter-function analysis.

## 3. Why Build is rejected

A Build disposition requires both technical precision and useful product
coverage.

The R3 prototype passes the synthetic bounded grammar, but a critical rule built
from that grammar would remain silent on realistic Circle quickstart and
maintained-application shapes.

Expanding the surface would require a separate analyzer program involving at
least:

- viem import and client provenance;
- exact CCTP burn sink ownership;
- receipt-result and success-guard semantics;
- one-hop burn and polling helper resolution;
- source-chain/domain relations across constants or maps;
- `fetch` options and `try`/`catch` ownership;
- broader V2 response-body handling.

That work exceeds the bounded replacement problem and would recreate a generic
provenance effort without sufficient product evidence.

The current proximity regex is not an acceptable fallback. Keeping it critical
would preserve known false-positive and false-negative classes after research
has shown that its premise is incomplete.

## 4. Why Retire is deferred

The underlying guidance remains useful:

- verify the burn, transaction hash, and source domain before treating a `404` as
  ordinary pending state;
- use delayed and bounded polling;
- keep `404`, `429`, unexpected non-OK responses, empty messages, pending, and
  complete states distinct;
- do not retry indefinitely merely because an endpoint returned `404`.

Immediate retirement would remove that migration guidance and may break users
who explicitly reference the public rule ID.

Advice-only is therefore the lowest-risk first disposition. A later Retire review
may remove the rule after one compatibility period if explicit usage is
negligible and migration documentation is sufficient.

## 5. Current architecture constraints

The current rule is:

- exported publicly;
- included in `bridgeRules`, which is the all-known public bridge inventory;
- selected by the default bridge preset because `defaultPresetRegistry` currently
  consumes that same array;
- assigned `defaultSeverity: "critical"`;
- described as detecting fatal `404` handling;
- backed by a proximity regex that cannot prove endpoint or control-flow
  ownership.

The current configuration architecture has another important constraint:

- `config.rules[id]` only overrides severity for rules already selected by a
  preset;
- removing a rule from `bridgeRules` would therefore make the existing ID
  impossible to opt into through normal configuration;
- unknown configuration keys are accepted but do not select a rule.

C08A must not claim compatibility merely because the symbol remains exported.
It needs an explicit known-rule selection path for default-excluded guidance.

## 6. Selected migration contract

C08A must implement all of the following as one reviewed migration.

### 6.1 Known/default inventory split

- keep `bridgeRules` unchanged as the all-known public bridge array, including
  `attestation404NotFatalRule`;
- introduce one private `bridgeDefaultPresetRules` subset used only by
  `defaultPresetRegistry`;
- exclude the attestation rule only from that private default subset;
- retain the public rule export and known inventory entry during the
  compatibility period;
- reduce default inventory from 17 to 16 while keeping 19 known, 7 wallet, and 4
  canonical rules;
- preserve default ordering for all remaining rules.

### 6.2 Explicit opt-in

Keep the default-excluded registry private to the module's top-level default
selection helper. Do not attach it to every `PresetRegistry` instance.

Selection semantics must be:

1. obtain ordinary rules from `defaultPresetRegistry` exactly as today;
2. inspect only IDs in the private built-in default-excluded registry;
3. add a known excluded rule only when `config.rules[id]` is explicitly present
   with `info`, `warning`, or `critical`;
4. do not add it for missing or `off` configuration;
5. deduplicate by rule ID;
6. preserve deterministic private-registry order;
7. do not turn arbitrary public exports or unknown config keys into runtime
   selectors;
8. leave `PresetRegistry` and custom `createPresetRegistry()` instance behavior
   unchanged, with no automatic built-in excluded rules.

This is a compatibility mechanism in the top-level default helper, not a general
plugin or custom-registry API.

### 6.3 Advisory policy

- change the rule's default severity to `info` for direct/custom-registry use;
- update the finding and remediation copy so it does not claim every `404` is
  retryable;
- state that users must verify burn/hash/domain provenance and separate pending,
  rate-limit, unexpected-status, and completion behavior;
- keep the detector explicitly deprecated and low-confidence;
- do not connect the R3 prototype to production execution.

An explicit config level remains authoritative for an opted-in run.

### 6.4 Catalog and documentation

Update runtime and documentation catalogs to record:

- taxonomy: advice;
- impact: recommendation;
- recommended default enabled: false;
- CI failure eligible: false;
- maturity: deprecated;
- deprecated: true;
- detector limitations and conditional `404` semantics;
- C08-R1/R2/R3/D evidence and the later Retire review.

### 6.5 Compatibility tests

At minimum, prove:

- `bridgeRules` still includes the public known rule ID;
- the private default bridge subset and default bridge preset exclude the rule;
- normal bridge scans no longer execute or emit it;
- explicit `info`, `warning`, and `critical` configuration selects it with the
  configured severity;
- explicit `off` does not select it;
- unknown rule IDs remain non-selecting;
- custom `createPresetRegistry()` instances never receive built-in excluded
  rules;
- public exports remain available;
- duplicate preset/config selection cannot execute twice;
- instrumentation ordering remains deterministic;
- legacy reports, scoring, `failOn`, CLI exits, FindingV2, schemas, and reporters
  do not otherwise change;
- known/default/canonical inventory assertions are updated intentionally.

## 7. Rejected shortcuts

C08A must not:

- keep the rule in the default preset and merely reduce severity;
- remove it from public `bridgeRules` instead of splitting known and default
  arrays;
- remove it from the preset without providing real explicit opt-in;
- use catalog metadata as runtime selection policy;
- select every configured or exported rule generically;
- add the R3 prototype to production;
- preserve the current unconditional retry wording;
- silently change unknown config-key behavior;
- combine C09 or C10 work with this migration.

## 8. Risk assessment

The migration is bounded but affects rule scheduling.

Primary risks:

- accidentally scheduling unknown or deprecated rules;
- changing order or deduplication of existing presets;
- allowing an `off` entry to select a rule;
- retaining default execution through another registry;
- breaking direct imports or explicit user configuration;
- changing default finding counts, fixture expectations, and CLI exits beyond the
  intended removal of one critical heuristic.

These risks justify an R2 implementation milestone with independent review at
each semantic phase.

## 9. Implementation disposition

C08A is the only authorized next implementation milestone for C08.

C08A may change preset selection, the deprecated rule policy, catalog metadata,
documentation, and tests. It may not implement a new attestation analyzer.

C08 remains active until C08A is merged, default behavior is verified, and a
closeout records the final inventory and compatibility behavior.

- explicit opt-in is technically possible and narrowly scoped;

## 11. Conclusion

C08 research has answered the product question.

A narrow control-flow parser can be precise, but it does not provide enough
burn-hash provenance or first-party coverage to justify a default critical rule.
The current regex is therefore unsuitable for continued critical execution.

Advice-only preserves useful migration guidance and short-term ID compatibility
without pretending that the detector proves a compatibility failure.
