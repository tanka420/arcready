## 1. Product question

C10 asked whether ArcReady should replace its deprecated generic App Kit
capability detector with version-aware compatibility analysis for official App
Kit chain identifiers, operations, tokens, and adapters.

The product decision test requires all three of the following before a build:

1. Arc developers realistically encounter the selected incompatibility;
2. ArcReady can prove it inside a narrow, truthful, maintainable boundary;
3. the finding has a clear corrective action.

The research established an official release boundary and a feasible lexical
call shape, but it did not establish the first requirement for a new default
critical rule. C10 therefore stops at Research / Defer.

## 2. Corrected premise

The exact official evidence is:

- App Kit chain identifiers are case-sensitive and Arc Testnet is
  `Arc_Testnet`;
- `@circle-fin/app-kit` 1.3.0 added Arc Testnet Swap support;
- 1.4.0 added Unified Balance support, not Arc Testnet Swap;
- current releases retain `SwapChain.Arc_Testnet`;
- a root manifest declaration is not proof of the effective installed version.

The first architecture candidate incorrectly used 1.4.0 as the Swap support
floor. That would have reported valid 1.3.x integrations and is rejected.

The pre-1.3.0 package line also is not one uniform analyzable class. The
inspected 1.0.0 tarball does not contain the declared implementation and type
entrypoints, while later pre-floor packages have different published shapes.
No implementation may collapse these releases into one unsupported range
without release-by-release evidence.

## 3. Decision

Decision: Research / Defer.

Do not implement the proposed version-operation rule. In particular, C10 does
not authorize:

- `app-kit/APPKIT_OPERATION_COMPATIBLE` or any replacement public ID;
- a new default rule, critical finding, score change, or exit change;
- a compatibility table, manifest resolver, lockfile resolver, or generic
  TypeScript analysis framework;
- new production analyzer code, fixtures, catalog entries, exports, or package
  dependencies;
- repurposing or re-enabling `APPKIT_CAPABILITY_SUPPORTED`;
- broadening `APPKIT_CHAIN_IDENTIFIER_VALID` under this milestone.

This is a product evidence decision, not an assertion that pre-1.3.0 Arc Swap
usage is impossible. The proposed finding is deferred because the reviewed
evidence does not justify shipping it as a trusted compatibility gate.

## 4. Why the candidate build was rejected

### 4.1 No demonstrated user problem

The inspected official Circle sample and public JavaScript repositories use
App Kit releases at or above the corrected 1.3.0 support floor. Repository
search did not produce a real pre-floor JavaScript or no-typecheck Arc Testnet
Swap violation.

For the exact direct literal form proposed by the candidate, App Kit 1.2.1's
published TypeScript declarations already reject `Arc_Testnet` as a Swap chain.
That leaves an unproven JavaScript/no-checkJs audience rather than evidence for
a new default critical gate.

### 4.2 Declared version is not installed version

An exact root `package.json` entry can be superseded by package-manager
resolutions, overrides, workspace ownership, nested manifests, or another
dependency authority. Reporting from the declaration alone would claim an
effective runtime version ArcReady had not proved.

Silencing every such case would leave a very small surface, but it would not
repair the missing product evidence. Adding lockfile and workspace resolution
would be an R3 dependency-analysis platform without a justified first consumer.

### 4.3 Source ownership contract was incomplete

The disposable AST probe showed only that direct call and chain-slot extraction
is syntactically feasible. A production rule would additionally need:

- exact field-specific object semantics, including a consistent shorthand
  policy;
- receiver mutation, escape, deletion, `Object.assign`, and
  `Object.defineProperty` handling;
- block/function shadowing and source-order proof;
- malformed compiler-shape handling;
- a public ID naming the exact versioned Arc Swap boundary.

These gaps are solvable in isolation, but solving them before the product
premise exists would violate the repository's product-first contract.

## 5. Deliberately unchanged behavior

C10 changes no executable behavior. The following remain exactly as they were
at the base SHA:

- known/default/App Kit/canonical inventory and rule order;
- legacy scoring and exit behavior;
- FindingV2, CoverageV2, ScanResultV2, schemas, reporters, config, and presets;
- package exports, dependencies, and package contents;
- the default-excluded deprecated `APPKIT_CAPABILITY_SUPPORTED` rule;
- the existing default `APPKIT_CHAIN_IDENTIFIER_VALID` rule;
- all wallet, bridge, dApp, and Solidity analyzers.

The weak contracts already documented for the two existing App Kit rules are
not recast as safe. They remain candidates for separate evidence-backed work.

## 6. Reopen triggers

Reopen versioned App Kit compatibility only when at least one concrete trigger
exists:

- a real repository or user report shows a pre-support App Kit operation that
  the language/toolchain did not already prevent;
- repeated unsupported-version incidents establish a useful JavaScript or
  no-typecheck audience;
- a first-party release changes or documents a compatibility boundary that
  creates a current migration problem;
- reliable installed-version ownership becomes available through an already
  required consumer, without introducing a speculative resolver;
- two real consumers require the same stable version/package semantics.

A reopened milestone must rerun premise research against then-current official
packages and docs. It must independently review effective version ownership,
operation ownership, mutation/escape semantics, object shapes, severity,
default status, public naming, inventory, scoring, and exit impact before any
fixture expansion.

Hardening the existing chain-identifier rule requires separate evidence of real
invalid identifiers and a separate R2/R3 plan. It is not a substitute for the
missing version-compatibility premise.
