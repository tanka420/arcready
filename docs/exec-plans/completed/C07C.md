## Product decision

C07C built and completed a conservative viem explicit-pattern MVP.

ArcReady reports only source-proven patterns inside the declared surface.

Unsupported or ambiguous code produces no viem finding.

No finding is not a claim that unsupported code is safe.

The design prefers bounded false negatives over critical false positives.

C07C does not authorize a general TypeScript analysis platform.

## Product goal

Extend the completed ethers-only rule with bounded viem coverage.

A viem record is reportable only when one same-file submission proves:

- exact first-party import provenance;
- exact Arc Testnet ownership;
- exact built-in HTTP transport;
- an approved account route;
- an exact wallet-client `sendTransaction` sink;
- an exact own `type: "eip4844"` property;
- safe direct or one-level immutable bindings;
- no supported mutation, escape, reassignment, or evidence joining.

## Pinned source premise

Use viem `2.55.10` at commit
`fe2bce6cc4d689d18a0d95b4ae818afc661becf1`.

The source was reviewed on 2026-07-28.

The MVP relies on these source-backed facts:

- exact `type: "eip4844"` represents an EIP-4844 transaction;
- `arcTestnet` represents Arc Testnet;
- Arc Testnet has chain ID `5042002`;
- its primary RPC is `https://rpc.testnet.arc.network`;
- built-in `http()` uses the selected chain's default HTTP endpoint;
- `privateKeyToAccount(...)` creates the approved local-account route.

The scanned project may use another viem version.

Version drift remains an accepted limitation until a separate contract exists.

## Architecture

Use two private viem-specific modules:

```text
packages/arcready/rules/wallet/viem-transaction-submission-lexical.ts
packages/arcready/rules/wallet/viem-transaction-submission-analyzer.ts
```

The lexical module owns:

- exact named-import provenance;
- lexical binding identity;
- declaration order;
- direct and one-level immutable `const` resolution;
- shadowing and reassignment checks.

The analyzer module owns:

- lazy TypeScript compiler loading;
- file eligibility and deterministic statuses;
- client, chain, transport, account, request, and sink classification;
- candidate-local safety;
- deterministic ordering by `callOffset`.

Both modules remained private and unconsumed during C07C-A. C07C-B made them
reachable only through the existing rule, without adding a public analyzer
export.

Do not import, modify, or expose the existing ethers analyzer.

Do not extract a shared AST framework.

## Exact supported surface

### Imports

Allow exact named ESM imports from exact modules:

```ts
import { createWalletClient, http } from "viem";
import { arcTestnet } from "viem/chains";
import { privateKeyToAccount } from "viem/accounts";
```

A direct named import alias is allowed only when import identity is proven.

Do not support:

- namespace imports;
- default imports;
- type-only imports;
- CommonJS or dynamic imports;
- user-module re-exports;
- wrong viem subpaths;
- same-spelling local functions.

### Binding depth

Allow a direct expression or one immutable same-file `const` for:

- the client;
- the request;
- the JSON-RPC account;
- the private-key account;
- the `arcTestnet` chain value.

`http(...)` must remain direct.

Transport bindings are unsupported.

Do not support depth 2+, branching aliases, wrappers, imported values,
conditional values, callbacks, cross-function values, or cross-file values.

### Client

Allow exact `createWalletClient(...)` with one direct object literal.

The client object must prove approved chain, transport, and account evidence.

Relevant properties must be own, direct, non-computed data properties.

Do not support spreads, accessors, methods, duplicate relevant keys,
prototype-sensitive keys, or ambiguous shorthand.

### Chain

Allow only imported `arcTestnet`.

It may be direct or resolved through one immutable `const`.

Do not support:

- numeric chain ID `5042002` by itself;
- direct chain objects;
- `defineChain(...)`;
- viem `arc`;
- Ethereum mainnet;
- omitted or null chain values;
- per-call chain overrides.

### Transport

Allow only direct root-import calls:

```ts
http();
http("https://rpc.testnet.arc.network");
```

No options argument is allowed.

Do not support computed URLs, environment values, wrappers, bindings,
non-Arc URLs, `custom`, `fallback`, or `webSocket`.

### Account

Allow a lowercase JSON-RPC address literal matching:

```text
^0x[0-9a-f]{40}$
```

The address may be direct or resolved through one immutable `const`.

Also allow exact `privateKeyToAccount(<one argument>)` from `viem/accounts`.

That call may be direct or resolved through one immutable `const`.

Do not support:

- per-call account overrides;
- custom account objects;
- `toAccount(...)`;
- mnemonic or HD accounts;
- smart accounts;
- custom `signTransaction` implementations;
- imported accounts;
- account extension.

Account classification and binding identity remain separate.

Equal-looking values from different bindings must not be joined.

### Sink

Allow only a non-optional dot call with exactly one argument:

```ts
client.sendTransaction(request);
```

The direct receiver form is also allowed:

```ts
createWalletClient({ ... }).sendTransaction(request);
```

Do not support element access, optional chaining, detached actions,
destructuring, `call`, `apply`, `bind`, wrappers, or alternate actions.

### Request

Allow a direct object literal or one immutable same-file `const` object.

The only positive transaction-kind evidence is:

```ts
type: "eip4844";
```

The property must be own, direct, non-computed, and unambiguous.

Do not support numeric `3`, string `"0x3"`, identifiers, shorthand, templates,
concatenation, getters, imports, or computed values.

Duplicate non-relevant properties do not invalidate a request by themselves.

Duplicate relevant keys and structurally dangerous keys are unsupported.

## Ambiguity and safety policy

Fail closed when required evidence is ambiguous or unsupported.

The bounded safety contract includes:

- declarations must dominate the sink;
- approved imports and bindings must not be reassigned before the sink;
- protected values must not be mutated before the sink;
- protected values must not escape to unknown calls before the sink;
- static element access to protected methods must fail closed;
- depth-2 and branching aliases must be rejected, not analyzed;
- candidate-local invalidation must preserve unrelated valid candidates;
- sibling objects and calls must not lend evidence;
- mutations after the sink must not invalidate an earlier call;
- partial compiler API shapes must return `compiler-unavailable`.

Do not build a general alias graph, mutation graph, prototype engine,
`Object` or `Reflect` engine, or escape-analysis framework.

A shape that needs those facilities is outside the positive grammar.

## File statuses and private records

Preserve these private file statuses:

- `analyzed`;
- `unsupported-file`;
- `compiler-unavailable`;
- `malformed`;
- `unsupported-source` for an approved file-wide barrier only.

A private submission record retains:

- provenance;
- sink;
- structural safety;
- ownership;
- account route;
- transaction kind;
- evidence token `eip4844`;
- exact `callOffset`;
- an optional internal reason code.

C07C-A adds no public finding or reporting behavior.

## Explicitly deferred surface

Defer all of the following:

- `maxFeePerBlobGas` inference;
- `authorizationList` precedence;
- blobs, KZG, versioned hashes, and sidecars;
- per-call chain or account overrides;
- alias depth 2+ and branching aliases;
- general mutation and prototype analysis;
- imported, cross-function, and cross-file resolution;
- `.extend(...)` and custom actions;
- custom transports, formatters, serializers, and hooks;
- `writeContract`, raw, sync, deploy, and simulation paths;
- account-abstraction paths;
- direct chain objects and `defineChain(...)`;
- shared static-analysis infrastructure.

Reopen a deferred family only from concrete usage evidence or a separately
approved milestone.

Theoretical expressibility alone is not sufficient.

## Acceptance strategy

Use approximately 35–50 meaningful cases.

Positive families must cover:

- direct JSON-RPC account and request;
- one client binding;
- one request binding;
- one JSON-RPC account binding;
- direct and one-binding private-key accounts;
- approved import aliases;
- direct and one-binding `arcTestnet`;
- `http()` and the exact primary Arc RPC;
- multiple valid calls ordered by source offset.

Fail-closed families must cover:

- wrong import source, form, export, alias, and shadowing;
- reassignment before the sink;
- depth 2+, branching aliases, wrappers, and imported values;
- omitted, null, non-Arc, and per-call chain values;
- computed, configured, custom, fallback, and WebSocket transports;
- invalid, mixed-case, custom, and imported accounts;
- mutation and unknown-call escape before the sink;
- spread, duplicate relevant keys, computed keys, accessors, and prototype keys;
- all non-exact type values and deferred blob-looking fields;
- unsupported sink forms;
- sibling evidence isolation;
- malformed source and progressive compiler-shape failures;
- exact before-sink and after-sink behavior;
- unrelated valid candidates surviving local invalidation.

Each positive family receives a meaningful fail-closed mutation.

Tests assert status, state or reason, reportable count, and exact `callOffset`
when ordering matters.

## Review and correction process

Merge this planning alignment before implementation.

Start the replacement from fresh `main`.

Do not copy or cherry-pick the rejected monolith.

Implement compiler and lexical contracts before positive classification.

Run targeted tests, lint, formatting, build, diff checks, and package proof.

Obtain independent adversarial review.

Correct until no known blocker remains in the declared scope.

Repeated local defects with one root cause require a full regression family.

A missing contract class requires a specification and matrix update.

A systemic architecture defect requires scope reduction, redesign, or a split.

There is no fixed numerical cap on correction or review rounds.

## Stop conditions

Stop implementation or integration when:

- reliable support requires cross-file or module resolution;
- useful support requires a generic AST or data-flow framework;
- readable production or test budgets cannot be met;
- package, dependency, export, API, schema, or canonical boundaries would drift;
- inventory, scoring, reporter, or exit behavior would change;
- C07B ethers behavior would need to change;
- review identifies another systemic architecture defect.

A stop triggers a scope decision, not symptom patching.
