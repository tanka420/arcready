## 1. Product problem

ArcReady currently exposes `bridge/ATTESTATION_404_NOT_FATAL` as a critical
bridge rule. Its implementation treats nearby fatal-looking `404` handling as a
problem unless retry or pending language is also nearby.

That premise is incomplete. Current Circle documentation says a CCTP attestation
`404` can mean that the burn has not yet been observed or processed, but it can
also occur when the transaction hash or source domain is incorrect. A static
rule must therefore distinguish an expected pending response inside a proven
polling flow from a parameter, endpoint, or control-flow failure. It must not
claim that every `404` is safe to retry indefinitely.

C08 exists to decide whether ArcReady can make that distinction conservatively.
It does not authorize implementation.

## 2. Current implementation audit

The current detector is a text heuristic in:

```text
packages/arcready/rules/bridge/attestation-404-not-fatal.ts
```

It currently:

- gates on broad CCTP-related content;
- removes obvious comments and negative guidance;
- searches for `404` near `throw`, `fatal`, `failed`, or `error`;
- suppresses the finding when retry or pending words occur nearby.

It does not prove:

- Circle Iris host ownership;
- CCTP API version or endpoint identity;
- `fetch`, Axios, or another HTTP client's error semantics;
- that the tested status belongs to the attestation response;
- that execution is inside an actual polling loop;
- that retry includes delay, backoff, timeout, or cancellation;
- that the transaction hash came from a successful burn;
- that the source domain matches the burn chain;
- that `400`, `404`, `429`, and `5xx` branches are separated correctly;
- that a V1 response body and a V2 response body are interpreted correctly.

The heuristic is therefore not an acceptable foundation for additional critical
behavior.

## 3. Pinned first-party evidence

C08 research must use current first-party Circle and Arc sources. Initial sources
revalidated on 2026-08-05 are:

- Circle, Resolve Attestation Issues:
  `https://developers.circle.com/cctp/howtos/resolve-stuck-attestation`
- Circle, Troubleshoot CCTP Transfers:
  `https://developers.circle.com/cctp/howtos/troubleshoot-transfers`
- Circle, Get messages and attestations:
  `https://developers.circle.com/api-reference/cctp/all/get-messages-v2`
- Circle, Get an attestation:
  `https://developers.circle.com/api-reference/cctp/all/get-attestation`
- Circle, Migrate from CCTP V1 to V2:
  `https://developers.circle.com/cctp/migration-from-v1-to-v2`
- Circle Arc transfer quickstarts that call `GET /v2/messages`.

The current documented response model includes these distinct states:

| Surface      | State                                 | Meaning for research                                                                                |
| ------------ | ------------------------------------- | --------------------------------------------------------------------------------------------------- |
| V2 HTTP      | `404`                                 | Not yet observed, or incorrect transaction hash/domain; not sufficient alone to prove retry safety. |
| V2 body      | empty `messages`                      | Transaction found but not processed; polling may continue.                                          |
| V2 body      | `status: "pending"`                   | Awaiting required confirmations; polling may continue.                                              |
| V2 body      | `status: "complete"` with attestation | Attestation is ready; proceed to mint.                                                              |
| HTTP         | `429`                                 | Rate limited; requires a separate backoff policy.                                                   |
| Other non-OK | `400` or unexpected status            | Must not be silently treated as the same state as an expected pending `404`.                        |
| V1 body      | `pending_confirmations` or `complete` | Version-specific body semantics; do not infer V2 behavior from V1 syntax.                           |

C08 must preserve the distinction between transport status, response-body state,
parameter validity, and control-flow action.

## 4. Decision: Research / Replace

C08 must not harden the existing regex.

The current rule is treated as a replacement problem. Research must end in
exactly one reviewed disposition:

1. **Build.** Replace the heuristic with a private, fail-closed same-file
   analyzer and integrate only an independently approved exact surface.
2. **Advice-only.** Remove the rule from the default critical path and retain the
   existing rule ID only as default-excluded, deprecated guidance.
3. **Retire.** Remove the unsupported rule when neither a bounded analyzer nor
   useful advisory guidance is justified.

`Replace` describes the migration action for the selected disposition; it is not
itself a final disposition.

Keeping the current critical heuristic unchanged is not a successful C08
outcome.

## 5. Research questions

C08 must answer all of the following before any Build decision:

1. What exact syntax proves a Circle Iris attestation request rather than an
   unrelated `404` response?
2. Can endpoint version, environment, source domain, and transaction-hash query
   be recognized without general URL or string data flow?
3. What minimum same-file provenance is required before a `404` can be treated as
   an expected not-yet-observed state?
4. Can ArcReady prove an actual polling loop and distinguish `continue` from
   terminal `throw`, `return`, rejection, or state transition?
5. Must a safe path prove a delay, bounded timeout, cancellation path, or rate
   limit backoff?
6. How should `404`, empty `messages`, `pending`, `complete`, `429`, and other
   non-OK responses be modeled without conflation?
7. Can one bounded design support both `fetch` and Axios without shared generic
   HTTP analysis?
8. Should V1 and V2 be separate analyzer families?
9. Can transaction-hash and domain provenance be proven from a same-file burn
   result, or is that requirement too deep for ArcReady's product limits?
10. What exact evidence would justify a critical finding rather than advisory
    guidance?

## 6. Candidate bounded surface for feasibility testing

The feasibility prototype may inspect only plain `.js` and `.ts` files and must
remain private. It may test exact first-party patterns such as:

- exact Circle Iris sandbox or production host;
- exact V2 `GET /v2/messages/{sourceDomainId}` request;
- exact `transactionHash` query parameter;
- direct `fetch` first, with Axios considered only as a separate candidate;
- one direct `while` or `for` polling loop;
- one direct response-status branch;
- one direct delay before retry;
- exact V2 body checks for empty messages, `pending`, and `complete`;
- separate `429` handling;
- no imported, cross-file, computed, wrapper, alias-graph, mutation-graph, or
  general control-flow support.

This list is a research boundary, not an approved implementation contract.

## 7. Required adversarial matrix

The research corpus must include complete-source cases across these dimensions:

- V1 versus V2 endpoints;
- sandbox versus production Iris hosts;
- `fetch` versus Axios semantics;
- direct literal URL versus one immutable same-file URL binding;
- correct, incorrect, and unknown source-domain provenance;
- correct, incorrect, and unknown transaction-hash provenance;
- `404` with `continue`, delayed retry, terminal throw, return, rejection, or
  unrelated error logging;
- empty `messages`, `pending`, and `complete` body states;
- `429` backoff and accidental `429`/`404` conflation;
- `400`, `401`, `403`, and `5xx` handling;
- bounded timeout, cancellation, and infinite polling;
- nested loops, helper wrappers, callbacks, recursion, aliases, mutation, and
  imported values as unsupported cases;
- comments, examples, tests, documentation strings, and malformed source.

Every accepted case must declare the exact evidence that makes it safe to
classify. Every rejected case must name the missing or ambiguous proof.

## 8. Work phases

### C08-R1 — premise and API-state inventory

- pin current Circle endpoint and response semantics;
- separate V1 and V2 behavior;
- record all states that must not be conflated;
- audit the current rule, catalog entry, tests, and preset impact.

### C08-R2 — source-shape corpus

- collect first-party Circle Arc quickstart patterns;
- collect a small set of real public integration shapes;
- classify syntax dimensions without designing a general HTTP framework;
- build adversarial complete-source fixtures.

### C08-R3 — private feasibility prototype

- no public finding changes;
- no rule-ID, severity, preset, schema, reporter, or scoring changes;
- test whether exact endpoint, loop, status, body, and action evidence can be
  proven with bounded same-file analysis;
- delete or discard the prototype if it requires generic control-flow or data
  flow.

### C08-D — independent decision review

The review must choose exactly one disposition:

- `Build`: a bounded contract is explicit, testable, and fail-closed;
- `Advice-only`: remove the rule from the default critical path and retain it
  only as default-excluded, deprecated guidance;
- `Retire`: remove the unsupported rule entirely.

`Replace` is the migration action used to implement the selected disposition;
it is not a fourth disposition.

No implementation begins from a Research disposition alone.

## 9. Non-goals

C08 does not include:

- live Circle API calls;
- burn or mint simulation;
- cross-file or package resolution;
- general HTTP-client abstraction;
- general loop, CFG, SSA, taint, or data-flow infrastructure;
- proof that a transaction hash or domain is correct at runtime;
- automatic retry execution;
- changes to canonical FindingV2;
- SARIF, suppression, baseline, or report-format work;
- C09 or C10 implementation.

## 11. Exit criteria

C08 research is complete only when:

- current Circle V1/V2 semantics are pinned and non-conflicting;
- the current heuristic's false-positive and false-negative classes are
  documented;
- the adversarial source corpus is complete enough to test the proposed proof;
- the feasibility prototype either proves a bounded contract or demonstrates why
  it exceeds ArcReady's intended architecture;
- an independent review selects exactly one of Build, Advice-only, or Retire;
- the selected disposition is recorded in the roadmap, backlog, catalog, and
  implementation plan as applicable.

Until those criteria are met, `bridge/ATTESTATION_404_NOT_FATAL` must not be
promoted, canonicalized, or expanded.
