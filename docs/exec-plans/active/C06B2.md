## 1. Product goal

Prevent one exact write-side Arc USDC unit error: a statically safe nonzero
18-decimal `parseEther` value passed directly to the six-decimal canonical Arc
USDC ERC-20 `transfer(address,uint256)` sink.

This milestone does not claim general write, amount, transaction, or data-flow
analysis. Unsupported syntax fails closed and a missing finding is not a safety
claim.

## 2. Architecture-reset decision

Five review rounds repeatedly found that the prior broad source-chain and matrix
representations mixed different kinds of evidence, hid incomplete program
shapes, and overclaimed live execution. The correction is therefore a Class C
architecture reset:

- reduce the MVP to direct `parseEther` only;
- separate symbol provenance from non-positional semantic source relations;
- replace acceptance rows with deterministic complete-source fixtures;
- record analyzer stage and expression-evaluation class independently for every
  fixture;
- describe only source-level submit capability, never live submission success;
- defer conversions, multiple candidates, mutation, and wider parsers.

This Approved plan does not authorize implementation. Implementation still
requires explicit authorization.

## 3. Premise and pinned sources

Arc and Circle documentation was accessed on 2026-07-30 and revalidated on
2026-07-31:

- Arc's stablecoin-native model states native accounting uses 18 decimals and
  the optional ERC-20 interface uses six decimals.
- Arc's contract-address reference and Circle's USDC address table identify Arc
  Testnet USDC as `0x3600000000000000000000000000000000000000`.
- Arc's gas example conflicts with the native raw-value premise. Native writes
  therefore remain Research / blocked.
- Current Arc documentation uses `https://rpc.testnet.arc.io`; existing
  analyzers retain the previously documented `.network` literal. RPC migration
  remains a separate R2 maintenance task, and `.network` is not declared
  retired.

## 5. Exact retained MVP

Only this semantic family is retained:

```ts
import { createWalletClient, erc20Abi, http, parseEther } from "viem";
import { privateKeyToAccount } from "viem/accounts";
import { arcTestnet } from "viem/chains";

const PRIVATE_KEY =
  "0x1111111111111111111111111111111111111111111111111111111111111111";
const RECIPIENT = "0x2222222222222222222222222222222222222222";
const account = privateKeyToAccount(PRIVATE_KEY);
const client = createWalletClient({
  account,
  chain: arcTestnet,
  transport: http()
});

client.writeContract({
  address: "0x3600000000000000000000000000000000000000",
  abi: erc20Abi,
  functionName: "transfer",
  args: [RECIPIENT, parseEther("1")]
});
```

The accepted client is exactly the shown `const account` followed by the shown
`const client`. Direct temporary receivers and every other client alias are
unsupported. The recipient is exactly the shown `const RECIPIENT` binding. The
request, address, ABI, function, amount, and parser result are direct at the
shown positions.

### Parser grammar and decision

The only parser is direct root `parseEther(<ordinary string literal>)`.

```text
0
[1-9][0-9]*
0\.[0-9]{1,18}
[1-9][0-9]*\.[0-9]{1,18}
```

Evaluation uses bigint only:

```text
integer_part * 10^18 + right_padded_fraction
```

The result must satisfy:

```text
0 <= value <= 2^256 - 1
```

Decision:

```text
value === 0 → native18 → accepted → no finding
value > 0 and value <= 2^256 - 1 → native18 → accepted → one finding
everything else → unknown → no finding
```

There is no conversion state or post-conversion bound in this MVP.

### 7.2 Exact transformation language

Each fixture declares one base and an ordered list of these operations:

```text
identity()
replace_once(FRAGMENT_OR_EXACT_TEXT, exact replacement text)
delete_once(FRAGMENT_OR_EXACT_TEXT)
insert_before_once(FRAGMENT_OR_EXACT_TEXT, exact inserted text)
prepend_once(exact inserted text)
source_exact(exact complete source text)
```

Expansion fails if a target is absent or occurs other than once. Operations are
applied in listed order. There are no implicit defaults beyond the named base,
and the resulting source is the fixture's complete source.

The expansion grammar is deterministic:

- an operation ends at the final `)` before either the end of the expansion or
  `; ` followed by another allowed operation name;
- for a one-operand operation, everything between its opening and closing
  parentheses is the operand;
- for a two-operand operation, the separator is the rightmost comma for which
  the decoded left operand resolves to a named fragment or exact text occurring
  exactly once in the current source; every later comma must fail that test;
- the separator's one following ASCII space is not part of the right operand;
- named fragments are resolved before exact text is matched, and `\n` in an
  operand decodes to one LF.

The rightmost-match rule allows operands to contain imports, object literals,
calls, commas, and unbalanced source fragments while remaining mechanically
unambiguous. For example,
`replace_once(client.writeContract(, client["writeContract"]()` replaces the
dot-call prefix with the element-access call prefix; the last `)` terminates the
operation and is not part of the replacement.

Mechanical fixture validation must expand every fixture, preserve its declared
extension, reject an operation that does not have its declared arity, and parse
the result with trusted TypeScript 5.9.3 except for the explicitly malformed
fixture.

## 8. Analyzer stage, evaluation class, and evidence model

Analyzer stages describe only static-analysis control flow. Each fixture has
exactly one terminal analyzer stage:

| Stage | Meaning                 |
| ----- | ----------------------- |
| E0    | file/compiler           |
| E1    | provenance              |
| E2    | account                 |
| E3    | chain                   |
| E4    | transport               |
| E5    | client structure        |
| E6    | sink grammar            |
| E7    | request structure       |
| E8    | contract identity       |
| E9    | ABI/function            |
| E10   | arguments               |
| E11   | parser/value            |
| E12   | accepted source-to-sink |

Evaluation classification is independent of analyzer stage. It describes only
parsing, static eligibility, and the pinned semantics of the amount expression;
it is not a transaction-runtime model.

| Evaluation class      | Exact meaning                                                                                                                                                         |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `EV-NOT-PARSED`       | The file mode is unsupported, source is malformed, or the trusted compiler is unavailable. There is no expression-evaluation claim.                                   |
| `EV-STATIC-REJECTED`  | Source parses, but the analyzer rejects it before the amount contract is evaluated. There is no runtime claim.                                                        |
| `EV-ARGUMENT-THROWS`  | Pinned parser semantics prove that the amount expression throws if evaluated. No `writeContract`, ABI, preparation, signing, submission, or RPC execution is claimed. |
| `EV-ARGUMENT-RETURNS` | The amount expression returns a value, but another static parser/value requirement is unsupported. No transaction or submission claim is made.                        |
| `EV-ALTERNATE-SINK`   | Source uses a different sink shape, so the retained `writeContract` contract does not apply.                                                                          |
| `EV-EXACT-SINK-SHAPE` | Complete source matches the retained static source-to-sink grammar. This proves source-level submit capability only, never successful runtime execution.              |

Every fixture independently declares its terminal analyzer stage, evaluation
class, argument result (`not-applicable`, `throws`, or `returns`), exact retained
sink-shape match, ownership state, amount state, outcome, finding count,
applicable P IDs, and applicable REL IDs. Nothing is inherited from E0–E12.
P IDs establish symbol identity only. REL IDs establish the pinned semantic
facts in section 3.2 only; no fixture mapping claims that a relation executed.

The implementation validator declares four independent inventories:

- provenance IDs: P01 through P07, count 7;
- the nine named semantic REL IDs from section 3.2;
- analyzer stages: E0 through E12;
- the six evaluation classes above.

The validator uses semantic membership, never numeric position, ordering,
prefixes, ranges, or analyzer-stage ceilings. These explicit sets are part of
the contract:

- Keep the write candidate private; do not export it or change any public
  schema:

```ts
type C06B2WriteCandidate = {
  kind: "erc20-transfer-native18-amount";
  callOffset: number;
  amountOffset: number;
  amountLength: number;
  parserIdentity: "parseEther";
  literal: string;
  effectiveValue: bigint;
};
```

- The exact private issue kind is
  `erc20-transfer-native18-amount`.
- The exact message is:
  **“Arc USDC ERC-20 transfers use 6-decimal token units, but this amount is
  parsed with 18-decimal native units.”**
- The exact suggested correction is:
  **“Parse the transfer amount with 6-decimal USDC units before passing it to
  transfer(...).”**
- `parseUnits(value, 6)` may be shown as remediation guidance only. It is not an
  accepted safe-path analyzer contract in this milestone.
- `callOffset`, `amountOffset`, and `amountLength` are private ordering and test
  metadata only. They are not emitted location fields.
- The finding uses the existing file-level location behavior of
  `wallet/ARC_USDC_AMOUNT_CONVERSION` through `createWalletFinding`.
- Expression-level user-visible ranges are deferred to a separate R3
  prerequisite. C06B2 changes no legacy Finding field, FindingV2 contract,
  schema, adapter, fingerprint, or reporter.
- Emit at most one issue per file using this exact algorithm:
  1. collect existing C06B1 read candidates without changing them;
  2. collect valid C06B2 write candidates;
  3. concatenate the read candidates followed by the write candidates while
     retaining each candidate's original collection index;
  4. sort by source offset ascending;
  5. for equal offsets, use kind priority
     `native-read-as-erc20` = 0, `erc20-read-as-native` = 1,
     `erc20-transfer-native18-amount` = 2;
  6. use original collection index only as the final deterministic tie-break;
  7. emit only the first candidate, or none when the combined set is empty.

The two existing read kinds therefore retain their relative order, and the new
write kind follows both at an equal offset. When there is no write candidate,
the existing C06B1 kind, message, correction, file-level location, ordering, and
earliest-only behavior remain exactly unchanged.

E3 acceptance locks the following integration-selection cases:

| Case                            | Required result                                                                                     |
| ------------------------------- | --------------------------------------------------------------------------------------------------- |
| write only                      | emit the write issue with the existing file-level location behavior                                 |
| read only                       | emit the unchanged C06B1 issue                                                                      |
| write before read               | emit the write issue                                                                                |
| read before write               | emit the unchanged read issue                                                                       |
| equal offset                    | emit the read kind selected by the explicit kind priority                                           |
| multiple writes                 | emit only the earliest candidate                                                                    |
| repeated analysis               | identical kind, message, correction, file-level location, and ordering on every run                 |
| no candidate                    | emit nothing                                                                                        |
| invalid write plus valid read   | invalid write contributes no candidate and cannot suppress the read                                 |
| earlier read, later valid write | the earlier read remains exactly unchanged and wins                                                 |
| no write candidate              | output exactly matches the current legacy C06B1 finding, including its file-level location behavior |

These are integration-selection tests only. They do not add multi-write lexical
analysis, sibling isolation, mutation awareness, or any other deferred analyzer
surface.
