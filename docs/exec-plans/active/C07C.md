## Plan decision and supported surface

Build C07C later as two bounded implementation slices. Add a new private,
viem-specific analyzer beside the existing ethers analyzer, then add a thin
rule-level aggregator that selects the earliest valid ethers or viem violation.
Do not reopen the settled C07B ethers grammar, do not extract a generic AST
framework, and do not expand the first viem slice beyond source-proven
`createWalletClient(...).sendTransaction(...)` ownership.

The first slice recognizes only:

1. `createWalletClient` imported from the exact `"viem"` root entry;
2. `arcTestnet` imported from the exact `"viem/chains"` entry;
3. the exact built-in `http` transport from `"viem"`;
4. a JSON-RPC address account or a standard `privateKeyToAccount` account from
   `"viem/accounts"`;
5. the built-in `sendTransaction` wallet action without a user `.extend(...)`;
6. an exact, structurally safe request whose viem behavior proves EIP-4844;
7. an Arc Testnet client whose chain and transport agree.

Everything else is a tested negative or explicit defer. In particular, the
first slice does not infer ownership from file-level Arc text, package names,
generic `sendTransaction` property names, arbitrary RPC URLs, type annotations,
or imported values whose construction cannot be inspected.

## Goal

Extend `wallet/NO_BLOB_TX_ON_ARC` from its completed, bounded ethers surface to
a bounded viem surface without weakening C07B evidence, output, determinism,
package shape, or failure behavior.

A critical finding is permitted only when one same-file viem submission proves
all of these facts:

- the call is the built-in wallet client's `sendTransaction` action;
- the relevant client, chain, transport, account, and request bindings are

- Arc Testnet ownership is proven by exact first-party chain identity and a
  compatible built-in transport;
- the active account route has source-proven viem behavior;
- the active request is source-proven to be EIP-4844 for that account route;
- no supported override, mutation, escape, ambiguity, or conflict can alter
  those facts before the sink.

### Q1 — What exactly proves a viem blob transaction?

The answer depends on the active account path.

For a standard local account, `sendTransaction` calls
`prepareTransactionRequest`, then signs the request with the chain serializer.
`getTransactionType` checks an explicit truthy `type` first, then
`authorizationList`, then `blobs`, `blobVersionedHashes`,
`maxFeePerBlobGas`, or `sidecars`. The standard serializer dispatches an
`eip4844` request to an envelope beginning with `0x03`.

For a JSON-RPC account, viem formats a request and invokes
`eth_sendTransaction` or `wallet_sendTransaction`; it does not run the local
type inference or serializer. The standard formatter maps exact
`type: "eip4844"` to RPC type `0x3`. It forwards `blobs` and
`maxFeePerBlobGas`, but direct `blobVersionedHashes` is not extracted by the
standard send path unless a custom chain formatter participates. Node or wallet
inference from blob-looking fields is external behavior, not a viem source
guarantee.

Therefore the initial classifier is route-sensitive:

- exact `type: "eip4844"` is `proven-blob` for either approved account route;
- exact `type: "legacy"`, `"eip2930"`, `"eip1559"`, or `"eip7702"` is
  `proven-non-blob` when no contradictory blob evidence exists;
- for the standard local account only, omitted `type`, absent
  `authorizationList`, and an own, direct, nonnegative bigint
  `maxFeePerBlobGas` is `proven-blob`;
- numeric `3`, `"0x3"`, computed strings, identifiers, getters, shorthand from
  unsupported bindings, and node-dependent inference are `unknown`;
- an explicit non-blob type combined with blob-inference fields is
  `conflicting`, even though viem's explicit type currently wins;
- `kzg` alone is `unknown`; `getTransactionType` does not inspect it;
- `blobs` plus `kzg`, direct `blobVersionedHashes`, and `sidecars` are
  source-capable EIP-4844 paths but deferred until their validity, KZG
  provenance, dense-array semantics, and mutation families have a separate
  approved contract.

### Q2 — Is `writeContract` a first-party blob-capable public input?

Yes. In viem `2.55.10`, public `WriteContractParameters` includes formatted
transaction-request fields other than the contract-controlled data/from/to/value
positions. The implementation encodes the call and forwards the remaining
request to `sendTransaction`, so fields including `type`, `blobs`,
`blobVersionedHashes`, and `maxFeePerBlobGas` can reach the transaction path.

C07C nevertheless defers it as a scope/evidence decision, not a capability
denial. It needs a separate sink grammar, argument projection, ownership rules,
and adversarial family; simulated/imported requests remain deferred too.

### Q3 — What proves Arc ownership?

The initial positive ownership tuple is deliberately exact:

| Dimension      | Accepted initial evidence                                                                                      |
| -------------- | -------------------------------------------------------------------------------------------------------------- |
| Chain          | `arcTestnet` imported from `"viem/chains"` and passed directly or through one safe immutable same-file binding |
| Chain ID       | Source identity fixes it to decimal `5042002`; no independent numeric-ID grammar is needed                     |
| Transport      | built-in `http()` or `http("https://rpc.testnet.arc.network")` from the exact `"viem"` root import             |
| Client         | exact built-in `createWalletClient` with no user extension                                                     |
| Per-call chain | omitted, or the exact same safe `arcTestnet` identity as the hoisted chain                                     |

`http()` is sound only with the exact hoisted `arcTestnet` identity because the
built-in transport selects that chain's first default HTTP endpoint.
An explicit non-Arc URL conflicts with Arc chain evidence. An arbitrary,
computed, environment-derived, imported, fallback, WebSocket, or custom
transport is not positive evidence.

Direct chain object literals, standalone chain ID `5042002`, exact RPC literals
without `arcTestnet`, `defineChain(...)`, and `.extend(...)` can express Arc but
are deferred. Their separate formatter, serializer, fee, RPC, extension, and
mutation surfaces would expand the proof beyond the value of the first slice.
The viem export named `arc` has ID `5042`; it is not the approved Arc Testnet
identity and must never be confused with `arcTestnet`.

`chain: null`, an omitted client chain, an unknown per-call chain, or a
client/per-call disagreement yields no finding. This is stricter than viem's
runtime precedence because transport construction, request formatting, and
assertion behavior otherwise derive from different loci. Custom
`prepareTransactionRequest`, formatters, serializers, and chain extension
hooks invalidate the candidate.

### Q4 — Which account routes are safe?

The first slice approves:

- a lowercase exact source-valid address literal matching
  `^0x[0-9a-f]{40}$` supplied as the JSON-RPC account;
- a standard local account returned by exact `privateKeyToAccount` imported
  from `"viem/accounts"`.

Each may be client-hoisted or per-call. If both loci exist, they must resolve to
the same exact safe binding; disagreement is `conflicting`. One direct factory
call or one immutable same-file binding is allowed. Named import aliases are
allowed only when exact import-declaration identity and lexical binding
resolution prove the approved module export; C07C does not add a TypeScript
`Program`, `TypeChecker`, or module-resolution architecture.

Mnemonic and HD accounts eventually delegate to the same standard signer, but
their options and derivation surface are deferred to keep the initial account
grammar small. `toAccount`, arbitrary account objects, imported accounts,
custom `signTransaction`, smart accounts, account extension, and altered
serializers are unknown. A string or object type annotation is not provenance.

### Q5 — How do ethers and viem coexist?

The private analyzers remain independent; a thin consumer combines only their
already-proven submissions. No analyzer may borrow evidence from the other.
Candidate-invalid or unknown
viem evidence is returned under `analyzed` and does not suppress a valid ethers
candidate, and vice versa. The exact C07 whole-file barriers suppress both
libraries because they can alter either proof.

The rule filters each analyzer's records by its own explicit validity contract,
combines only already-valid violations, and selects the smallest `callOffset`.
An impossible equal-offset tie is resolved ethers before viem solely for stable
ordering. File iteration order and the maximum of one finding per file remain
unchanged.

Compiler-unavailable remains a hard rule error. If either analyzer reports it,
the consumer throws the existing `typescript compiler unavailable` error rather
than silently accepting partial analysis. This should be unreachable when both
use the same lazy compiler loader, but the failure contract must be explicit.
Thrown errors, unrecognized statuses, or disagreement on the common
file-eligibility/parse result are hard implementation errors.

## Static-analysis contract

### Provenance and import rules

- Resolve named ESM imports from exact import declarations and lexical
  bindings, matching the C07 analyzer architecture.
- Approve `"viem"` only for `createWalletClient` and `http`.
- Approve `"viem/chains"` only for `arcTestnet`.
- Approve `"viem/accounts"` only for `privateKeyToAccount`.
- Reject same-spelling locals, ambient declarations, re-exports through user
  modules, namespace access, default imports, CommonJS, dynamic imports, and
  type-only imports.
- Do not infer package identity from comments, strings, lockfiles, or nearby
  imports.

### Supported shapes

- Preserve the exact C07 eligibility predicate: `.js` and `.ts` only, excluding
  declarations, tests/specs, generated files/directories, dist, build, and
  coverage paths.
- Direct shape:
  `createWalletClient({ chain: arcTestnet, transport: http(), account }).sendTransaction(request)`.
- Client-binding shape:
  one immutable same-file `const client = createWalletClient(...)`, followed by
  exact `client.sendTransaction(request)`.
- Request-binding shape:
  one immutable same-file `const request = { ... }`, followed by an approved
  sink.
- Account-binding shape:
  one immutable same-file binding for `privateKeyToAccount(...)` or an exact
  JSON-RPC address.
- Chain-binding shape:
  one immutable same-file binding that resolves only to the exact imported
  `arcTestnet`.
- Binding depth is per approved slot: direct is depth 0, one immutable
  same-file `const` is depth 1, and depth 2+ is unsupported. `http(...)` must be
  direct; transport bindings are unsupported.
- The sink is an exact non-optional dot call with exactly one argument.

Object literals must use approved own, non-computed data properties. Reject
spreads, accessors, methods, duplicate relevant keys, computed keys, prototype
keys, unsupported shorthand, and ambiguous assignments. A supported shorthand
must resolve to one safe immutable binding whose value grammar is independently
approved.

### Binding safety and evaluation order

- Follow lexical bindings, not matching identifier text.
- Require declarations to dominate the sink.
- Honor source order for initialization and subsequent writes.
- Reject reassignment, update, destructuring write, property mutation,
  `Object.assign`, `Object.defineProperty`, deletion, alias mutation, and escape
  to an unknown call before the sink.
- Reject conditional, loop-dependent, exception-dependent, closure-dependent,
  async callback, or cross-function initialization.
- Treat a user `.extend(...)` on the client as candidate-invalid because viem
  permits an extension to replace protected wallet actions.
- Keep invalidation binding- or candidate-local whenever the affected identity
  is known.
- Reuse the exact C07 whole-file barrier contract without extracting a shared
  framework: global dynamic-code/global-object references, constructor-named
  call/new, prototype or `__proto__` access, computed-dynamic element access,
  unsafe global `Object`/`Reflect` use, and unresolved built-in mutation
  targets. Per-request prototype mutation is candidate-invalid when the exact
  target is proven; `Object.prototype` mutation is whole-file unsupported.

### State model

The private viem analysis result uses the existing file statuses `analyzed`,
`unsupported-file`, `compiler-unavailable`, `malformed`, and
`unsupported-source`, plus library-specific records. `unsupported-source` is
reserved for the approved C07 whole-file barriers above.

- provenance: `viem-wallet-client` or `unknown`;
- sink: `sendTransaction` or `unknown`;
- structural safety: `safe` or `candidate-invalid`;
- ownership: `proven-arc`, `proven-non-arc`, `unknown`, or `conflicting`;
- account: `json-rpc`, `private-key-local`, `unknown`, or `conflicting`;
- transaction kind: `proven-blob`, `proven-non-blob`, `unknown`, or
  `conflicting`;
- exact evidence token: `eip4844` or `maxFeePerBlobGas`;
- call offset: numeric source offset;
- optional internal reason code for tests and review, not public output.

The public rule reports only records with approved provenance, exact sink,
`safe` structure, `proven-arc` ownership, an approved non-conflicting account,
`proven-blob` kind, and an approved exact evidence token. Candidate-level
reason codes distinguish client, chain, transport, account, request, and sink
invalidation for sibling-isolation tests.

| Combined file result                             | Consumer action                                                             |
| ------------------------------------------------ | --------------------------------------------------------------------------- |
| Both `analyzed`                                  | Filter independently, combine valid violations, select minimum `callOffset` |
| One has only candidate-invalid/unknown records   | The other analyzer's valid violation survives                               |
| Either `unsupported-source`                      | Suppress the file only for an approved shared whole-file barrier            |
| Either `malformed` or both `unsupported-file`    | No finding; preserve current eligibility/parse behavior                     |
| One `unsupported-file` while the other is not    | Hard implementation error                                                   |
| Either `compiler-unavailable`                    | Throw the existing compiler-unavailable error                               |
| Throw, unknown status, or impossible combination | Hard implementation error                                                   |

## Architecture options

### Option A — Extend the existing ethers analyzer

Rejected. Its 2,199 lines and 297 tests encode ethers-specific signer/provider
semantics; adding viem account, transport, extension, and type rules would
couple two runtime models and enlarge C07B regression risk.

### Option B — Separate private viem analyzer plus thin aggregator

Selected. It preserves ethers, gives viem its own states/tests, keeps
aggregation inspectable, and adds no public/dependency surface. Duplicate small
syntax stays private until two consumers prove stable shared semantics.

### Option C — Extract a generic transaction AST framework first

Rejected. One consumer with different account/chain/hook semantics does not
justify speculative R3 infrastructure; sharing requires two stable consumers
and preservation tests.

## Threat model and mutation families

Implementation review must mutate every accepted evidence dimension:

- import source, export spelling, alias, shadowing, and re-export;
- client constructor, extension state, assignment, alias, and escape;
- chain identity, hoisted/per-call precedence, null, omission, and conflict;
- transport constructor, URL, options, wrapper, fallback, and mutation;
- account locus, route, factory, signer override, reassignment, and conflict;
- request locus, property syntax, duplicate, spread, getter, mutation, and escape;
- explicit type token, inferred blob-fee field, contradictory field, and
  authorization-list precedence, unsupported source-capable field, and
  inherited type injection through per-request/global prototypes;
- sink receiver, property access, destructuring, wrapper, alternate action, and
  multiple-candidate order;
- cross-library ordering and analyzer-local invalidation;
- malformed source, compiler absence, and each approved whole-analyzer barrier.

A passing happy path without its mutation family is not acceptance evidence.
When repeated misses share a cause, update the contract and the whole mutation
family rather than patching individual fixtures.
