## Product decision

Implement C07C as a **conservative explicit-pattern MVP**.

ArcReady will report only a small, common, source-proven viem submission shape.
Ambiguous or unsupported shapes produce no viem finding and must not be described
as safe.

This plan deliberately prefers bounded false negatives over critical false
positives. C07C is not authorization to build a general TypeScript data-flow,
mutation, alias, or module-resolution engine.

## Goal

Extend the completed ethers-only `NO_BLOB_TX_ON_ARC` rule with reliable viem
coverage for exact `createWalletClient(...).sendTransaction(...)` calls that
prove all of the following in one same-file executable flow:

- exact first-party viem import provenance;
- exact Arc Testnet chain identity;
- exact built-in HTTP transport;
- an approved JSON-RPC or private-key local account route;
- an exact built-in wallet-client `sendTransaction` sink;
- an exact own direct `type: "eip4844"` request property;
- direct or one-level immutable binding safety;
- no supported mutation, reassignment, shadowing, or evidence joining before the
  sink.

## Non-goals

- Do not modify C07A or C07B ethers behavior.
- Do not create a shared ethers/viem AST framework.
- Do not add `viem` as a dependency.
- Do not add TypeScript `Program`, `TypeChecker`, or module resolution.
- Do not support cross-file ownership.
- Do not support generic control-flow or data-flow analysis.
- Do not support alias depth 2+, branching aliases, or general mutation graphs.
- Do not support per-call chain or account overrides in this MVP.
- Do not infer EIP-4844 from `maxFeePerBlobGas`, `authorizationList`, `blobs`,
  `blobVersionedHashes`, `sidecars`, or `kzg`.
- Do not support `writeContract`, raw, sync, deploy, custom, account-abstraction,
  or simulation-derived transaction paths.
- Do not support custom transports, formatters, serializers, hooks, or client
  extensions.
- Do not change rule ID, severity, message, suggested fix, docs URL, presets,
  schema, reporters, scoring, exits, file order, or one-finding-per-file behavior.
- Do not make the rule canonical during C07C.

## Architecture

Use two private, viem-specific modules:

```text
packages/arcready/rules/wallet/viem-transaction-submission-lexical.ts
packages/arcready/rules/wallet/viem-transaction-submission-analyzer.ts
```

Responsibilities:

### `viem-transaction-submission-lexical.ts`

- exact named-import provenance;
- executable lexical scopes needed by the declared MVP surface;
- direct and one-level immutable `const` bindings;
- declaration order;
- shadowing and reassignment checks;
- binding identity independent from classified value;
- no shared or generic AST framework.

### `viem-transaction-submission-analyzer.ts`

- lazy TypeScript compiler boundary;
- file eligibility and deterministic statuses;
- exact client, chain, transport, account, request, and sink grammar;
- candidate-local classification;
- deterministic source ordering by exact `callOffset`.

Both files remain private and unconsumed in C07C-A. They must not import, modify,
or expose the ethers analyzer.

## Exact supported positive surface

A record is reportable only when every dimension below is proven.

### Imports

Allow exact named ESM imports from exact modules:

```ts
import { createWalletClient, http } from "viem";
import { arcTestnet } from "viem/chains";
import { privateKeyToAccount } from "viem/accounts";
```

Direct named aliases are allowed only when exact import-declaration identity is
proven.

Namespace, default, type-only, CommonJS, dynamic import, user re-export, wrong
subpath, and same-spelling local provenance are unsupported.

### Binding budget

Allow depth 0 or one immutable same-file `const` binding for:

- client;
- request;
- JSON-RPC address account;
- `privateKeyToAccount(...)` account;
- `arcTestnet` chain identity.

`http(...)` must be direct. Transport bindings are unsupported.

Depth 2+, branching aliases, imported values, wrappers, conditional values,
cross-function values, callback-dependent values, and cross-file values produce
no viem finding.

### Client

Allow only exact built-in `createWalletClient` with one direct object literal.
The object must contain exact approved chain, transport, and account evidence.

Relevant object properties must be own, direct, non-computed data properties.
Spreads, accessors, methods, duplicate relevant keys, prototype-sensitive keys,
and ambiguous shorthand are unsupported.

### Chain

Allow only exact imported `arcTestnet`, direct or through one immutable `const`.

Do not support numeric chain ID `5042002`, direct chain objects,
`defineChain(...)`, viem `arc`, Ethereum mainnet, omitted/null chain, or per-call
chain override.

### Transport

Allow only direct exact root-import calls:

```ts
http()
http("https://rpc.testnet.arc.network")
```

No options argument is allowed. Computed URLs, environment values, wrappers,
transport bindings, non-Arc URLs, `custom`, `fallback`, and `webSocket` are
unsupported.

### Account

Allow only:

1. an exact lowercase JSON-RPC address literal matching
   `^0x[0-9a-f]{40}$`, direct or through one immutable `const`;
2. exact `privateKeyToAccount(<one argument>)`, direct or through one immutable
   `const`, from the exact `"viem/accounts"` import.

Do not support per-call account override, custom account objects, `toAccount`,
mnemonic/HD accounts, smart accounts, custom `signTransaction`, imported
accounts, or account extension.

Account class/value and binding identity must remain separate. Where two
supported loci are compared, agreement requires the same exact safe binding
identity, not merely equal-looking text.

### Sink

Allow only an exact non-optional dot call with exactly one argument:

```ts
client.sendTransaction(request)
```

The direct `createWalletClient(...).sendTransaction(...)` form is also allowed.

Element access, optional chaining, detached/destructured actions,
`call`/`apply`/`bind`, standalone actions, wrappers, and alternate transaction
actions are unsupported.

### Request and transaction kind

Allow a direct object literal or one immutable same-file `const` object.

The only positive blob grammar is an exact own direct property:

```ts
type: "eip4844"
```

Numeric `3`, `"0x3"`, identifiers, shorthand, computed values, getters,
imported values, template strings, and concatenated strings are unsupported.

Ordinary duplicate non-relevant properties do not invalidate a request merely
because they are duplicated. Duplicate rejection applies only to the approved
relevant-key set and structurally dangerous keys.

## Minimum safety contract

The replacement analyzer implements only the safety needed by its declared
surface:

- exact lexical binding identity;
- declarations dominate the sink;
- approved imports and bindings are not reassigned before the sink;
- direct protected client/request/account/chain identities are not mutated or
  passed to unknown calls before the sink;
- static element `.extend` equivalents are treated consistently with dot access;
- depth-2 and branching alias topology is rejected rather than analyzed;
- candidate-local invalidation does not suppress an unrelated valid candidate;
- evidence is never borrowed from sibling objects or calls;
- mutations after the sink do not invalidate an earlier call;
- partial or invalid compiler API shapes return `compiler-unavailable` rather
  than throwing.

The MVP does not implement a general alias graph, prototype engine, Object/Reflect
mutation engine, or escape-analysis framework. A shape requiring one of those
facilities is outside the positive grammar.

## File statuses and private records

Preserve deterministic private statuses:

- `analyzed`;
- `unsupported-file`;
- `compiler-unavailable`;
- `malformed`;
- `unsupported-source` only for an explicitly approved file-wide barrier.

Private submission records retain enough state for review and later integration:

- provenance;
- sink;
- structural safety;
- ownership;
- account route;
- transaction kind;
- exact evidence token `eip4844`;
- exact `callOffset`;
- optional internal reason code.

No public finding or reporting behavior is added in C07C-A.

## Acceptance strategy

Use approximately 35–50 meaningful cases rather than preserving the original
60 analyzer labels as artificial coverage.

Required positive families:

- direct JSON-RPC account and request;
- one `const` client binding;
- one `const` request binding;
- one `const` JSON-RPC account binding;
- direct and one-`const` `privateKeyToAccount` route;
- approved direct import aliases;
- direct and one-`const` `arcTestnet`;
- `http()` and exact primary Arc RPC;
- multiple valid calls ordered by exact source offsets.

Required fail-closed families:

- wrong import source/export/form and lexical shadowing;
- approved import or binding reassignment before the sink;
- depth 2+, branching alias, wrapper, cross-function, and imported values;
- omitted/null/non-Arc chain and per-call override;
- non-Arc/computed/options/custom/fallback/WebSocket transport;
- invalid, mixed-case, custom, and imported account routes;
- request mutation and unknown-call escape before the sink;
- spread, duplicate relevant key, computed relevant key, getter/method, and
  prototype-sensitive key;
- non-exact type values and all deferred blob-looking fields;
- unsupported sink forms;
- sibling evidence isolation;
- malformed source and progressive invalid compiler shapes;
- exact before/after-sink behavior;
- candidate-local invalidation preserving an unrelated valid candidate.

Every positive family receives at least one meaningful fail-closed mutation.
Tests assert exact status, state/reason where applicable, reportable count, and
exact `callOffset` when ordering matters.
