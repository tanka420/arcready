## 1. Goal

Migrate `bridge/ATTESTATION_404_NOT_FATAL` from a default critical heuristic to
explicitly opted-in, deprecated advice without introducing a new attestation
analyzer.

The migration must preserve the public rule ID for one compatibility period,
remove default bridge execution, provide a real configuration opt-in path, and
make the detector's conditional limitations explicit.

## 2. Approved disposition

C08-D selects:

```text
Advice-only
```

C08A implements that disposition. It does not reopen Build or Retire.

The R3 prototype remains research/test evidence and must not be imported into
production rule execution.

## 3. Current behavior

Today:

- `attestation404NotFatalRule` is included in `bridgeRules`;
- `bridgeRules` currently serves both the public all-known bridge inventory and
  the default bridge preset source;
- the default bridge preset therefore schedules it;
- its default severity is `critical`;
- the detector is a proximity regex;
- the finding copy says a `404` should be treated as retryable pending state;
- the public symbol and ID are exported;
- `config.rules[id]` only overrides a rule after preset selection.

Removing the rule from `bridgeRules` alone would remove default execution but
would not create a usable explicit opt-in path.

## 4. Target behavior

After C08A:

### Default bridge scan

- public `bridgeRules` still includes the known rule ID;
- the private default bridge subset does not include the rule;
- the rule is not selected by a normal default scan;
- it emits no findings;
- it cannot affect score, `failOn`, process exit, reports, or FindingV2;
- remaining bridge-rule order is unchanged;
- known/default inventory becomes 19 / 16 while wallet remains 7 and canonical
  remains 4.

### Explicit configuration

Given:

```json
{
  "presets": ["bridge"],
  "rules": {
    "bridge/ATTESTATION_404_NOT_FATAL": "info"
  }
}
```

ArcReady selects the known default-excluded rule exactly once and normalizes any
finding to `info`.

The same applies to explicit `warning` and `critical` levels.

A missing entry or explicit `off` does not select the rule.

Unknown IDs remain valid configuration data but do not select runtime rules.

### Direct/custom-registry use

The rule remains publicly exported for compatibility and uses
`defaultSeverity: "info"` when run directly or through a custom registry without
an explicit override.

## 5. Bounded architecture

### 5.1 Known/default bridge split

Keep `bridgeRules` unchanged as the all-known public bridge array, including the
attestation rule.

Create one private `bridgeDefaultPresetRules` subset in the preset module and
use it only when constructing `defaultPresetRegistry`. Exclude only
`attestation404NotFatalRule` from that subset. Do not reorder the remaining
bridge rules.

This follows the existing separation between `appKitRules` and
`appKitDefaultPresetRules`.

### 5.2 Private built-in default-excluded registry

Add one private deterministic registry such as:

```text
defaultExcludedRulesById
```

The registry initially contains only:

```text
bridge/ATTESTATION_404_NOT_FATAL
```

The registry belongs to the module's top-level default-selection path. It is not
attached to `PresetRegistry`, passed implicitly into `createPresetRegistry()`, or
exported publicly.

### 5.3 Explicit top-level selection

Extend only the top-level default helper with the configured rule-level map:

```text
getRulesForScan(configuredPresets, detection, configuredRules = {})
```

The helper must:

1. obtain ordinary rules from `defaultPresetRegistry.getRulesForScan(...)`;
2. append each known default-excluded rule whose configured level is `info`,
   `warning`, or `critical`;
3. omit missing and `off` entries;
4. deduplicate by rule ID;
5. preserve deterministic private-registry order.

Do not iterate arbitrary config IDs to discover public exports. Do not throw on
unknown IDs or change config validation semantics.

### 5.4 Public API and custom-registry isolation

Keep `PresetRegistry` and `createPresetRegistry()` instance signatures and
behavior unchanged. Custom registries must never receive built-in excluded rules
implicitly.

Extend only the already-exported top-level `getRulesForScan` function with an
optional third argument defaulting to an empty map. This preserves existing
two-argument source compatibility.

`runScan` must pass `config.rules` into that top-level helper.

## 6. Rule policy migration

Update `attestation-404-not-fatal.ts` without widening detection.

Required changes:

- `defaultSeverity: "info"`;
- description and finding text identify conditional attestation handling advice;
- remediation requires validation of burn success, transaction hash, and source
  domain before retrying;
- remediation requires delayed/bounded polling and separate handling for `429`,
  unexpected non-OK responses, empty messages, pending, and completion;
- no statement says every `404` is safe or retryable;
- detector remains the existing deprecated low-confidence heuristic;
- no R3 AST prototype code is imported.

## 7. Catalog migration

Update both:

```text
docs/rule-catalog.md
packages/arcready/core/rules/catalog.ts
```

Required policy values:

```text
taxonomy=advice
impact=recommendation
maturity=deprecated
recommendedDefaultEnabled=false
recommendedCiFailureEligible=false
deprecated=true
```

Update rationale and detector limitations to state:

- `404` is conditional;
- request provenance and control flow are not proven;
- the detector is explicit optional guidance only;
- C08 found no bounded critical analyzer with meaningful first-party coverage.

Record C08-R1/R2/R3/D as internal evidence and schedule a later Retire review.

The catalog remains policy metadata and must not become the runtime selector.

## 8. Implementation phases

### C08A-E1 — explicit selection foundation

Scope:

- keep `bridgeRules` as all-known inventory and add the private default bridge
  subset;
- add the one-rule private built-in default-excluded registry;
- extend only top-level default rule selection with explicit configured levels;
- pass `config.rules` from `runScan`;
- add deterministic selection and compatibility tests.

Acceptance:

- public `bridgeRules` retains the ID while the default bridge subset excludes
  it;
- default bridge preset excludes the rule;
- explicit `info`, `warning`, and `critical` select it once through the top-level
  default helper;
- missing and `off` do not select it;
- unknown IDs do not select anything;
- custom registry instances never receive the built-in excluded rule;
- remaining preset order and deduplication are byte-for-byte stable where
  observable;
- no rule policy or copy changes in E1 beyond what tests need.

### C08A-E2 — advisory rule and catalog policy

Scope:

- set default severity to `info`;
- update rule copy and remediation;
- update runtime/documentation catalog metadata;
- mark deprecated/default-excluded policy explicitly;
- add rule-level behavior tests for conditional wording and configured severity.

Acceptance:

- no unconditional retry claim remains;
- policy metadata agrees across code and docs;
- direct/custom-registry execution defaults to `info`;
- explicit levels remain authoritative;
- no detector widening occurs.

### C08A-E3 — integration, fixtures, and closeout evidence

Scope:

- update default fixture and inventory expectations;
- verify default finding-count changes intentionally;
- update roadmap/backlog/C08 closeout state;
- document explicit opt-in configuration and deprecation behavior;
- run full repository verification.

Acceptance:

- inventory is 19 known / 16 default / 7 wallet / 4 canonical;
- default bridge scans do not execute the rule;
- explicit opt-in behavior is covered end to end;
- legacy reports, scoring, `failOn`, CLI exits, schemas, reporters, and FindingV2
  change only as a consequence of removing the default heuristic finding;
- full repository gate and independent review pass.

## 9. Test matrix

### Selection tests

- `bridgeRules` retains the known ID;
- the private default bridge subset and default bridge preset exclude the ID;
- bridge plus wallet/app-kit presets preserve order and deduplication;
- explicit `info` selects the rule;
- explicit `warning` selects the rule;
- explicit `critical` selects the rule;
- explicit `off` does not select the rule;
- missing entry does not select the rule;
- unknown ID does not select a rule;
- a custom `createPresetRegistry()` instance does not receive the built-in
  excluded rule;
- duplicate preset/default-excluded selection executes once;
- an empty configured-rules map preserves existing selection behavior.

### Runtime tests

- default bridge scan does not execute the rule;
- explicit opt-in executes it and emits configured severity;
- explicit opt-in with non-matching source emits no finding;
- explicit `off` records no scheduled occurrence;
- instrumentation selection indices remain deterministic;
- execution failure fallback uses the configured level where applicable.

### Regression tests

- public rule export and `bridgeRules` inventory entry remain available;
- private default bridge rule order excluding the ID is pinned;
- all inventory assertions are intentional;
- default demo/fixture finding counts are updated only where the heuristic was
  previously emitted;
- default `critical` exit behavior no longer depends on this rule;
- JSON, Markdown, HTML, terminal, and `json-v2` contracts remain valid;
- package build and smoke tests pass.

## 11. Non-goals

C08A does not include:

- a production attestation AST analyzer;
- import, helper, CFG, SSA, taint, or cross-file analysis;
- live Circle API calls;
- runtime burn/hash/domain validation;
- a generic plugin or arbitrary rule registry;
- changes to `PresetRegistry` or custom `createPresetRegistry()` semantics;
- config schema changes beyond passing existing `rules` data into selection;
- removal of the public rule ID;
- immediate Retire;
- changes to canonical FindingV2;
- C09 or C10 implementation.

## 12. Risk controls

## 14. Exit criteria

C08A is complete only when:

- default bridge execution excludes the rule;
- explicit opt-in works for known non-off levels and only known excluded rules;
- missing/off/unknown configuration remains non-selecting;
- public ID compatibility is retained;
- rule and catalog policy are Advice-only and deprecated;
- no unconditional retry wording remains;
- inventory and fixture changes are intentional;
- full repository verification passes;
- independent review reports `APPROVE` with zero blocker, major, and minor
  findings;
- C08 closeout records the later Retire review trigger.

## 15. Conclusion

C08A is a bounded scheduling and policy migration, not an analyzer build.

The optimal implementation removes an unsupported critical heuristic from
default CI while preserving a narrow, explicit compatibility path for users who
still need the public ID during deprecation.
