# C07 — Ethers Transaction-Submission Ownership and Blob Rule Hardening

Status: Approved

Risk class: R3

Owner: ArcReady maintainers

Base branch: `main`

Base SHA: `49b95b85d13a223e902bd66dde7c630d78871fa5`

Last reviewed: 2026-07-24

## 1. Product goal

Replace the file-level `wallet/NO_BLOB_TX_ON_ARC` heuristic with an
ethers-specific, same-file proof that an exact ethers v6 signer submits an
explicit type-3 transaction through an effectively Arc-owned provider.

C07 does not claim support for every Arc transaction submission. The approved
implementation scope is:

- C07A: a private ethers transaction-submission ownership analyzer with no
  user-visible findings;
- C07B: an ethers-only consumer that hardens
  `wallet/NO_BLOB_TX_ON_ARC`.

All C07C-dependent ownership and consumer work remains blocked on a separate
future exec plan and independent approval. C07A/B is therefore not a complete
prerequisite for C07C-dependent write-side C06B2 work.

Success means that, for a bounded same-file JavaScript or TypeScript flow,
ArcReady can prove:

1. the provider and signer have exact supported ethers v6 provenance;
2. the exact signer submits one structurally supported transaction;
3. provider and transaction ownership resolve to `proven-arc`;
4. the transaction contains the exact decimal source token `type: 3`;
5. no unsupported mutation, prototype behavior, wrapper, or dynamic execution
   invalidates the proof.

Ambiguous, conflicting, inherited, imported, computed, reassigned, mutated,
cross-file, or otherwise unsupported evidence produces no critical finding.

## 2. Architecture decision

Decision: **Build C07A and C07B; defer C07C**.

### C07A — private ethers ownership analyzer

C07A supports only:

- exact root ESM imports from `"ethers"`;
- `JsonRpcProvider`;
- `Wallet` constructed with a supported provider;
- exact awaited `provider.getSigner()`;
- `ethers-wallet` and `ethers-json-rpc-signer` provenance;
- exact `signer.sendTransaction(transaction)` sinks;
- bounded provider, signer, transaction, and ownership evidence;
- private internal types and tests;
- no user-visible findings or production consumer.

C07A is not a shared cross-library analyzer and does not create a generic AST
framework.

### C07B — ethers-only rule hardening

C07B reports only when all of the following are proven:

1. exact supported ethers v6 signer provenance;
2. exact `signer.sendTransaction` sink grammar;
3. effective ownership is `proven-arc`;
4. the submitted transaction object is structurally supported;
5. `type` is an own data property whose value is the exact decimal source token
   `3`.

Blob-looking supporting fields never independently prove transaction kind.
There is no generic method-name or blob-field fallback.

### C07C — separately planned viem milestone

C07C is outside this plan's implementation scope. It requires its own premise,
object/prototype contract, threat model, acceptance matrix, implementation
slices, validation, and independent approval before any viem finding is
enabled.

This split is a class-C architecture correction for C07-RR-11 and C07-RR-12,
not another expansion of the current analyzer.

## 3. Premise and version boundary

Sources were revalidated on 2026-07-24.

### Arc

- Arc infrastructure documentation states that EIP-4844 blob transactions are
  unsupported:
  https://docs.arc.io/integrate/infrastructure
- Arc bridge guidance requires type-2 EIP-1559 transactions rather than blob
  transactions:
  https://docs.arc.io/integrate/infrastructure/bridges
- Arc Testnet chain ID is `5042002` and its primary RPC is
  `https://rpc.testnet.arc.network`:
  https://docs.arc.io/arc/references/connect-to-arc

### Ethers v6

The reviewed semantic baseline is exact `ethers@6.17.0`. The official
`refs/tags/v6.17.0` is a lightweight tag that resolves directly to source
commit `3ea4c226dd0b3a074abf90748de9d11192027f4f`; there is no separate peeled
`refs/tags/v6.17.0^{}` object.

- `Wallet` follows the `AbstractSigner` path: populate, sign, then broadcast.
- `JsonRpcSigner`, returned by `JsonRpcProvider.getSigner()`, formats and sends
  an `eth_sendTransaction` request.
- The reviewed JSON-RPC formatter forwards `type`, `chainId`, and
  `blobVersionedHashes`, but not `blobs`, `kzg`, or `maxFeePerBlobGas`.
- `AbstractSigner.populateTransaction` checks an explicit transaction `chainId`
  against the connected provider network before broadcast.
- Wallet type inference can select type 2 from fee data. C07 therefore does not
  infer blob kind from supporting fields or omitted type.

Reviewed source:

- https://github.com/ethers-io/ethers.js/tree/v6.17.0
- https://github.com/ethers-io/ethers.js/blob/v6.17.0/src.ts/providers/provider-jsonrpc.ts
- https://github.com/ethers-io/ethers.js/blob/v6.17.0/src.ts/providers/abstract-signer.ts
- https://github.com/ethers-io/ethers.js/blob/v6.17.0/src.ts/providers/network.ts

ArcReady does not depend on ethers and does not inspect application lockfiles.
Exact imports and syntax establish API provenance only; they do not prove the
installed dependency version. Unsupported or version-shaped module specifiers,
including a literal `"ethers@6.17.0"` specifier, fail closed.

## 4. Current state and boundaries

The legacy rule currently:

- scans wallet files as text;
- combines broad Arc markers with blob-related text;
- cannot prove submission, signer provenance, transaction ownership, or
  transaction kind;
- can join evidence from unrelated Arc and Ethereum sibling flows.

At the planning baseline:

- known rule inventory: 19;
- default rules: 17;
- wallet rules: 7;
- canonical FindingV2 runtime: exactly 4 rules;
- `wallet/NO_BLOB_TX_ON_ARC`: active legacy, default critical, non-canonical;
- TypeScript runtime dependency: exact `5.9.3`, loaded lazily;
- no public AST or ownership API exists.

C07A changes none of these runtime boundaries. C07B changes only the internal
detection behavior of the existing legacy rule.

## 5. C07A supported surface

### 5.1 Eligible files

Support only:

- plain `.js` and `.ts`;
- non-test, non-spec, non-declaration files;
- files outside `test`, `tests`, and `__tests__` directories;
- parse-valid executable syntax;
- source, block, function, class-expression, namespace/module-block, catch,
  loop, and case lexical scopes.

Exclude:

- `.d.ts`, `.jsx`, `.tsx`, `.mjs`, `.cjs`;
- ambient declarations, string-named modules, type-only surfaces;
- comments, strings, documentation, generated files, and cross-file analysis;
- files with TypeScript parse diagnostics.

TypeScript loads only when an enabled consumer reaches an eligible file.

### 5.2 Import and library identity

Supported identities:

- named value imports and import aliases from exact module `"ethers"`;
- namespace imports from exact module `"ethers"`;
- exact named-import alias or namespace dot access for constructors.

Unsupported:

- default imports;
- type-only imports as runtime evidence;
- CommonJS `require`;
- `@ethersproject/*`, ethers subpaths, version-shaped module names, wrapper
  packages, adapters, re-exports, and local modules;
- local lookalikes, shadowed imports, detached or locally rebound
  constructors;
- imported provider, signer, or transaction instances;
- subclasses and wrapper factories.

### 5.3 Exact call grammar

#### JsonRpcProvider

Supported:

```text
new <exact-JsonRpcProvider-identity>(<rpc>)
new <exact-JsonRpcProvider-identity>(<rpc>, <network>)
```

- exactly one or two present, non-spread arguments;
- direct supported arguments or their allowed slot binding;
- optional trailing comma after the final present argument.

Zero, extra, omitted, spread, optional, element-access, detached,
local-alias, shadowed, wrong-package, and lookalike forms are unsupported.

#### Wallet

Supported:

```text
new <exact-Wallet-identity>(<private-key-expression>, <supported-provider>)
```

- exactly two present, non-spread arguments;
- optional trailing comma;
- result assigned to the one supported signer binding.

Missing provider, zero/one/extra/omitted/spread arguments, direct constructor
sink receiver, `Wallet.createRandom`, `Wallet.fromPhrase`, `connect`, and every
other signer factory are deferred.

#### JsonRpcSigner

Supported:

```text
const signer = await provider.getSigner()
```

- exact supported provider binding;
- dot property access;
- exactly zero arguments;
- required `await`;
- valid async or module top-level-await context;
- one signer binding.

Element access, optional property/call, detached/destructured references,
`.call`, `.apply`, `.bind`, any argument, invalid await context, and unawaited
forms are unsupported.

#### Submission sink

Supported:

```text
<supported-signer-binding>.sendTransaction(<one non-spread transaction>)
```

- dot property access only;
- exactly one present, non-spread argument;
- optional trailing comma;
- transaction is a direct object literal or the one transaction binding.

Zero, extra, omitted, spread, optional, element-access, detached/destructured,
`.call`, `.apply`, `.bind`, arbitrary Signer-like objects, preparation,
signing-only, estimation, static call, contract send, deploy, and raw broadcast
forms are unsupported.

### 5.4 Binding budget

This table is the canonical value-binding budget. The budget is per semantic
slot, and bindings may accumulate across different slots in one supported flow.
The exact call grammar in section 5.3 may further restrict where a direct form
may appear; in particular, a signer must still use its one binding as the sink
receiver and `getSigner` must still use a provider binding.

| Semantic slot         | Direct form                                                  | One immutable same-file `const` binding     | Rejected depth + 1                      |
| --------------------- | ------------------------------------------------------------ | ------------------------------------------- | --------------------------------------- |
| RPC URL               | supported ordinary string literal                            | `const rpc = "..."`                         | `rpc2 -> rpc1 -> literal`               |
| provider network      | supported number, bigint, or `"mainnet"` literal             | `const network = <supported-literal>`       | `network2 -> network1 -> literal`       |
| provider              | exact `new JsonRpcProvider(...)` construction                | `const provider = new JsonRpcProvider(...)` | `provider2 -> provider1 -> constructor` |
| Wallet signer         | exact `new Wallet(key, provider)` construction               | `const signer = new Wallet(key, provider)`  | `signer2 -> signer1 -> Wallet`          |
| JsonRpcSigner         | exact `await provider.getSigner()`                           | `const signer = await provider.getSigner()` | `signer2 -> signer1 -> getSigner`       |
| transaction object    | direct supported object literal at the sink                  | `const tx = { ... }`                        | `tx2 -> tx1 -> object`                  |
| transaction `chainId` | direct own supported literal only                            | none; an identifier value is `unknown`      | every identifier hop                    |
| transaction `type`    | direct own exact decimal source token `3` only for a finding | none; an identifier value is `unknown`      | every identifier hop                    |
| blob/hash array       | direct supported array                                       | one array binding                           | `values2 -> values1 -> array`           |
| blob-fee value        | direct supported literal                                     | one value binding                           | `fee2 -> fee1 -> literal`               |

The Wallet and JsonRpcSigner direct forms in the table describe their supported
initializers; a direct constructor or awaited call is not a supported sink
receiver. An import alias and namespace dot identity are not value-binding
dereferences. Alias-to-alias, imported, destructured, reassigned, conditional,
factory-produced, or cross-file values are unsupported. Transaction `chainId`
and `type` deliberately do not inherit the one-binding allowance of any other
slot.

### 5.5 Mutation and dynamic-execution policy

Every critical evidence binding—RPC, provider network, provider, signer,
transaction, blob/hash array, and blob-fee value—uses file-global invalidation
tied to lexical identity.

The critical object bindings for target analysis are:

- provider;
- `ethers-wallet` signer;
- `ethers-json-rpc-signer`;
- transaction;
- one approved alias of any of those objects.

The proof is invalidated by a matching write before or after the sink:

- direct, compound, or logical assignment;
- prefix/postfix increment or decrement;
- property or element assignment;
- property/element compound or logical assignment;
- property/element increment or decrement;
- `delete`;
- destructuring or loop-target writes;
- `Object.assign` targeting a critical object or alias;
- `Object.defineProperty` or `Object.defineProperties` targeting a critical
  object or alias;
- `Object.setPrototypeOf` or `Reflect.setPrototypeOf` targeting a critical
  object or alias;
- `push`, `pop`, `shift`, `unshift`, `splice`, `sort`, `reverse`,
  `copyWithin`, or `fill` on a critical array;
- the same operations through one exact one-hop alias;
- escape of a critical object as the receiver or argument of an unsupported
  call, `new`, or tagged template, including `.call`, `.apply`, `.bind`, and
  `this`-based mutation;
- storing, returning, yielding, or exporting a critical object through an
  unsupported object, aggregate, or external binding;
- unsupported alias topology.

For each named built-in mutator, the target is its first present, non-spread
argument after balanced-parenthesis removal. A target that resolves to a
critical object or approved alias invalidates that proof. A dynamic or unknown
target that cannot be proven distinct from every critical object makes the
whole eligible file unsupported. A missing, omitted, or spread target is
unknown and also rejects the file. A target may be ignored only when it is a
fresh direct object/array literal or lexical identity proves it is an unrelated
local `const` binding initialized to such a fresh literal, and no supported
alias, assignment, aggregate, or escape connects it to a critical object.
Merely using a different identifier spelling is not proof of unrelated
identity.

A nested write resolving to an outer binding invalidates it. A write resolving
only to a shadowed binding does not. No control-flow-sensitive “after send” or
unreachable-branch recovery is attempted.

Only `ParenthesizedExpression` is transparent. `as`, `satisfies`, non-null,
angle-bracket assertion, and every other TypeScript assertion wrapper make the
affected critical slot unsupported, including nested mixed wrappers.

An eligible file is wholly unsupported when an unshadowed global identifier
`eval` or `Function` occurs in an executable value position. This deliberately
includes direct, optional, indirect, aliased, passed, returned, called, and
constructed forms; the analyzer does not inspect code strings or attempt to
prove a reference harmless. Declarations and uses that resolve to a shadowing
local binding are not global dynamic-code barriers.

The file is also wholly unsupported by any of these constructor-derived dynamic
execution forms:

- `Reflect.construct(Function, ...)` where both names resolve to the unshadowed
  globals;
- a call or `new` expression whose callee is a dot access with the exact static
  name `constructor`;
- a call or `new` expression whose callee is an element access with the exact
  static string name `"constructor"`;
- immediate invocation or construction of the result of either
  constructor-derived call.

This rejects forms such as `(() => {}).constructor("...")()`,
`(function () {}).constructor("...")`, and
`object["constructor"]("...")` without attempting arbitrary runtime analysis.
An ordinary property read named `constructor` that is not a call/new callee is
not this barrier, but it remains subject to critical-object escape and mutation
rules. A locally shadowed `Function` does not trigger the global-`Function`
barrier; constructor-named call/new syntax remains conservatively unsupported
regardless of receiver identity.

The same whole-file rule applies to an executable unshadowed global-object
reference through `globalThis`, `window`, `self`, or Node's `global`. This
closes same-file aliases such as `globalThis.Object` without modeling the
global object. A declaration that lexically shadows one of these names is not a
global-object barrier.

### 5.6 Prototype and own-property contract

Critical transaction properties are:

- `type`;
- `chainId`;
- `blobs`;
- `maxFeePerBlobGas`;
- `blobVersionedHashes`;
- `kzg`.

For every critical property:

- evidence must come from an own data property;
- inherited values are never evidence;
- a present inherited critical value makes the transaction unsupported when
  same-file analysis can expose it;
- identifier and quoted own keys are equivalent;
- computed keys, spread, duplicate critical keys, and shorthand critical keys
  fail closed;
- any getter, setter, or method on the submitted object fails closed,
  regardless of property name;
- identifier or quoted `"__proto__"` in an object literal rejects the object;
- ordinary non-critical own data properties remain allowed.

Prototype safety is deliberately conservative and does not build a
prototype-flow engine. Any executable property or element access whose static
name is `prototype` or `__proto__` is a whole-file barrier, regardless of the
receiver. This covers reads, alias creation, calls, assignment,
compound/logical assignment, increment/decrement, `delete`, and passing or
returning the value; the analyzer does not attempt to prove such an access
harmless. Object-literal `__proto__` keys use the separate rejection above.

The file is also unsupported when an unshadowed global `Object` or `Reflect`
identifier escapes as a bare value, when one of their methods is detached or
aliased, or when either is used through optional or computed-dynamic access.
Any computed-dynamic element access anywhere else in the eligible file is also
a whole-file barrier because it could acquire `prototype` or `__proto__`.
Static string element names are analyzed like dot names.

The only direct global built-in calls analyzed rather than rejected are
`Object.assign`, `Object.setPrototypeOf`, `Reflect.setPrototypeOf`,
`Object.defineProperty`, and `Object.defineProperties`; their critical targets
follow the all-critical-object target policy in section 5.5. Every other direct
`Object.*` or `Reflect.*` call, including `getPrototypeOf`, is a whole-file
barrier. `Reflect.construct(Function, ...)` is additionally rejected by the
dynamic-execution policy even though it is a direct `Reflect.*` call. This is
deliberately a small allowlist, not a general prototype-flow model.

The relevant provider, signer, or transaction proof is invalidated
file-globally by:

- `Object.setPrototypeOf(criticalObjectOrAlias, ...)`;
- `Reflect.setPrototypeOf(criticalObjectOrAlias, ...)`;
- `Object.defineProperty` or `Object.defineProperties` targeting a critical
  object or alias;
- `Object.assign` targeting a critical object or alias;
- any explicit executable `prototype` or `__proto__` access described above,
  including assignment, `delete`, aliases, or property access;
- `Object.defineProperty` or `Object.defineProperties` targeting
  `Object.prototype`;
- `__defineGetter__` or `__defineSetter__` on the transaction, its alias, or
  `Object.prototype`;
- an unknown receiver/argument escape that can alter a critical object or its
  prototype, including detached or aliased mutation helpers;
- a dynamic built-in target that cannot be proven unrelated to every critical
  object;
- the dynamic-execution barriers in section 5.5.

For the named built-ins, `Object` and `Reflect` mean unshadowed globals and the
method may use dot access or an exact static string element name. A shadowed
lookalike does not receive built-in semantics, but a call that receives the
provider, either signer subtype, transaction, or an alias is still rejected by
the general unknown escape rule.
`Object.create(...)`, class instances, and every other prototype-derived
transaction initializer are unsupported because the submitted transaction must
resolve to a direct object literal.

These checks are file-global even in a sibling function, an apparently
unreachable branch, or after the sink. The exact conservative policy is more
important than flow-sensitive recovery.

Runtime or cross-file prototype pollution is a declared limitation. A critical
proof assumes no unsupported external mutation of the submitted object's
prototype chain or JavaScript built-ins.

## 6. Ownership and provenance model

### 6.1 Ownership states

```ts
type OwnershipState =
  | "proven-arc"
  | "proven-non-arc"
  | "unknown"
  | "conflicting";
```

A C07B consumer may inspect transaction kind only when effective ownership is
`proven-arc`.

| Arc evidence | Non-Arc evidence | State            |
| ------------ | ---------------- | ---------------- |
| no           | no               | `unknown`        |
| yes          | no               | `proven-arc`     |
| no           | yes              | `proven-non-arc` |
| yes          | yes              | `conflicting`    |

Unknown-present evidence suppresses proof. Omitted optional evidence is neutral.
Known disagreement is always `conflicting`.

### 6.2 Provider RPC evidence

Supported RPC evidence is a direct ordinary string literal or one RPC binding.

- exact `https://rpc.testnet.arc.network` is Arc;
- known non-Arc evidence uses a private semantic copy of the reviewed C06B1
  host grammar: parse with `URL`, lowercase the hostname, remove one trailing
  dot, and lowercase the first non-empty path segment; classify
  `cloudflare-eth.com`, any hostname ending in `.infura.io` or `.alchemy.com`,
  any hostname containing `ethereum`, and `rpc.ankr.com` whose first path
  segment is `eth`, `eth_sepolia`, or `eth_holesky` as non-Arc;
- arbitrary strings are neutral unknown;
- template, concatenated, imported, computed, reassigned, cross-file, wrapped,
  malformed, and unsupported values are unknown-present.

C07A does not extract or alter the C06B1 helper. Tests lock this private copy to
the reviewed grammar so C06B1 behavior remains unchanged.

### 6.3 Provider-network grammar

The optional `JsonRpcProvider` network argument supports source tokens in only
these grammars, either directly or through its one provider-network binding:

- unsigned decimal-integer or hexadecimal direct safe-number literals;
- unsigned decimal-integer or hexadecimal direct bigint literals;
- exact registered name `"mainnet"` as known non-Arc.

Arc forms:

- `5042002`;
- `5042002n`;
- `0x4cef52`;
- `0x4cef52n`.

Another supported positive integral number/bigint token is non-Arc. Decimal or
hexadecimal strings, other registered names, unsafe numbers, zero, negative,
fractional, exponent, binary, octal, separator-bearing, arithmetic, coercion,
dynamic, imported, or wrapped values are unknown-present. A provider-network
identifier is supported only when it is the one immutable binding whose
initializer is a direct supported literal; every other identifier is
unknown-present. An explicit unknown-present network argument is sticky and
cannot be rescued by RPC or transaction `chainId`.

### 6.4 Transaction-chainId grammar

An own `chainId` data property supports positive integral direct:

- unsigned decimal-integer or hexadecimal safe-number literals;
- unsigned decimal-integer or hexadecimal bigint literals;
- decimal strings matching `^[0-9]+$`;
- hexadecimal strings matching `^0[xX][0-9a-fA-F]+$`.

Arc forms include `5042002`, `5042002n`, `0x4cef52`, `0x4cef52n`,
`"5042002"`, and `"0x4cef52"`. Hexadecimal strings compare
case-insensitively.

Another supported positive integral value is non-Arc. Leading zeroes in a
string are allowed and values compare numerically. Nullish, unsafe, zero,
negative, fractional, exponent, binary, octal, separator-bearing numeric,
separator-bearing string, signed string, identifier, call, conditional,
arithmetic, coercion, imported, inherited, accessor, method, computed, spread,
duplicate, shorthand, mutated, or wrapped forms are unknown-present.

Transaction `chainId` transitions:

| Provider state    | Omitted          | Arc           | Non-Arc          | Unknown-present |
| ----------------- | ---------------- | ------------- | ---------------- | --------------- |
| `proven-arc`      | `proven-arc`     | `proven-arc`  | `conflicting`    | `unknown`       |
| `proven-non-arc`  | `proven-non-arc` | `conflicting` | `proven-non-arc` | `unknown`       |
| neutral `unknown` | `unknown`        | `proven-arc`  | `proven-non-arc` | `unknown`       |
| sticky `unknown`  | `unknown`        | `unknown`     | `unknown`        | `unknown`       |
| `conflicting`     | `conflicting`    | `conflicting` | `conflicting`    | `conflicting`   |

### 6.5 Signer provenance

| Provenance               | Exact construction           | Reviewed behavior                     |
| ------------------------ | ---------------------------- | ------------------------------------- |
| `ethers-wallet`          | `new Wallet(key, provider)`  | populate, sign, broadcast             |
| `ethers-json-rpc-signer` | `await provider.getSigner()` | format and send `eth_sendTransaction` |

Provenance survives provider-to-signer resolution and is retained on every
submission result. The two subtypes never borrow supporting-field semantics
from one another.

### 6.6 Private analyzer result

Conceptually:

```ts
interface EthersSubmission {
  readonly provenance: "ethers-wallet" | "ethers-json-rpc-signer";
  readonly sink: "sendTransaction";
  readonly ownership: OwnershipState;
  readonly callOffset: number;
  readonly transaction: ObjectLiteralExpression;
}
```

The exact private representation may differ, but it must not expose compiler
types through public declarations or exports. Analyzer results are returned in
ascending `callOffset` order. Repeated analysis of identical source must return
the same sequence; traversal or collection order must not depend on map/set
insertion from unrelated declarations.

## 7. C07B transaction-kind contract

```ts
type TransactionKind = "proven-blob" | "proven-non-blob" | "unknown";
```

The `type` property must be an own, statically named data property.

- exact decimal source token `3` after removing only balanced parentheses:
  `proven-blob`;
- exact decimal source token `0`, `1`, `2`, or `4`:
  `proven-non-blob`;
- omitted, inherited, dynamic, unsupported, or every other form: `unknown`.

Runtime-equivalent forms are intentionally unsupported:

- `"3"`;
- `3n`;
- `3.0`;
- `3e0`;
- `0x3`;
- `0b11`;
- `0o3`;
- separator-bearing numeric literals;
- unary or signed forms;
- identifiers, templates, concatenation, arithmetic, calls, or computed
  values;
- assertion wrappers.

Supporting-field matrix:

| Field                                 | `ethers-wallet`            | `ethers-json-rpc-signer`   |
| ------------------------------------- | -------------------------- | -------------------------- |
| non-empty dense `blobs`               | serialization support only | not forwarded in 6.17.0    |
| `maxFeePerBlobGas`                    | serialization support only | not forwarded in 6.17.0    |
| non-empty dense `blobVersionedHashes` | serialization support only | forwarded RPC support only |
| `kzg`                                 | helper only                | not forwarded in 6.17.0    |

No supporting field upgrades omitted, dynamic, unknown, or exact type 2 to
`proven-blob`. Exact type 3 is sufficient even when supporting fields are
absent.

Supporting-value provenance is not transaction-kind provenance. In particular,
an ethers `toBlobs(...)` call, a `kzg` identifier, a
`blobVersionedHashes` value, or any other blob-looking value never upgrades
kind. A syntactically unsupported supporting value supplies no supporting
evidence but does not veto an otherwise structurally safe exact type-3
transaction; object accessors, methods, spreads, computed/duplicate critical
keys, mutation, dynamic execution, and prototype barriers still reject as
specified.

Supported arrays are non-empty, dense, direct arrays with present,
non-spread, syntactically non-nullish elements. `[blob,]` is dense. `[]`,
`[blob,,]`, `[,]`, spread-only, direct-plus-spread, and nullish-element arrays
provide no support. A supporting array may use its one binding and remains
subject to mutation and prototype safety.

`maxFeePerBlobGas` support is a direct non-negative safe-number or bigint
literal, including zero, or its one value binding. Unsupported values provide
no supporting evidence but do not erase an otherwise structurally safe exact
type-3 proof.

Computed, spread, duplicate, shorthand, accessor-bearing, method-bearing,
`__proto__`-bearing, prototype-mutated, or otherwise unsafe structure rejects
the whole transaction before kind classification.

### 7.1 C07B finding and remediation contract

C07B filters the ordered C07A submissions to supported `proven-arc`,
`proven-blob` violations, selects the violation with the smallest `callOffset`,
and emits at most one finding per file. An earlier unsupported, ambiguous,
non-Arc, conflicting, or non-blob sink is skipped and must not suppress a later
supported violation. Existing input-file order remains stable, and repeated
execution over identical inputs must select the same sink and return findings
in the same order.

The exact finding message is:

```text
Arc transaction submission uses EIP-4844 transaction type 3, which Arc does not support.
```

The exact suggested fix is:

```text
Submit a type-2 EIP-1559 transaction on Arc instead (`type: 2`) and remove any blob-only fields present in the submitted transaction.
```

The message and suggested fix describe only the selected supported submission.
They do not use “appears to assume” and do not claim repository-wide coverage,
runtime execution, or live RPC rejection.

## 8. Explicit C07C deferral

C07A/B implements no production viem path. C07C must separately decide and
review:

- own versus inherited property semantics;
- identifier and quoted `__proto__`;
- `Object.prototype` mutation;
- `viem-json-rpc-account`, local/custom, and unknown account provenance;
- imported, factory, private-key, and custom `signTransaction` accounts;
- formatters, serializers, and `prepareTransactionRequest`;
- `assertChainId`;
- request/client account and chain overrides;
- viem `sendTransaction`;
- `writeContract` forwarding;
- exact `type: "eip4844"` semantics;
- custom transports, HTTP options, and client extensions.

The current milestone does not decide these consumer semantics. Their absence is
an explicit deferral, not conditional support.

## 9. Threat model

### 9.1 False-positive threats

- Arc text belongs to an unrelated sibling flow.
- A same-named provider or signer is shadowed.
- A local/wrong-package constructor or arbitrary object mimics ethers methods.
- Provider RPC and network arguments conflict.
- Transaction `chainId` conflicts with provider ownership.
- An unsupported provider network string is treated as transaction
  `BigNumberish` evidence.
- Wallet supporting fields are used as kind proof despite inferred type 2.
- JsonRpcSigner is credited with fields its formatter does not forward.
- Type 3 is inherited rather than an own data property.
- `__proto__` injects type, chain ID, an accessor, or a mutation surface.
- A prototype getter changes an own critical property during library access.
- `Object.setPrototypeOf`, `Object.prototype`, `defineProperty`, or legacy
  getter/setter APIs mutate effective values before or after the sink.
- `Object.defineProperty`, `Object.defineProperties`, `Object.setPrototypeOf`,
  `Reflect.setPrototypeOf`, or `Object.assign` replaces provider `getSigner`,
  signer `sendTransaction`, transaction evidence, or an approved alias.
- A named built-in mutator uses a dynamic target that may alias a critical
  object.
- A critical binding is mutated through a property, element, alias,
  destructuring target, loop target, `Object.assign`, or array method.
- Direct/indirect eval, global `Function`, `Reflect.construct(Function, ...)`,
  or a constructor-derived call changes a critical object or built-in.
- A transaction `chainId` or `type` identifier is mistaken for an allowed
  one-binding value.
- Alternate numeric spelling is normalized into exact source token `3`.
- Optional, element, detached, missing, extra, omitted, or spread call syntax
  is accepted.
- A preparation, signing, simulation, estimate, contract send, deploy, or raw
  broadcast is mistaken for the supported sink.

### 9.2 False-negative and declared unsupported threats

- imported or cross-file providers, signers, and transactions;
- CommonJS, ethers v5, subpackages, wrappers, subclasses, BrowserProvider,
  injected providers, Contract sends, deploys, and custom runners;
- omitted or inferred transaction kind;
- alias chains and control-flow-selected values;
- harmless call/new expressions whose callee is statically named `constructor`;
  these are deliberately rejected to avoid analyzing constructor-derived code;
- runtime or cross-file prototype pollution;
- JSX/TSX, mjs/cjs, and inter-file flow;
- all C07C surfaces.

The initial ethers-only slice intentionally prefers a smaller truthful surface.

### 9.3 Architecture and boundary threats

- reintroducing C07C production behavior into C07A/B;
- creating a generic AST framework before two consumers prove stable common
  semantics;
- exposing compiler types publicly;
- loading TypeScript for disabled rules or unsupported files;
- changing C06B1 while attempting reuse;
- changing canonical tuple, inventory, public API, dependencies, reporter
  schemas/formats, scoring algorithms, or exit algorithms;
- retaining heuristic “appears to assume” wording or selecting a violating sink
  nondeterministically;
- claiming per-input finding, score, status, or exit outcomes are unchanged
  after deliberate false-positive removal.

## 16. Decision log

### 2026-07-24 — Keep capability and consumer separate

C07A establishes private ethers ownership without findings. C07B consumes only
the independently approved C07A contract.

### 2026-07-24 — Keep C06B1 unchanged

C07 uses a private ethers-specific analyzer. Shared extraction requires later
proof from multiple real consumers.

### 2026-07-24 — Preserve ethers signer provenance

Wallet and JsonRpcSigner retain distinct result variants and supporting-field
semantics.

### 2026-07-24 — Require exact own transaction kind

Only an own data property with exact decimal source token `3` proves blob kind.
Supporting fields and inferred type never upgrade kind.

### 2026-07-24 — Separate provider and transaction numeric grammars

Provider-network values and transaction `chainId` use independent syntax and
sticky-unknown rules.

### 2026-07-24 — Lock one canonical per-slot binding budget

RPC URL, provider network, provider, each signer subtype, transaction, and
supporting values have the exact direct/one-binding ceilings in section 5.4.
Transaction `chainId` and `type` are direct-own-value slots with no identifier
binding. D01 tests direct cases and the listed ownership/submission bindings;
supporting-value bindings remain governed by their canonical table rows and
P07/B09-B13. D02 rejects depth + 1 for every binding-enabled slot and treats a
transaction-`chainId` or transaction-`type` identifier as unknown at its first
hop. The canonical table overrides no call-grammar restriction.

### 2026-07-24 — Use file-global mutation and prototype invalidation

C07 does not recover proof based on statement order or apparent reachability.
Same-file critical and prototype mutations invalidate conservatively. Named
built-in mutators apply to provider, both signer subtypes, transaction, and
approved aliases; unknown targets reject the file unless lexical identity proves
they are unrelated.

### 2026-07-24 — Reject constructor-derived dynamic execution

C07 does not inspect code strings or infer the runtime identity of a
constructor-derived callable. Global `Function`,
`Reflect.construct(Function, ...)`, and constructor-named call/new syntax are
whole-file barriers. Harmless constructor calls may therefore be missed by C07B
instead of weakening critical evidence.

### 2026-07-24 — Lock deterministic finding text and selection

C07B emits at most one finding per file for the supported violation with the
smallest `callOffset`. Its exact message and suggested fix are part of the
observable contract, repeated runs select identically, and existing input-file
order remains stable.

### 2026-07-24 — Keep package evidence phase-specific

R03 belongs only to C07A and proves that the private analyzer has no production
import or package impact before a consumer exists. C07B deliberately reverses
that reachability condition: R08 proves the hardened rule privately imports the
analyzer, the production bundle and tarball include it, compiler loading remains
external and lazy, declarations leak no compiler types, and public,
dependency, inventory, and canonical boundaries remain unchanged.

### 2026-07-24 — Split C07C after repeated architecture blockers

C07-RR-11 proved that own/inherited property and prototype behavior can replace
apparent account provenance. C07-RR-12 showed that the prior plan still left
consumer support conditional. The approved correction is:

- C07A: ethers ownership capability;
- C07B: ethers-only rule hardening;
- C07C: separately planned deferred-library ownership and consumer.

The current plan does not implement or conditionally enable C07C production
behavior.
