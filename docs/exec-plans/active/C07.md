# C07 — Arc Transaction-Submission Ownership

Status: Draft

Risk class: R3

Owner: ArcReady maintainers

Base branch: `main`

Base SHA: `49b95b85d13a223e902bd66dde7c630d78871fa5`

Last reviewed: 2026-07-24

## 1. Product goal

Associate a concrete transaction-submission sink with a proven Arc provider or
chain context so ArcReady can make transaction-specific compatibility findings
without relying on unrelated file-level keywords.

The first consumer is `wallet/NO_BLOB_TX_ON_ARC`. The ownership capability is
also a prerequisite for C06B2 write-side native-versus-ERC-20 USDC amount
analysis and later transaction-specific gas or fee checks.

Success means ArcReady can answer all three questions for a bounded same-file
JavaScript or TypeScript flow:

1. Is this call a supported transaction-submission sink?
2. Is the receiver and effective call context proven to target Arc?
3. Is the submitted transaction object structurally safe enough to inspect?

The milestone must prefer no finding over a critical finding based on ambiguous,
conflicting, imported, computed, reassigned, or cross-file evidence.

## 2. Decision

Decision: **Build**, in two separately reviewable implementation slices.

- **C07A — private transaction-ownership analyzer:** add a domain-specific,
  private, lazy TypeScript AST analyzer and tests. C07A must not change findings,
  rule inventory, canonical runtime, public exports, reporters, scoring, or exit
  behavior.
- **C07B — harden `wallet/NO_BLOB_TX_ON_ARC`:** replace the current file-level
  keyword detector with the approved C07 ownership and structured-transaction
  contract. Keep the rule non-canonical.

C07A and C07B should normally be separate PRs. C07B must not begin until C07A's
contract, threat model, acceptance matrix, and implementation have passed
independent review.

A generic shared AST framework is **not** approved in C07. C06B1 currently has
one working private analyzer. Extracting its lexical or ownership machinery now
would increase regression surface before a second proven consumer exists. C07A
may duplicate the smallest domain-specific mechanics required for its contract.
After C07B and C06B2 provide at least two real consumers, a later R3 proposal may
compare duplication and extract only semantics proven identical by tests.

Canonicalization is not part of C07. A separate milestone may consider a
FindingV2 adapter only after C07B passes adversarial review, package validation,
and representative-repository pilot cases.

## 3. Premise and sources

Sources were revalidated on 2026-07-24.

### Arc and Circle

- Arc infrastructure integration states that EIP-4844 blob transactions are not
  supported:
  https://docs.arc.io/integrate/infrastructure
- Arc bridge integration explicitly says to use type-2 EIP-1559 transactions and
  not EIP-4844 blob transactions:
  https://docs.arc.io/integrate/infrastructure/bridges
- Arc Testnet chain ID is `5042002`, the primary RPC is
  `https://rpc.testnet.arc.network`, and USDC is the native gas token:
  https://docs.arc.io/arc/references/connect-to-arc
- Arc uses EIP-1559-style fee fields denominated in native USDC accounting units:
  https://docs.arc.io/arc/references/gas-and-fees

### viem

- A Wallet Client is created with a transport and may hoist a chain; the chain is
  used by `sendTransaction` and `writeContract` to assert the target chain:
  https://viem.sh/docs/clients/wallet
- `walletClient.sendTransaction` creates, signs, and sends a transaction. It
  supports a call-site `chain` and documents `blobs` and `kzg` for blob
  transactions:
  https://viem.sh/docs/actions/wallet/sendTransaction
- `walletClient.writeContract` internally uses the Wallet Client's
  `sendTransaction` action and is therefore a submission sink:
  https://viem.sh/docs/contract/writeContract
- `prepareTransactionRequest` and `signTransaction` do not submit by themselves;
  the documented sign flow submits only at `sendRawTransaction`:
  https://viem.sh/docs/actions/wallet/signTransaction

### ethers v6

- `Signer.sendTransaction` populates and sends a transaction. A Signer's provider
  supplies network context:
  https://docs.ethers.org/v6/api/providers/
- `populateTransaction` prepares a transaction but does not submit it:
  https://docs.ethers.org/v6/api/providers/
- Ethers transaction objects expose blob-related properties including `blobs`,
  `maxFeePerBlobGas`, and transaction `type`:
  https://docs.ethers.org/v6/api/transaction/
- Contract method `.send` is a submission operation, while
  `.populateTransaction` is preparation only:
  https://docs.ethers.org/v6/api/contract/

### Source limits

The sources establish product and library semantics. They do not prove arbitrary
user wrappers, imported clients, runtime-selected chains, dynamically built
objects, or inter-file flow. Those remain unsupported until a later milestone
explicitly models them.

## 4. Current state

### Existing blob rule

`packages/arcready/rules/wallet/no-blob-tx-on-arc.ts` currently:

- scans wallet files as text;
- requires only a broad file-level Arc marker;
- reports when any active line contains `blobVersionedHashes`,
  `maxFeePerBlobGas`, `type: 3`, or blob-related prose;
- cannot prove that the line belongs to a transaction;
- cannot prove that the transaction is submitted;
- cannot associate the transaction with the Arc-owned receiver;
- can combine an Arc marker from one flow with blob text from an unrelated
  Ethereum sibling flow.

The backlog therefore classifies the rule as Research and non-canonical until
Arc transaction-submission ownership exists.

### Existing TypeScript AST capability

C06B1 added `arc-usdc-amount-analyzer.ts`, a private lazy TypeScript AST analyzer
for same-file `.js` and `.ts`. It includes bounded lexical binding, import
identity, reassignment rejection, direct and one-binding value flow, Arc/non-Arc
ownership, safe object checks, and fail-closed parsing.

C07 must learn from those contracts but must not refactor or broaden C06B1 in the
same milestone.

### Baseline boundaries

At the C07 planning baseline:

- known rule inventory: 19;
- default rules: 17;
- wallet rules: 7;
- canonical FindingV2 runtime: exactly 4 rules;
- `wallet/NO_BLOB_TX_ON_ARC`: active legacy, default critical, non-canonical;
- `wallet/ARC_USDC_AMOUNT_CONVERSION`: active legacy, non-canonical;
- TypeScript runtime dependency: exact `5.9.3`, loaded lazily by eligible AST
  analysis;
- no public AST or ownership API exists.

## 5. Scope

### 5.1 C07A supported file surface

- plain `.js` and `.ts` files only;
- exclude `.d.ts`;
- exclude `.test.js`, `.test.ts`, `.spec.js`, and `.spec.ts`;
- exclude files below `test`, `tests`, or `__tests__` directories;
- reject source files with TypeScript parse diagnostics;
- skip ambient declarations, string-named module declarations, type-only syntax,
  comments, strings, and non-executable declaration surfaces;
- load TypeScript lazily only when an enabled consumer has an eligible file.

`.jsx`, `.tsx`, `.mjs`, `.cjs`, Solidity, JSON, YAML, generated code, and
inter-file project analysis are non-goals for the initial slice.

### 5.2 Lexical and import surface

Support:

- ESM named imports and aliases from exact module `viem`;
- ESM namespace imports from exact module `viem`;
- ESM named imports and aliases from exact module `ethers`;
- ESM namespace imports from exact module `ethers`;
- one immutable same-file `const` binding for supported chain, transport,
  provider, signer, client, and transaction objects;
- nearest lexical declaration across source, block, function, class-expression,
  namespace/module-block, catch, loop, and case scopes;
- rejection of duplicate declarations, use-before-declaration, reassignment,
  increment/decrement writes, unsupported destructuring, and local shadowing.

Do not support:

- CommonJS `require`;
- ethers v5 `@ethersproject/*` packages;
- imports from wrapper packages, wagmi, RainbowKit, App Kit adapters, or local
  modules;
- re-exported or imported client/provider/signer objects;
- dependency-version inference from lockfiles;
- more than one binding hop;
- wrapper functions, factory abstractions, class fields, mutation, or control-flow
  dependent assignment.

### 5.3 Ownership evidence states

Every supported receiver and effective call must resolve to exactly one of:

- `proven-arc`;
- `proven-non-arc`;
- `unknown`;
- `conflicting`.

A critical consumer may inspect a submission only when the result is
`proven-arc`.

Evidence merge rules:

| Arc evidence | Non-Arc evidence | State |
| --- | --- | --- |
| no | no | `unknown` |
| yes | no | `proven-arc` |
| no | yes | `proven-non-arc` |
| yes | yes | `conflicting` |

Known Arc evidence:

- direct literal numeric chain ID `5042002`;
- direct literal hexadecimal equivalent;
- direct literal string chain ID where the supported library accepts it;
- exact RPC string `https://rpc.testnet.arc.network`;
- an approved direct Arc chain object with literal `id: 5042002`.

Known non-Arc evidence:

- a direct supported chain ID other than `5042002`;
- known Ethereum mainnet, Sepolia, or Holesky RPC hosts already covered by the
  C06B1 ownership policy;
- a call-site chain that directly conflicts with Arc receiver evidence.

An arbitrary unknown RPC host is neutral, not non-Arc. A chain or RPC expression
that is imported, computed, spread, duplicated, reassigned, or otherwise
unsupported is unknown. Unknown evidence never upgrades a flow to Arc.

### 5.4 viem receiver ownership

Initial supported receiver:

```ts
const walletClient = createWalletClient({
  chain: { id: 5042002 },
  transport: http("https://rpc.testnet.arc.network")
});
```

Approved variations may use:

- imported alias or namespace identity for `createWalletClient` and `http`;
- a direct config object or one immutable config binding;
- a direct chain object or one immutable chain binding;
- a direct literal Arc RPC or one immutable string binding;
- `custom(...)` or `http()` as neutral transport evidence when the direct chain
  independently proves Arc;
- exact Arc RPC evidence when chain is omitted or unknown;
- a direct call-site `chain` on `sendTransaction` or `writeContract`.

The effective submission state merges client config evidence and call-site chain
evidence. Any proven Arc/non-Arc contradiction is `conflicting` and fails closed.

Do not infer Arc from:

- receiver identifier names such as `arcClient`;
- an account address;
- transaction recipient address;
- an unrelated Arc client in the same file;
- a Public Client method;
- `http()` with no Arc chain evidence;
- a custom transport with no Arc chain evidence;
- a chain object imported from another file;
- a `viem/chains` import unless a later reviewed slice explicitly pins the exact
  exported Arc chain identity and supported viem version.

### 5.5 viem submission sinks

Initial sinks:

- `walletClient.sendTransaction(transaction)`;
- `walletClient.writeContract(request)`.

Both receiver identity and ownership must be proven. The call must not use
optional chaining. The submitted argument must be a direct object literal or one
immutable same-file binding when a consumer needs structured fields.

Explicit non-sinks:

- `prepareTransactionRequest`;
- `signTransaction`;
- `simulateContract`;
- `estimateGas` or `estimateContractGas`;
- `readContract`;
- detached or destructured method references.

Deferred submission surfaces:

- `sendTransactionSync` and `writeContractSync`;
- standalone functions imported from `viem/actions`;
- `getContract(...).write.*` contract instances;
- `sendRawTransaction` and signed serialization flow;
- `sendCalls` / EIP-5792 call bundles;
- direct EIP-1193 `request({ method: "eth_sendTransaction" })`;
- custom client extensions.

These are real submission paths but are excluded to keep the first semantic
surface auditable. They require separate acceptance matrices and must not be
silently accepted by generic method-name matching.

### 5.6 ethers v6 receiver ownership

Initial provider forms:

```ts
const provider = new JsonRpcProvider(
  "https://rpc.testnet.arc.network",
  5042002
);
```

Support:

- imported alias or namespace identity for `JsonRpcProvider` and `Wallet` from
  exact module `ethers`;
- direct provider construction or one immutable provider binding;
- direct Arc RPC and supported direct network argument;
- a Wallet constructed with the proven provider;
- `const signer = await provider.getSigner()` in a valid async or top-level-await
  context;
- one immutable signer binding;
- `signer.sendTransaction(transaction)`.

The Signer inherits provider ownership. Conflicting RPC and network evidence
fails closed.

Do not support:

- `BrowserProvider` or injected EIP-1193 providers without static Arc evidence;
- `Wallet` without a provider;
- imported, wrapped, subclassed, reassigned, or cross-file providers/signers;
- `Contract` dynamic method calls in C07A;
- `provider.broadcastTransaction`;
- ethers v5 APIs or subpackages;
- generic objects that merely have a `sendTransaction` method.

### 5.7 ethers v6 submission sinks

Initial sink:

- `signer.sendTransaction(transaction)` for a signer whose provider ownership is
  proven.

Explicit non-sinks:

- `signer.populateTransaction`;
- `signer.signTransaction`;
- `provider.estimateGas`;
- `provider.call`;
- contract method `.populateTransaction`;
- contract method `.staticCall`;
- contract method `.estimateGas`.

Deferred sinks:

- ethers Contract method `.send`;
- callable non-view Contract methods whose send/call behavior depends on ABI;
- `ContractFactory.deploy`;
- `provider.broadcastTransaction` and signed raw transactions;
- custom `ContractRunner` implementations.

### 5.8 Structured transaction object

For consumers that inspect transaction fields, the supported object is:

- a direct object literal passed to the sink; or
- one immutable same-file `const` binding whose initializer is the object.

Fail closed when the object contains:

- spread assignments;
- computed property names;
- duplicate critical properties;
- getters, setters, methods, or shorthand for a critical property;
- conditional, merged, factory-produced, imported, cross-file, or reassigned
  structure;
- more than one binding hop.

Non-critical ordinary transaction fields may remain present. Safety checks must
be scoped to the fields that determine ownership or the consumer finding.

### 5.9 C07B blob evidence

C07B may report only when all conditions hold:

1. the call is a supported submission sink;
2. the effective receiver/call ownership is `proven-arc`;
3. the submitted object is structurally supported;
4. at least one approved direct blob signal is proven.

Initial approved blob signals:

- `blobs` is a direct non-empty array literal;
- `blobs` is one immutable binding to a direct non-empty array literal;
- `blobs` is a direct call to an exact viem `toBlobs` import inside a supported
  viem submission object;
- `maxFeePerBlobGas` is a concrete non-nullish expression in an ethers
  transaction object;
- transaction `type` is the direct numeric literal `3` in an ethers transaction
  object.

Policy details:

- `blobs: []`, `blobs: null`, and `blobs: undefined` do not prove blob usage;
- an arbitrary identifier used as `blobs` does not prove non-empty content unless
  it resolves through the one approved binding to a supported literal;
- `kzg` alone does not prove a submitted blob transaction;
- prose, comments, strings, docs, test files, and variable names do not count;
- `blobVersionedHashes` is deferred until a supported raw JSON-RPC or library
  transaction surface is documented and modeled;
- no generic `EIP-4844` keyword matching remains in the hardened rule.

## 6. Evidence and ownership model

### 6.1 Analyzer result

C07A should expose a private internal result shaped conceptually as:

```ts
type OwnershipState =
  | "proven-arc"
  | "proven-non-arc"
  | "unknown"
  | "conflicting";

interface TransactionSubmission {
  readonly library: "viem" | "ethers-v6";
  readonly sink: "sendTransaction" | "writeContract";
  readonly ownership: OwnershipState;
  readonly callOffset: number;
  readonly transaction?: ObjectLiteralExpression;
}
```

The exact private type may differ after implementation review. It must not expose
TypeScript compiler types through public declarations or package exports.

### 6.2 Association rules

- Receiver identity is lexical, not name-based.
- Library identity comes from exact imports, not method names.
- Ownership belongs to the receiver/provider/signer and supported call-site chain.
- Transaction evidence belongs to the exact argument submitted at that sink.
- An Arc sibling receiver cannot lend ownership to another receiver.
- An Arc call-site chain cannot override proven non-Arc receiver evidence; the
  result is conflicting.
- Unknown evidence cannot be treated as Arc because a blob field exists.
- A prepared or signed object is not a submission until it reaches a supported
  sink.

### 6.3 Finding policy

C07A produces no user-visible findings.

C07B should preserve the existing rule ID, preset, default severity, docs key,
and one finding per file behavior unless independent review approves a specific
change. The message must state that a proven Arc submission includes an
unsupported blob transaction configuration; it must not claim repository-wide
or runtime certainty.

## 7. Architecture options

### Option A — Continue regex and file-level association

Rejected.

Advantages:

- smallest code change;
- no additional AST logic.

Disadvantages:

- cannot prove sink, receiver, object, or Arc ownership;
- known multichain false positives remain;
- prose and unrelated sibling flows remain conflated;
- cannot safely support C06B2.

### Option B — Refactor C06B1 into a generic shared AST framework now

Rejected for C07.

Advantages:

- less duplicated lexical code in the long term;
- one generalized ownership substrate.

Disadvantages:

- changes a working C06B1 analyzer before a second consumer contract is proven;
- couples amount semantics and transaction semantics;
- creates an abstraction whose API would be designed from anticipated rather
  than demonstrated reuse;
- increases regression and package-smoke risk in the prerequisite milestone.

### Option C — Domain-specific private C07 analyzer, then prove reuse

Chosen.

Advantages:

- isolates transaction ownership from amount analysis;
- keeps C07A behavior-preserving;
- permits exhaustive review before the critical rule changes;
- provides a stable contract for C07B and later C06B2;
- allows later extraction based on measured duplicated semantics.

Cost:

- some bounded lexical and object-safety logic may temporarily duplicate C06B1.

The duplication is accepted only when accompanied by equivalent mutation tests.
A later extraction proposal must show two consumers, a smaller total semantic
surface, and behavior-preserving tests.

## 8. Threat model

### False-positive threats

- Arc text appears elsewhere in the file but the sink uses Ethereum.
- An Arc client and Ethereum client are siblings.
- A same-named client or signer is shadowed in another scope.
- A local lookalike `createWalletClient`, `JsonRpcProvider`, or `Wallet` is used.
- A method named `sendTransaction` belongs to an arbitrary object.
- A transaction is prepared, signed, simulated, estimated, or documented but not
  submitted.
- The client is Arc but a call-site chain is non-Arc.
- The provider RPC is Arc but the explicit network argument is non-Arc.
- Blob fields occur inside comments, strings, examples, tests, declarations, or
  an unrelated object.
- `blobs` is empty, nullish, computed, duplicated, or spread.
- `kzg` exists without blobs.
- A transaction object is mutated after initial construction.

### False-negative threats

- imported or cross-file clients and signers;
- viem `sendTransactionSync`, standalone actions, raw transactions, EIP-5792,
  or contract instances;
- ethers Contract sends, deployments, custom runners, and broadcast of signed
  transactions;
- CommonJS and ethers v5;
- wrapper factories and dependency injection;
- more than one binding hop;
- dynamically selected chains, transports, providers, or transaction objects;
- non-literal blob arrays or helper functions other than exact viem `toBlobs`;
- JSX/TSX wallet code.

These are declared limitations, not accidental omissions. The initial slice
optimizes for high-confidence evidence rather than broad coverage.

### Architecture threats

- silently turning C07 into a generic program-analysis framework;
- exposing compiler types through public declarations;
- loading TypeScript for disabled rules or unsupported files;
- changing C06B1 behavior while trying to share helpers;
- changing rule inventory, canonical tuple, scoring, or reporter behavior;
- permitting one consumer's permissive object policy to weaken another's
  critical evidence contract.

## 10. Implementation slices

Line budgets below are review-decomposition targets, not quality caps. If a
slice exceeds its target because required correctness or tests demand more work,
split the slice; do not weaken validation.

### C07A.1 — Parser, lexical identity, and private model

Goal:

- establish eligible files, lazy compiler loading, executable traversal, import
  identity, lexical binding, and reassignment rejection;
- define private ownership/submission result types;
- no rule behavior changes.

Expected files:

- new `packages/arcready/rules/wallet/arc-transaction-submission-analyzer.ts`;
- new focused test file;
- no public export.

Target budget:

- production: 300–500 lines;
- tests: 500–900 lines.

Targeted validation:

```text
corepack pnpm --filter arcready test -- arc-transaction-submission-analyzer
corepack pnpm --filter arcready build
```

Stop conditions:

- compiler types leak into generated declarations;
- TypeScript loads for disabled/unsupported paths;
- lexical mutation classes are not fully covered;
- implementation requires changing C06B1.

### C07A.2 — viem ownership and sinks

Goal:

## 15. Decision log

### 2026-07-24 — Split capability from rule hardening

C07A will establish ownership without changing findings. C07B will consume the
approved capability to harden `NO_BLOB_TX_ON_ARC`. This prevents rule behavior
from hiding analyzer defects during initial review.

### 2026-07-24 — Do not extract a generic AST framework

C06B1 remains unchanged. C07 will use a private transaction-specific analyzer.
Shared extraction may be reconsidered only after multiple real consumers prove a
stable common contract.

### 2026-07-24 — Limit initial sinks

The first slice supports viem `sendTransaction`/`writeContract` and ethers v6
`Signer.sendTransaction`. Sync actions, raw transactions, EIP-1193 requests,
contract instances, deployment, and wrappers are deferred to avoid broad
method-name heuristics.

### 2026-07-24 — Blob evidence must be structured and submitted

C07B removes generic blob prose and file-level keyword association. A finding
requires an approved blob field on the exact structured object passed to a
proven Arc submission sink.

## 16. Residual limitations

Even after C07B, ArcReady will not claim coverage for:

- imported or inter-file transaction clients, providers, signers, chains, or
  objects;
- CommonJS, ethers v5, JSX/TSX, mjs/cjs, or wrapper libraries;
- viem sync, raw, standalone action, contract-instance, or EIP-5792 submissions;
- ethers Contract sends, deployments, raw broadcast, BrowserProvider, or custom
  runners;
- direct EIP-1193 and JSON-RPC `eth_sendTransaction` requests;
- dynamically built, spread, computed, conditional, or mutated transaction
  objects;
- arbitrary blob-producing helper functions;
- runtime wallet network state;
- live RPC acceptance or rejection;
- canonical FindingV2 output.

These limitations must appear in user-facing rule documentation after C07B.
